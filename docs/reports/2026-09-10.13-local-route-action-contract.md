# Retained large-move failure and the effective action contract

## Finding

The effective executor contract blocks at least one legal distant relocation.
This is direct evidence of an executor limitation, not proof that insufficient
training explains the rejection. It does not yet establish that a better-scoring
factory is unreachable through the existing action domain.

The selected evaluation 208 / factory 0 / action 11 moves facility index 13
(display number 14, seed collector) from (2, 24) to (32, 3), rotation 0. Its body
fits. The baseline rejects the input belt, chain 28, with `local-no-path`.
The unchanged current witness identity is
`6df34232c00c5651915ae7318bd93fad9c6f3f953bc3f7965a12e41150f9a119`.

In an isolated checkout at `410aaef`, raising the per-edit new-bridge allowance
from 2 to 12 and routing output chain 43 before input chain 28 recovers the exact
same facility pose. It uses **4,964 expansions within the original 5,000 budget**.
The original full-factory validator accepts it as `accepted_exploration`, without
changing the request, canvas extent, catalogs, ports or external-boundary rules.
The candidate adds 12 bridges: four for chain 43 and eight for chain 28.

The score changes from `[1672, 346, 94]` to `[1672, 456, 108]`: area is unchanged,
transport tiles increase by 110, and turns increase by 14. This establishes a
missing executable transition, **not a missed immediate improvement**. Its value
as a preparatory move for a later contraction has not been measured.

## Exact obstacle and routing evidence

Only chains 28 and 43 are initially selected for reembedding. All other facilities
and most existing routing remain fixed. The local extent is x=0..37, y=0..43.

- Chain 28 must connect (1, 22) to the moved input at (32, 8).
- Chain 43 must connect the moved output at (32, 2) to (2, 22).
- The normal executor permits only two newly installed bridges for the entire
  edit. This is an implementation neighborhood bound, not a game rule.
- The first recovered chain-28 path crosses existing chains 57, 59, 41 and 13 at
  (6, 22), (6, 19), (13, 12) and (15, 11), respectively. With allowances 2 and 3,
  the local path search reports no path; allowance 4 finds this four-bridge path.
- In both routing orders, the first selected short route uses (15, 11). After its
  bridge is installed, this occupied component cannot host another crossing.
  Excluding that crossing explicitly still permits a longer seven-bridge first
  route. Therefore it is a shared short-route bottleneck, not a unique mandatory
  passage or proof of geometric impossibility.

The deterministic sequential router neither revisits the first selected path nor
automatically expands the reroute set to blocking neighboring chains. A failed
second route ends the transaction. Raising a work counter alone cannot repair
this restricted neighborhood.

## What actions are actually available to the learner?

The learner selects from an enumerated action list; it does not draw belt paths.
The deterministic executor supplies those paths. At this exact state, the list
contains 2,216 actions: 1,305 facility poses, 672 component moves, 124 port edits,
62 single-chain reroutes, 34 strip insertions, 18 bridge releases and one restore.
The pose list contains **616 singleton actions and 689 two-facility actions**;
there are no actions moving three or more facilities in this particular state.

There are three distinct restrictions:

1. **Generated destinations and groups.** Group translations and compound rigid
   rotations exist, so the domain is not restricted to one-cell singleton moves.
   However, they preserve relative group geometry. The public pose DTO can encode
   up to 16 members and four translation vectors; that broader DTO is not the
   set of freely chosen actions exposed to the learner. Compound generation uses
   groups of 2..4 members, selected origins and finite scan/preflight budgets.
   Here its 512 preflights are exhausted and all 51 streams are marked capped.
2. **No combined facility/port/reroute transaction in the action list.** A pose
   action sets only facility moves and rotations. Port selection, extra-chain
   rerouting and bridge release are separate action kinds. The internal `Edit`
   DTO being able to combine fields does not make that combination selectable.
3. **Restricted automatic repair.** A pose invokes the local router inside the
   current extent, with two new bridges shared across the edit and fixed
   pipe-first/chain-id ordering. The selected first path receives no alternate
   retry after another path fails. This limitation directly caused this rejection.

Consequently, simultaneous internal repacking, port reassignment and surrounding
route repair cannot generally be requested as one learner action. Every committed
intermediate action must independently validate. This can exclude transitions
that need coordinated changes, even though some distant and group moves exist.
Whether an equivalent sequence of existing valid actions reaches a better layout
remains an empirical question.

The relevant source is `full_factory/candidates.rs::execute`,
`poses.rs::{options,actions,translations}`, `groups.rs::compound_groups`, and
`routing.rs::reembed` in `crates/aic-pilot-native/src/`.

## Decision supported by this slice

Do not attribute this rejection to the PPO policy's routing skill. Establish
executor coverage before interpreting more training as the remedy. A useful next
experiment would replay the same retained states and proposed actions under the
current and a bounded transactional repair contract, comparing validation rate,
work, immediate score and reachable subsequent contractions. Also audit whether
known improving coordinated poses are absent from the generated action list.

The twelve-bridge setting and reversed chain order are diagnostic witnesses, not
a general fix: another order or bridge allowance can consume more work and yield
worse routes. This slice changes no training behavior, reward, production routing
or action vocabulary, and does not restart training.

## Reproduction and retained evidence

`tools/factory-edit-pilot/route_failure_probe.py` creates a detached diagnostic
checkout at `410aaef`, instruments only that checkout and installs the accompanying
Rust probe. It uses runtime catalogs from the pinned checkout and three explicit
external case inputs. Its assertions check the exact baseline failure and the
fully validated 5,000-budget recovery. Instrumentation captures detailed geometry;
reported wall times include capture overhead and are not performance benchmarks.

```sh
python3 tools/factory-edit-pilot/route_failure_probe.py \
  --input artifacts/factory-edit-pilot/compact-policy-visual \
  --output artifacts/factory-edit-pilot/route-failure-probe/replay \
  --checkout target/route-failure-replay
```

Required input filenames are `request.json`, `failure-before.json` and
`failure-action.json`. The before-state is frame 10 from the retained evaluation
replay, including its accepted exploratory history. It must not be replaced by an
earlier best checkpoint. All raw evidence stays under ignored `artifacts/`.
The accompanying provenance manifest records selected input/output hashes.
Disposable intermediate runs and diagnostic checkouts are removed after recording
the results; the selected validated candidate, inputs and final replay remain.

Verification: the standalone reproduction command completed all 80 cases and its
baseline/recovery assertions in release mode. `cargo fmt --all`,
`cargo check --workspace`, and `cargo test --workspace` passed (545 tests passed,
four ignored). Artifact-policy worktree and staged-index checks passed.
