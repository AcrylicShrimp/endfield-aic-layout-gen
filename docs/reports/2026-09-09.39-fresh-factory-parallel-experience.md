# Fresh factory generation and parallel experience

Status: completed and audited. Parallel collection preserved serial semantics;
the two-seed short learning check did not demonstrate held-out improvement.

## Question and method

The user requested a new production target, rate and initial geometry draw for
every training episode, followed by a new learning check on the experimental
server. This replaces the fixed training resets in the interrupted input screen.
Fixed-environment trajectories are valid RL experience; random factories address
the requested training distribution and do not guarantee useful learning.

The [stage contract](../designs/2026-09-09.39-fresh-factory-parallel-experience.md)
separates worker concurrency from optimizer batch size. The scaling matrix uses
1/2/4/8/16/24/32 persistent CPU workers and identical logical seed schedules, two
banks of 32 requested episodes, eight selections per admitted episode. The
single-worker reference runs first; the remaining counts follow a frozen random
order. Each worker count regenerates all requests from their draws. Compare
generated inputs, selected actions, native outcomes, episode gradients and one
assembled optimizer step with the serial reference.

The server is `ashrimp-arch`: Intel Core Ultra 9 285K, 24 CPU cores, approximately
64 GB RAM and an RTX 5090 with approximately 32 GB device RAM. This collection
uses one CPU Torch thread per worker. The isolated checkout is
`/home/ashrimp/Srv/aic-random-factory-20260909`, based on `e622b8e` plus the
hash-bound experiment sources. Current Linux CLI, witness validator and native
extension were built there; historical server checkouts were preserved.

The external distribution samples four product plans uniformly: medical, food,
copper liquid and watered grass. It then samples periods uniformly on a
one-second grid: 20–100 seconds for medical/food and 2–20 seconds for the other
two, with target quantity one. Uniform periods are not uniform production rates.
This is a finite declared task distribution, not coverage of every game recipe.

Every draw invokes contextual wiring and ordinary production construction,
followed by independent original-graph/geometry validation. Two through six
uniform-kind native setup edits vary the current layout, using the bounded
basic/local pose proposal option. Setup retains the last valid current layout,
including non-improving edits, and resets the episode incumbent to that layout.
It does not choose the best setup result. Fresh independent draws may repeat;
report request and rate-independent geometry identity separately.

The action-only policy receives candidate descriptors, compound-member geometry
and basic episode context. It retains the ordinary action vocabulary, including
restore-best, history masking and action-kind balancing. Workers hold weights
fixed for each optimizer batch. Results and gradients are assembled by logical
episode order, regardless of completion order.

Learning uses two initial parameter seeds, 32 updates, 32 newly generated request
attempts per update and 32 selections per admitted episode. Rank the exact
rational tuple `(best - start) / max(1, start)` lexicographically, area before
transport tiles before turns. This avoids comparing differently sized factories
by raw terminal area. Task difficulty remains unequal. The new data distribution,
batch size and return normalization changed together; this is not a causal test
of randomization alone. Initial, update-16 and update-32 policies are evaluated
on 16 separate matched generation draws per seed, with fresh generation each
time. Those draws never enter training.

## Execution checks

Arbitrary millisecond periods first produced contextual rate-rounding diagnostics.
All 81 configured complex-product grid periods passed a separate throughput
admission probe for both source plans. This defines the sampling grid; it does
not repair the numeric limitation or establish constructor completeness.

The reduced server check used 1/2/4 workers, eight attempts, two selections and
two setup edits. All worker counts produced identical factories, decisions,
native outcomes, gradients and assembled updates. Throughput was approximately
0.385/0.644/0.996 valid selections per second, including generation and validation.
Two small learning updates and matched evaluations completed. The audit reopened
all 40 recorded initial/best witnesses, reconstructed all updates and re-executed
18 selected actions. These counts are execution checks, not full learning evidence.

Five fresh-experience tests and ten input-contract tests passed. The new tests
cover deterministic varied draws, geometry identity excluding rates, exact
own-reset fractional ordering, accumulated gradient equivalence to a direct
float64 objective, and rejection before an optimizer update. Deadline and
worker-startup fault probes verified cleanup of owned process groups.

## Parallel scaling

All seven worker settings completed both registered banks with identical
factory, action, native-state, gradient and assembled-update signatures. Each
setting attempted 64 requests, admitted 62 complete factories and selected 496
policy actions. The two rejected food requests exhausted the constructive route
candidate budget at periods 21 and 26 seconds, with 20 of 26 facilities covered.
They remained rejected attempts at every worker count; no replacement factory
entered their place. The entire matrix took 888.427 seconds.

Rates divide all valid selections by the combined collection wall time, including
generation failures. Startup is measured separately. RSS is a sampled sum across
owned processes and the coordinator; shared mappings can be counted multiple
times. The registered selection rule chose 24 workers, 1.94 times the throughput
of four and 6.49 times serial. The 16/24/32 results are close; two banks do not
establish a universal best worker count. The 32-worker result used almost all
of the configured 40 GiB summed-RSS allowance.

The logical 64 draws contained 18 medical, 18 food, 17 copper-liquid and 11
watered-grass requests. The 62 admitted factories contained 56 distinct request
DTOs and 58 distinct rate-independent geometries. Of those starts, 56 differed
geometrically from their deterministic constructor result. Facility counts were
2/3/16/18/23/26. This verifies fresh sampling and actual geometry variation;
it does not make every draw unique or every episode difficult.

In the serial reference, summed generation/setup/validation time was 325.697
seconds and policy rollout time was 25.280 seconds, approximately 93% and 7%
of those stages respectively. This eight-selection measurement is dominated by
CPU factory preparation. It does not measure GPU inference speed or the stage
balance of the longer learning episodes.

## Learning results

Both seeds completed 32 updates in 1,905.745 seconds combined. Seed 17 admitted
1,002 of 1,024 attempts and selected 32,064 actions; seed 29 admitted 1,011 and
selected 32,352. All 64 batches had non-flat relative returns. Generation
rejections remained in the attempt denominator and were not replaced.

| Seed | Initial area reduction, % | Update 16, % | Update 32, % | Final change, pp | Final score W/T/L |
| ---: | ---: | ---: | ---: | ---: | --- |
| 17 | 14.793884 | 14.580932 | 14.721399 | -0.072485 | 2/12/2 |
| 29 | 14.392391 | 13.842247 | 13.240157 | -1.152234 | 2/10/4 |

Each percentage is the mean reduction from each evaluation factory's own reset.
Changes compare the checkpoint with the untrained policy on 16 matched factories
per seed. All 96 evaluation episodes completed, selecting 3,072 actions. Neither
seed's final mean improved. Positive rank rewards and diverse experience do not
establish learning, and these results do not identify the cause of regression.

Training covered all four products and 2/3/16/18/23/26 facilities. Seed 17 had
868 distinct geometries and 189 request DTOs; seed 29 had 892 and 191. All eight
action kinds occurred. The audit checked 2,592 result records, including 49
rejections, native-validated all 2,543 admitted starts and bests, reconstructed
64 learning and 14 scaling optimizer transitions, and re-executed 496 selected
actions. It completed in 62.188 seconds. Full analysis and static PNG/SVG plots
were produced from the audited records.

## Reproduction and retention

Run from the isolated server checkout with its existing Python environment.
All output directories must be fresh. The commands below describe the registered
bounded pilot, not the cancelled twelve-hour experiment. Preparation with
`--smoke` deliberately changes sample counts and is only an execution check.

```sh
PYO3_PYTHON=/home/ashrimp/Srv/endfield-aic-layout-gen/tools/factory-edit-pilot/.venv/bin/python \
  cargo build --release -p aic-cli -p aic-pilot-native \
  --features aic-pilot-native/extension-module
/home/ashrimp/Srv/endfield-aic-layout-gen/tools/factory-edit-pilot/.venv/bin/python \
  tools/factory-edit-pilot/random_factory_pilot.py prepare \
  --config tools/factory-edit-pilot/random-factory-server-pilot.json \

  tools/factory-edit-pilot/random_factory_pilot.py scaling \
```

Keep actual generated requests, wiring obligations, randomized starts, setup and
policy traces, gradient payloads, all optimizer/RNG checkpoints and source/native
identities in ignored artifacts. A seed alone is insufficient retained evidence.
The full audit checks every recorded start and best with native validation and
reconstructs every optimizer transition. It re-executes declared trajectory
samples with the same runtime and rollout implementation; it is not a second
independent implementation of the learning or physics engine.
