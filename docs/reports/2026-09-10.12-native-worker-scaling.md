# Native collector worker scaling

## Decision

Use **8 persistent workers** for subsequent native PPO runs. The user selected
this count after reviewing the complete sweep, including 1–8 workers.
Eight workers collect the fixed batch in 4.163 s, versus 4.105 s with 12 and
4.078 s with 24. The 1.4% difference from 12 workers costs 4.80 GiB of additional
aggregate RSS at 12 workers. Four workers need 6.405 s, a clear throughput loss.

The ordinary input-screen, representative harness and area-study configuration
files now specify eight workers. The small two-worker readiness check retains
its diagnostic setting. Previously frozen run protocols remain historical inputs.

## Controlled comparison

- Host: Intel Core Ultra 9 285K, 24 logical CPUs, Linux; release Rust 1.98.1 native
  library, Python 3.12.13, Torch 2.14.0. Worker inference runs on CPU with one Torch
  intra-op and inter-op thread; the configured CUDA learner performs no updates.
- Frozen workload: `current-history-16`, initialization seed 17, training batch 4,
  its existing actor/critic checkpoint, 32 fresh factories and 32 actions each.
- Worker order: 16, 12, 8, 24, 32, 1, 4, 2 (`Random(20260910)` shuffle).
- Each count opens one pool, executes one cold batch, then three fresh collections
  with the same workers and weights. The table reports the median and range of
  those three retained-pool collections. Startup is measured separately.
- Existing task, batch and RSS limits remain active, with a 600-second profiling
  guard per worker count. The complete eight-count driver took 277.8 seconds.
- All 32,768 actions across 1,024 factory episodes match the frozen generation,
  geometry, observation hashes, allowed actions, probability hashes, chosen actions
  and physical trajectories. Per-repetition semantic hashes are retained.

and all four batches; shared mappings may be counted more than once. Sampling at
progress callbacks, at most every 250 ms, is not an exact peak-memory measurement.

The cold 8-, 12-, 16-, 24- and 32-worker batches all finish with factory index 4,
a medical factory whose individual task takes approximately 4.1–4.3 seconds.
This supports a straggler explanation for the plateau: extra workers cannot
shorten the longest individual episode. This is evidence for this factory mix,
checkpoint and horizon; richer inputs, longer episodes or different batches can
have a different crossover. The sweep does not establish universal optimality or
measure learner-update time. Startup was observed only once per count.

## Implementation, reproduction and retained evidence

`profile_native_factory_collection_batch.py` adds explicit `--workers` (1–32)
and `--repeats` (1–8) flags. The default retains the reference worker count and one
collection. Repetitions use the same pool with fresh output directories and verify
parity before removing duplicate regenerable outputs. The first repetition keeps
its experiences, input witnesses and results. No collector algorithm changes.

From the retained native server checkout:

```sh
PY=/home/ashrimp/Srv/endfield-aic-layout-gen/tools/factory-edit-pilot/.venv/bin/python
SCREEN=/home/ashrimp/Srv/aic-ppo-area-20260909/artifacts/factory-edit-pilot/ppo-input-contract-screen
OUT=artifacts/factory-edit-pilot/native-worker-scaling-reproduction
for workers in 16 12 8 24 32 1 4 2; do
  "$PY" tools/factory-edit-pilot/profile_native_factory_collection_batch.py \
    --screen "$SCREEN" --output "$OUT/workers-$workers" \
    --workers "$workers" --repeats 4
done
```
