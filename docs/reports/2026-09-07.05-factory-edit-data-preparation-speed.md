# Profile-Guided Factory Edit Data Preparation

Status: completed, 2026-09-07.

The user prioritized reusable training-time data generation and validation, then asked to
rank optimizations by their share of total elapsed time. This slice targets repeated PPO batch
preparation first, followed by pure environment representation reuse. It preserves the fixed
factory, model, action set, observation values, acceptance, PPO allowance, and default permitted
numerical variation. See the [contract](../designs/2026-09-07.06-factory-edit-feature-reuse.md).

## Cost decomposition and priorities

The preceding full CUDA run took 118.670 s. CPU inference consumed 29.176 s, observation
construction 28.467 s, PPO updates 23.038 s, candidate construction 20.564 s, and environment
steps 11.600 s. Validation is nested within steps and must not be added again.

Within PPO updates, batch construction/transfers consumed 11.236 s, forward/loss 3.769 s,
backward 5.681 s, and optimizer work 2.033 s. Rebuilding/transferring the same collected data
across four epochs was therefore a larger target than optimizer kernels. `costs.py` now
produces a structured decomposition from complete metadata and update rows, reporting missing
or inconsistent clocks and separating evaluation time.

## Selected changes at `403642b`

CUDA updates prepare rollout tensors once per collected batch. Each unchanged minibatch crops
the device tensors to exactly its previous maximum height, width, and candidate count, then
selects the same examples in the same order. It does not train on a globally enlarged padded
canvas. Advantages, sample permutations, loss formulas, and all 16 Adam steps per rollout
remain unchanged. All preparation and selection are charged to the existing batch clock.

Prepared payload is capped at 1 GiB; estimates above the cap use ordinary minibatch construction
and record that mode. The cap is an implementation memory bound, not a geometry or training
allowance restriction. CPU updates retain ordinary batching. In this full run all 256 rollouts
used device preparation, with maximum estimated payload 296.220 MiB.

Two independent 4,096-entry LRU caches retain pure candidate features and canonical typed-command
JSON sort strings. Keys include every relevant command field and resolved absolute coordinate;
mutable geometry, validation results, rewards, or selected actions are never cached. Eviction
recomputes exactly the same value. Returned observation arrays own their copies. CPU action
inference uses read-only tensor views instead of building a padded one-element batch.

## Fixed-input measurements

Each update sample resets the same model, Adam state, retained observations/actions, and
minibatch RNG. Three measured rounds alternate implementations after a warm-up. The reference
is `5562ae4`; both execute standard PyTorch layers and autograd on the same RTX 5090 server.

| Fixed input | Previous update, s | Reused preparation, s | Reduction |
| --- | ---: | ---: | ---: |
| Initial-policy rollout | 0.064382 | 0.048812 | 24.2% |
| Elongated-state rollout | 0.180860 | 0.080343 | 55.6% |

A separate deterministic diagnostic on elongated inputs produced the **same final parameter
hash** across both implementations and both repetitions: four identical results after all
16 Adam steps. This checks the representation change independently of permitted production
CUDA variation. Deterministic execution remains a diagnostic option, not a training default.

Environment replay compares every candidate in order, every observation byte/dtype/shape,
step reward/outcome, and final state against the historical environment and retained inputs.
All 768 states passed. The default cache-lifetime server comparison reduced total environment
work by 10.4% on initial inputs, 20.2% on later-policy inputs, and 6.1% on elongated inputs.
Interleaved CPU inference on identical elongated states fell from 0.153499 to 0.145404 s per
256 calls, a smaller 5.3% benefit. A local inference comparison was only about 1.2% faster;
the server measurements, not local extrapolation, determine the execution choice.

## Does reuse depend on fixed-instance overfitting?

The largest improvement, PPO preparation reuse, applies whenever one collected rollout is
trained for multiple epochs. The next rollout is newly prepared. It does not require the next
episode or problem to be the same. Single-observation copy removal has the same independence.
The current pilot still requires its existing uniform observation dimensions within a batch;
this optimization neither adds nor removes that model constraint.

Environment cache benefit depends on repeated expressions. To remove cross-episode reuse from
the measurement, an explicit diagnostic clears both LRU caches and category templates after
every episode. Clearing cost is included; observation/transition parity still passes.

| Episode-cold server input | Previous environment, s | Reused expressions, s | Reduction | Encoding hit rate |
| --- | ---: | ---: | ---: | ---: |
| Initial-policy sequence | 0.250320 | 0.220776 | 11.8% | 95.7% |
| Later-policy sequence | 0.291204 | 0.263480 | 9.5% | 96.6% |
| Elongated sequence | 0.493024 | 0.380359 | 22.9% | 96.6% |

This demonstrates reuse within a sequence of local edits without retaining prior-episode
entries. It is still a replay of the same four-facility problem, not a benchmark of arbitrary
new factories or near-zero-hit workloads. Invocation-to-invocation timing differs, so the two
cache-scope matrices are not a precise causal comparison of cache lifetime. A first exploratory
encoding-only variant slightly regressed one local input; it was not selected alone.

## Complete-run observation and memory tradeoff

The rerun `server-cuda-t16-seed17-prepared-data` uses committed source `403642b`, the same host,
16 CPU threads, learner/actor allocation, seed 17, 100,898 parameters, 65,536 training commands,
4,096 Adam steps, and five 32-rollout evaluations. No benchmark or other training overlapped.

| Recorded wall-time component, s | Previous full run | Prepared-data run |
| --- | ---: | ---: |
| Training total | 118.670 | 85.521 |
| CPU actor inference | 29.176 | 22.376 |
| Observation construction | 28.467 | 21.976 |
| Candidate construction | 20.564 | 11.844 |
| PPO update total | 23.038 | 12.185 |
| PPO batch preparation within update | 11.236 | 2.524 |
| Environment step including validation | 11.600 | 11.094 |
| Complete validation within step | 5.028 | 5.065 |
| Evaluation, separately measured | 29.008 | 23.736 |

Observed training time fell 27.9%. The trajectory generated 7,705,035 candidate commands,
versus 11,109,040 previously, so this is **not** an equal-trajectory causal speedup. Both runs
had zero positive training episodes and zero final evaluation improvements. The new valid
retained champion remains [154, 25, 0]; faster execution does not establish learned quality.
Fixed-input timings and the exact deterministic update comparison are the stronger evidence
for the implementation improvement.

Peak allocated GPU memory rose from 282.730 to 735.859 MiB; peak process RSS rose from
2,742.969 to 2,917.355 MiB. These are whole-run observed peaks, not isolated cache allocation
measurements. The full run exercised both environment caches at their 4,096-entry bounds;
encoding and sort hit rates were about 99.45% and 99.47% respectively. Their hits do not bypass
any mechanical filtering or complete-factory validation.

## Verification, reproduction, and remaining work

All 20 server Python checks passed, including CUDA output/gradient checks, exact CPU resume,
cached-versus-original minibatch tensors/shapes/dtypes, payload accounting and memory-bound
fallback, both cache evictions, and observation ownership. Local checks passed with two CUDA
checks skipped. Cargo workspace check/test passed. Independent full-run acceptance/replay
passed for five layouts and six traces, with source hashes checked against `403642b`.

Run `benchmark.py --reference-update 5562ae4` for update comparison and
`rollout_benchmark.py --reference-policy 5562ae4` for CPU inference comparison, using retained
inputs and the same runtime settings. `environment_benchmark.py --reference-source 5562ae4`
compares pure environment work; add `--reset-caches-per-episode` to isolate within-episode reuse.
`costs.py --runs <before-run> <after-run> --output <fresh-directory>` retains non-overlapping
cost components. The [tool README](../../tools/factory-edit-pilot/README.md) documents full training.
Microbenchmarks used working sources whose runtime implementations match `403642b`; a later
cache-eviction test changed the test-file hash. Episode-cold replay is a later diagnostic only.

The next largest observed components are CPU inference (22.376 s) and observation construction
(21.976 s). Actual complete validation is 5.065 s here. Bigger and more varied factories need
separate scaling measurements before these shares can justify a broad environment rewrite.
The current CPU actor will also need attention as model size grows; a GPU learner alone does
not accelerate its action-selection forward pass. This slice does not claim optimization is
exhausted or that the four-facility pilot is a finished general factory training environment.
