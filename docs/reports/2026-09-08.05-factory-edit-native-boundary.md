# Environment Profile and Prospective Rust Boundary

Status: profiled, 2026-09-08. No native extension or dependency has been added.

The user prioritizes future GPU model growth over additional CPU neural inference tuning and
proposes Rust for Python overhead. Full 262,144-command runs spend 42.8–45.9% of training time
in candidate generation, observation construction, and environment stepping/validation. These
are Python implementations, but their entire time is not necessarily interpreter overhead.

`profile_environment.py` replays three retained 256-command inputs five times each, excluding
neural inference. It verifies every observation array against retained values after profiling.
All 3,840 replayed observations match exactly. Profiler timings below include instrumentation
overhead; use them to select a boundary, not as uninstrumented throughput measurements.

| Input | Profiled total s | Candidates cumulative s | Observe cumulative s | Index cumulative s | Acceptance cumulative s |
| --- | ---: | ---: | ---: | ---: | ---: |
| Initial | 1.106 | 0.409 | 0.331 | 0.138 | 0.122 |
| Later | 1.247 | 0.419 | 0.364 | 0.170 | 0.176 |
| Elongated | 1.904 | 0.560 | 0.480 | 0.358 | 0.398 |

Columns overlap because indexing is nested in other operations. Large self-time functions are
Python candidate enumeration, raster/object construction, adjacency/occupancy indexing, and
acceptance. State cloning, layout serialization, sorting, list operations and conversion to
NumPy also contribute. This is not a profile dominated by one expensive NumPy kernel.

## Proposed boundary, not an implemented API

Keep Python/PyTorch for policy execution and PPO. A Rust extension could own the mutable
draft, valid base, best layout, runtime catalog-derived tables, candidates and geometry indexes.
One observation call would construct NumPy-compatible arrays; one step call would receive an
action index and return reward, termination and structured diagnostics. Exact state/trace export
would remain available for checkpoints, interruption and independent audit. Avoid serializing
the entire factory into Python dictionaries on each action or exposing every grid lookup as a
separate Python-to-Rust call.

PyO3 supports native Python modules in the same process ([official guide](https://pyo3.rs/main/)).
rust-numpy supports array borrowing and transferring Rust-owned storage into NumPy buffers
([array documentation](https://pyo3.github.io/rust-numpy/numpy/array/struct.PyArray.html)).
These mechanisms can avoid selected CPU-side copies with correct ownership; they do not remove
CPU-to-CUDA transfers. Actual conversion cost and throughput remain unmeasured here.

The existing constructive validator accepts `ConstructiveNode` and several validated catalogs,
and is internal to the production constructive module. It supports a broader transport/component
contract than the pilot's directed-path edit environment. It is not a drop-in implementation of
the pilot DTO or its diagnostics. Reuse needs a semantic mapping, not only a Python binding.

Before implementation, specify native input/output DTOs, exact candidate ordering, coordinate
arithmetic, array shapes/dtypes/ownership, invalid-edit behavior, scoring/reward, and checkpoint
state. Keep the current Python environment/acceptance as an independent comparison oracle.
Replay initial, later, elongated and adversarial states; compare commands, arrays and transitions
before measuring release-mode end-to-end collection. No speedup or completed Rust migration is
claimed by this report. GPU batched collection remains the separate measured execution opportunity.

## Reproduction

`profile_environment.py --case <case> --config <config> --input <initial-input.pt>
<late-input.pt> <interrupted-input.pt> --output <fresh-directory> --repeats 5` records every
function's call count, self/cumulative time, input hashes and source/runtime provenance.
The source tool is retained; raw profiling output stays ignored under
`artifacts/factory-edit-pilot/environment-profile/result.json` on local and server storage.
