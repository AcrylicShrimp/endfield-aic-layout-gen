# Plan .01 terminal replay validation profile

## Question and method

Locate the cost of the admitted native replay observed in the one-shot caller calibration. The same ignored release fixture constructs a physically valid 256-facility, 254-connection belt/pipe layout through ordinary native commands and applies one six-command bridge route. The local stage timer was temporary test-only instrumentation; it was removed after measurement. A bounded 500-replay CPU sampling run used a dedicated server checkout under `~/Srv/plan01-native-replay-20260927`, with no training process. The server had 152 GiB available disk and an idle RTX 5090 before this CPU diagnostic. `AIC_CALIBRATION_PROFILE_REPLAY=500` repeated the identical admitted replay after fixture construction.

## Result and decision

The server release fixture reported 11 ms for the full one-shot caller. A separate server run reported 3 ms for ordinary `clone` plus `Session::step` and 14 ms for admitted replay **including two post-replay assertions**; the latter is not a pure `advance` time. Five hundred admitted replay iterations took 4348 ms during sampling, within a 4.426-second whole-test capture; that loop includes per-iteration progress/allowance creation and result release. The SQLite export retains the caller and 500-repeat output, while the separate 3/14-ms output is represented by its source and the observed command result, not by a retained raw log. Of 2920 whole-capture leaf samples, 194 named `NativeReplayProgress::advance`, 185 `replay_owned_source`, 140 `Permit::visit`, 128 `validate_core`, 92 `ValidationCursor::advance`, and 45 `RequestAllowance::charge`; additional samples were in time checks and unresolved libc/vDSO addresses. These counts support a validator/admission hot path, not a precise percentage breakdown of the 500 replay loop.

The retained local release run gave fork 0.939 ms, commands 0.051 ms, completed-layout materialization 0.898 ms, and independent validation 8.008 ms on its first replay; its next unpaged replay gave 0.774, 0.030, 0.749 and 7.266 ms. Direct `validate_with_visit` on the *same completed child layout*, charging `ValidationRecords` once for each of 49,798 visits and checking the returned `Metrics`, took 3.706 ms after the second replay. Admitted replay charged 58,895 validation records in total because that category also covers materialization. The corrected local fixture reported 2 ms ordinary replay and 8 ms admitted replay before any additional direct validation. The direct and admitted timings are adjacent, not randomized or statistically bounded; they locate material extra cost in the retained validator plus admission path as a whole. They do not isolate the admission bridge's share from other cursor effects. This is a performance finding, not a correctness failure or a license to precharge visits, skip independent validation, or remove memory reservations.

Plan .01 remains **BLOCKED** pending a representative placed-input old/current caller comparison and a justified treatment of this cost. A possible implementation direction is to let the retained validator cursor communicate directly with the replay owner's allowance while retaining exact per-visit charging, memory reservation, page stops, typed hard stops and source ownership. That direction requires a reviewed design and measured improvement before adoption. The first-turn atomic-tail question also remains open; the synthetic 50-ms page is not evidence for the actual first-turn credit.

## Review and cleanup manifest

Independent report review took three rounds. The first found missing temporary-timer provenance and an ambiguous replay time; the second found that the earlier server timer includes two post-replay assertions. Both source-boundary issues were corrected. Round 3 `/root/review_plan01_profile_closeout_r3` returned **PASS_WITH_NOTES** for report accuracy and cleanup only, after checking the saved hashes, timer positions, stage output, SQLite samples and isolated server directory. The separate server 3/14-ms stdout was not retained, so that observation remains contextual. This review does not approve Plan .01 implementation.

Before cleanup, the dedicated server checkout occupied 367,000 KiB and the server filesystem reported 158,756,120 KiB available. After confirming no diagnostic process was active, removed only `~/Srv/plan01-native-replay-20260927`, including its copied source, build and raw Nsight/SQLite profiles. Available space rose to 159,123,120 KiB, an exact 367,000-KiB difference in filesystem accounting. Locally, removed the 508-KiB raw SQLite export, a 280-KiB duplicate source copy used to form the stage patch, and two 8-KiB regenerable Cargo warning logs from ignored `artifacts/plan01-caller-2026-09-27/`. Local available space rose from 31,041,880 to 31,042,648 KiB; the 768-KiB accounting difference is not a per-file byte measurement. Retained the source snapshots, stage patch and compact stage output while the code is uncommitted. No training input, checkpoint, replay buffer or unrelated server state was removed.
