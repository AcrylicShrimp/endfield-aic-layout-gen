# Factory Edit Observation Construction Speed

Status: completed, 2026-09-07.

The user requested further optimization before scaling experiments. This slice preserves the
same candidate domain, canonical candidate order, observation bytes, transition semantics,
acceptance, model, PPO settings, and training exposure. It changes Python representation work.
See the [contract](../designs/2026-09-07.05-factory-edit-observation-cost.md).

## Implementation

Source `15dfe26` derives immutable categorical feature indexes from runtime catalogs, caches
one-hot prefixes keyed only by finite action/catalog categories, and copies them into owned
NumPy candidate arrays. Coordinates and mutable state never enter the template cache. Numeric
feature division and float32 conversion retain their original ordering. Reusing the standard
JSON encoder avoids per-command encoder construction while keeping its exact sort key.

This removes dense Python float-list creation and conversion for every candidate. It adds no
language dependency, alternate environment semantics, state cache, observation approximation,
reward shaping, or command pruning. PyTorch remains responsible for forward/backward execution.

## Fixed-input environment comparison

`environment_benchmark.py` imports the trusted `274d588` environment only as a diagnostic
reference. Three retained inputs each contain 256 recorded commands. On every replay it checks
ordered candidate dictionaries, all five observation arrays including dtype/shape/bytes, step
rewards/outcomes, and final draft/base/best serialization against the reference. It also checks
observations against the original retained tensors. All 768 states passed exact parity on
both Mac and server, across warm-up and three alternating measured rounds.

| Server input | Reference environment, s | Optimized environment, s | Reduction |
| --- | ---: | ---: | ---: |
| Initial policy sequence | 0.337 | 0.252 | 25.1% |
| Later policy sequence | 0.433 | 0.287 | 33.7% |
| Elongated interrupted sequence | 0.647 | 0.466 | 27.9% |

These median clocks include candidate/observation/step work and evidence retention in memory,
exclude neural inference and PPO updates, and perform parity comparisons after timing. The
local templates version reduced the corresponding totals by 30.4%, 24.2%, and 34.1%.

## Complete CUDA rerun

The same server, Python/PyTorch installation, 16 threads, seed 17, initial weights, 65,536
commands, 4,096 Adam updates, and 160 evaluation episodes are used. The previous full CUDA run
is `server-cuda-t16-seed17`; this run is `server-cuda-t16-seed17-observation-speed`.

| Recorded measurement | Before | After |
| --- | ---: | ---: |
| Training wall time, s | 140.263 | 118.670 |
| Evaluation wall time, s | 34.720 | 29.008 |
| Candidate generation, s | 23.719 | 20.564 |
| Observation construction, s | 48.683 | 28.467 |
| PPO update, s | 20.065 | 23.038 |
| CPU actor inference, s | 27.260 | 29.176 |
| Environment step including validation, s | 12.756 | 11.600 |
| Enumerated candidate commands | 10,514,010 | 11,109,040 |
| Positive training episodes | 1 / 512 | 0 / 512 |
| Final frozen evaluation improvements | 0 / 32 | 0 / 32 |

Recorded training wall time fell 15.4%, but this is not a perfectly controlled whole-run
speedup: training trajectories differ, with aggregate episode rows first differing at episode
17. Initial policy tensors and initial CPU RNG states are identical; later checkpoints differ.
The new run's training champion remains the valid initial factory, while the earlier run found
one improving factory. Neither final policy demonstrates the learned improvement. Therefore
the fixed-input benchmark, rather than equal seed alone, is the primary causal timing evidence.
The elapsed-time reduction does not establish an improvement in time to learned quality.

A short read-only checkpoint comparison ran during the full rerun; no other training or
benchmark jobs overlapped. Full-run clocks are observations from one execution, not confidence
intervals. All generated results remain outside tracked source directories.

## Repeatability diagnostic

Repeatedly reset the same model, Adam state, 256 input observations/actions/returns, and
minibatch RNG, then execute the same four-epoch update on CUDA. Four executions (including
warm-up) produced four different parameter hashes, with maximum parameter difference from
the first of 0.0000336834. Environment construction is absent from this experiment. This
confirms numerical update non-repeatability independently of the observation optimization.
It does not establish that this alone causes the sparse-reward policy's failure to learn.

The training runs disable cuDNN benchmarking and TF32, but do not request deterministic
algorithms. Disabling benchmarking alone does not guarantee deterministic CUDA convolutions;
see [PyTorch reproducibility](https://docs.pytorch.org/docs/2.14/notes/randomness.html).
`benchmark.py` now records parameter hashes/differences outside timing, and an explicit
`--deterministic` diagnostic selects deterministic algorithms with cuBLAS workspace settings.
This diagnostic does not change production training defaults.

With deterministic algorithms enabled, all four update parameter hashes matched exactly.
Median update time was 0.075931 s versus 0.064021 s in the default diagnostic, an 18.6%
increase for this small fixed batch. The local one-thread CPU control also matched exactly.
These tests establish a reproducibility option and its measured local cost; they do not show
that enabling it improves learning quality or makes CPU and GPU updates bit-identical.

The user explicitly accepted small numerical variation to preserve throughput. Deterministic
execution remains a diagnostic option; it is not made the default for training. No configuration
schema migration or deterministic training rerun was implemented.

The earlier CUDA run's single positive episode is a discovered retained factory, not evidence
that its policy reliably learned the edit. Its 1/512 positive training episodes and 0/32 final
evaluation improvements do not describe a well-trained policy failing under deployment shift:
evaluation uses the same fixed factory. The optimized rerun found no positive training episode.
Numerical variation can change an on-policy exploration path, but explaining why rare success
does not become reliable behavior requires separate learning-stability investigation. That
cause is not established by the update repeatability diagnostic or the current parity checks.
