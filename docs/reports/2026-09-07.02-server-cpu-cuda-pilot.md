# Same-Server CPU and CUDA Factory Edit Pilot

Status: completed, 2026-09-07.

The user authorized experiments on the Arch Linux server after the Mac CPU pilot and
asked specifically about Python work during training. This experiment keeps the fixed
factory, 100,898-parameter CNN+MLP, seed 17, 65,536 training commands, 4,096 Adam updates,
and five 32-rollout evaluations. See the [execution contract](../designs/2026-09-07.03-factory-edit-cuda-comparison.md).

## Elongated-input thread cliff

The first 24-thread CPU attempt was explicitly interrupted at 38,656 commands after a large
slowdown. Its 32,768-command checkpoint, partial rollout, optimizer, and interruption state
remain retained. This attempt is not a completed CPU/GPU comparison. At 32,768 commands,
recorded training time was 394.419 s: about 49.659 s in candidate/observation/environment work
and 163.846 s in measured update components. The old interruption metadata did not retain
all clocks; the runner now preserves them and a nonempty interruption message.

A diagnostic replay of the actual retained 256-command sequence reproduced every observation
tensor exactly, while interleaving inference and Python environment work. The unfinished drafts
had observation rasters up to 242 rows by 12 columns and up to 496 candidate commands; those
are observed private-state sizes, not validated factory footprints or layout ceilings.

| CPU threads | Interleaved 256-command replay, s | Model inference within replay, s |
| ---: | ---: | ---: |
| 1 | 0.893 | 0.299 |
| 4 | 0.851 | 0.235 |
| 8 | 0.853 | 0.233 |
| 16 | 0.857 | 0.232 |
| 24 | 5.167 | 4.492 |

These medians use two measured rounds after one warm-up. The 24-thread inference time is
about 19.4x the 16-thread time on identical inputs. A separate update benchmark on the same
retained observations, with inference fixed at 16 threads, gave 0.822 s for 16-thread updates
and 2.210 s for 24-thread updates. Both full-run configurations therefore use 16 threads.
This establishes a workload-dependent thread cliff; it does not identify the precise internal
kernel/scheduler mechanism. No custom convolution, backward kernel, or language migration was
needed. The interrupted model snapshot is used only for timing, not as a completed learned
result or an initialization for the fresh full runs.

Update stages synchronize CUDA before stopping wall clocks. `batch` includes CPU preparation
and device transfers; forward/loss, backward, and optimizer clocks include host work and
completed device work. These are not pure GPU kernel times. Synchronization adds diagnostic
overhead, and the end-to-end update clock includes it. This follows the distinction between
asynchronous dispatch and completed work in [PyTorch's CUDA semantics](https://docs.pytorch.org/docs/main/notes/cuda.html).

## Interpreting Python cost

Complete-factory validation is one measured part of training-time checking. Mechanical
collision, binding, and connectivity filtering inside candidate construction is charged to
candidate generation, so the validation timer alone is not the cost of all checking.
Validation is also nested within environment-step time and must not be added twice.

This is an on-policy experiment: the learner's edits create the states used for subsequent
training. Input observations cannot all be generated in advance as an offline dataset.
Static catalog preprocessing and training-time candidate/observation/validation work are
different optimization targets. This comparison changes the learner device, not the language
or semantics of the environment. A future Rust or Mojo experiment should isolate a measured
hot function and compare identical states/outputs before replacing any behavior.

CPU evaluation improvement counts at 0, 8,192, 16,384, 32,768, and 65,536 commands are
0, 0, 1, 27, and 32 of 32. CUDA counts are zero at every checkpoint. CUDA found the same
three-command battery-export trim once during training but did not retain it as reliably
sampled final-policy behavior. The saved best factory and the final policy are different
outputs: both champions improve the initial [154, 25, 0] score by one boundary belt cell;
neither establishes learned facility packing. The known scripted 9.09% witness remains unmet.

CUDA reduces training wall time by 9.0% at the same command allowance, while update time is
2.43x lower. This is **not a speedup to equal learned quality**. The trajectories generate
7,825,864 CPU versus 10,514,010 CUDA candidate commands, so the full runs do not hold runtime
inputs fixed. On the identical retained elongated inputs, CUDA's 0.182 s update is 4.52x faster
than CPU's 0.822 s. These measurements isolate update throughput more directly.

Initial policy tensors, CPU RNG state, and the initial evaluation trace were exactly equal.
CPU/CUDA output and gradient parity tests passed their documented float32 tolerances. Training
aggregate episode counts first diverge at episode 20, before either first positive episode.
Numerical differences can alter sampled actions and subsequent on-policy data; this is a
plausible explanation, not a proven exclusive cause. One training seed per device cannot
establish a systematic learning-quality difference. Independent training seeds and time to
specified quality remain unmeasured. The 32 evaluation seeds vary action sampling, not training.

CUDA candidate/observation construction takes 72.402 s, about 51.6% of training; full validation
alone takes 5.929 s, about 4.2%. The measured Python representation work is now a stronger
end-to-end optimization target than adding GPU capacity. No language rewrite is selected here.

`compare.py` checks matched source/runtime/configuration fields and renders frozen outcomes,
raw/smoothed rewards, and non-overlapping wall-time components. Run it with `--runs` naming the
two retained run directories and `--output artifacts/factory-edit-pilot/server-comparison`.
The generated figure is an external artifact, not a tracked source asset.
