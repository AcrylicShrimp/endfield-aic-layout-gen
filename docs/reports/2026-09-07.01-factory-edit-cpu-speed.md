# CPU Execution Timing for the Factory Edit Pilot

Status: completed, 2026-09-07.

The user prioritized elapsed time and authorized higher CPU use after the
[first pilot](2026-09-07.00-first-cpu-factory-edit-pilot.md). The selected change is four
PyTorch intra-operation threads instead of one. Standard Conv2d, PyTorch autograd, the
100,898-parameter architecture, fixed environment, seed 17, all 65,536 commands, 4,096 Adam
updates, and five 32-rollout evaluations remain unchanged. Inter-operation threads stay one.
This is a local execution setting, not a general recommendation for every CPU or model.

## Full run result

Training time decreased **343.834 -> 247.081 seconds**, a **28.1% reduction** (1.39x throughput).
Including the five evaluations, recorded time decreased 376.348 -> 277.737 seconds, or 26.2%.
The 512 training episode returns/scores and all 160 evaluation returns/scores are identical.
Every final policy tensor is bit-for-bit identical, with maximum parameter difference zero.
Both runs use 4,096 optimizer steps and finish at score `[147, 24, 0]`: all 32 final evaluation
rollouts improve area by 4.545%. The selected training/evaluation layouts and best-training
trace are identical. More threads did not change the learned behavior in this comparison.

| Recorded component | Original, s | Four threads, s |
| --- | ---: | ---: |
| PPO update, including preparation | 236.218 | 155.958 |
| Training action inference | 21.755 | 17.201 |
| Candidate generation | 19.095 | 18.729 |
| Observation encoding | 38.232 | 37.769 |
| Environment step, including validation | 10.604 | 10.679 |
| Other recorded training time | 17.931 | 6.745 |
| Total training | 343.834 | 247.081 |
| Separate evaluation | 32.514 | 30.656 |

The new PPO total contains 3.759 s batch preparation, 44.847 s forward/loss, 104.477 s backward,
and 2.766 s gradient clipping/Adam, plus about 0.109 s unclassified bookkeeping. Peak process
RSS decreased from about 874 MiB to 832 MiB. Validation is nested inside environment step;
it must not be added again. Training timers include checkpoint/plot/startup overhead and exclude
timed evaluation. They are not pure model-training benchmarks or complete process lifetimes.

This is one historical full baseline versus one new full run, supported by the fresh fixed-input
thread matrix below. The unclassified overhead also changed, so the whole 96.8-second difference
must not be attributed exclusively to thread count. The user subsequently raised GPU preparation;
no GPU run or GPU speedup was measured here. Native CPU execution is now a measured comparison
point for a future GPU implementation.

## Controlled timing comparison

Host: Apple arm64 macOS, 10 physical/logical CPU cores, 24 GiB memory. Python 3.14.7,
PyTorch 2.14.0, NumPy 2.5.3. All work ran on CPU. Each benchmark loads one explicitly supplied
local checkpoint, collects 256 observations once, and retains those tensors. Before each timed
four-epoch update it restores model weights, Adam state, and minibatch RNG. Threads 1, 2, 4,
and 8 are visited in alternating order; one warm-up round is excluded, then the median of
three measured rounds is reported. Inference times cover the same 256 observations after the
update. Collection and process startup are excluded from these microbenchmarks.

| Threads | Initial checkpoint update, s | Initial inference, s | Learned checkpoint update, s | Learned inference, s |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 0.816 | 0.083 | 0.994 | 0.078 |
| 2 | 0.660 | 0.070 | 0.788 | 0.069 |
| 4 | 0.637 | 0.071 | 0.753 | 0.073 |
| 8 | 0.654 | 0.077 | 0.786 | 0.081 |

Four threads reduce update time by 21.9% on initial-policy observations and 24.2% on
learned-policy observations. Two threads are slightly faster for single-observation inference;
the dominant update workload determines the selected uniform setting. These are medians from
a single host, not confidence intervals. A brief Python test run overlapped one learned-policy
round; the raw per-round record is retained. No CPU-heavy test or benchmark ran alongside the
full training comparison.

New update timing separates batch preparation, forward/loss, backward, and Adam/clipping work.
At four threads on initial observations, preparing batches costs about 0.014 s per four-epoch
update, versus about 0.42 s in backward. A short PyTorch CPU profiler sample attributed 57.9%
of self CPU time to `aten::convolution_backward` and 19.8% to NNPACK convolution forward.
These are sampled operator times, not the full-run wall-clock breakdown.

Channels-last tensors and two unfold-plus-linear convolution formulations were also tried
through PyTorch. Their initial-input update medians were about 0.679 s at four threads,
0.675 s at four threads, and 0.612 s at eight threads respectively. The latter's small advantage
did not justify changing the training implementation. All three remain optional benchmark-only
experiments. They do not implement custom backward kernels and are not used in training.

## Reproduction and retained evidence

The [tool README](../../tools/factory-edit-pilot/README.md) documents the benchmark CLI.
To reproduce the thread matrix, pass each of `checkpoint-0.pt` and `checkpoint-65536.pt` from
the first retained run as `--checkpoint`, use `--threads 1 2 4 8 --repeats 3`, and select a new
ignored output directory. The checkpoint is an explicit external input; generated training
outputs are not tracked benchmark source assets.

The full follow-up uses:

```sh
tools/factory-edit-pilot/.venv/bin/python -u tools/factory-edit-pilot/run.py train --case tools/factory-edit-pilot/case.json --config tools/factory-edit-pilot/run.json --output artifacts/factory-edit-pilot/cpu-100898-seed17-threads4
```

Retained evidence lives under ignored `artifacts/factory-edit-pilot/`: the original
`cpu-100898-seed17`, follow-up `cpu-100898-seed17-threads4`, and five `speed-*` benchmark
directories. These include selected valid layouts/traces, full training checkpoints, raw curves,
per-round timings, and exact benchmark input tensors. Source/input hashes in each record identify
the files actually executed, including experimental versions measured during development.

## Verification

index artifact checks passed. The benchmark and full training CLI were exercised directly.
The retained factory audit validates five selected layouts and replays seven selected traces;
