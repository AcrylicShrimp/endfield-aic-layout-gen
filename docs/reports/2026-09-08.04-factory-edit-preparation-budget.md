# Configurable CUDA Preparation Budget

Status: selected, 2026-09-08. The server configuration raises the prepared rollout payload
ceiling from 1 GiB to 4 GiB. Other configurations retain the 1 GiB default. This implements
the user's preference for throughput when GPU memory is available.

The previous long compiled run used ordinary minibatch preparation in 3/1,024 rollouts:
its largest estimated payload was 1,156,028,416 bytes. This is a rare overhead for that run,
not an explanation for its full training slowdown. The ceiling only chooses a representation;
it never drops samples, changes shapes, or reduces training exposure.

## Controlled budget crossing

`preparation_benchmark.py` repeats one retained 256-command rollout eight times inside the
diagnostic, creating a 2,048-command input whose estimated padded payload is 1,745,297,408
bytes. Both variants receive exactly that same input, initial model/Adam state and minibatch
permutations, four epochs and 128 Adam steps. This synthetic repetition is not a training
configuration or a quality experiment. Alternating order follows one warm-up per variant.

| Configured ceiling | Median update seconds | Peak CUDA allocated bytes | Preparation |
| --- | ---: | ---: | --- |
| 1 GiB | 1.647060 | 367,252,992 | Each minibatch |
| 4 GiB | 0.836614 | 2,114,610,688 | Once per rollout |

The larger ceiling reduces this update cost by 49.2%. All eight deterministic CUDA updates
produce exactly the same parameter hash, `f7d4d41116de5c0ab009b6df8d9f223039f98e9634594ceaf5a1bdb9070bbfb7`.
Training keeps its existing nondeterministic execution setting; deterministic algorithms are
used only to isolate this comparison. An earlier diagnostic that injected the two ceilings
directly also found 1.640668 versus 0.825728 s. The table uses the final public configuration path.

## Contract and verification

Optional `prepared_rollout_max_bytes` is a nonnegative integer; zero disables whole-rollout
preparation. Invalid values report the configuration path before training creates output.
`updates.jsonl` records effective `preparation.maximum_bytes` with the selected mode and
estimated payload. The ceiling covers prepared tensors, not all model, gradient or optimizer
allocations. Ordinary minibatch preparation remains the explicit over-budget representation.

The server's existing 65,536-command configuration selects 4 GiB; matched historical long-run
configurations remain unchanged. No model, optimizer, sampling or environment contract changes.
No full-run speedup is claimed from the synthetic budget-crossing result.

Reproduce with `preparation_benchmark.py --case <case> --config <config>
--input <retained-input.pt> --output <fresh-directory>`. Exact input/source/runtime hashes
are recorded in its result. Ignored local and server artifact
`artifacts/factory-edit-pilot/preparation-budget-configured/result.json` has SHA-256
`e94f177e7275ddeb07ef8be3b310db43480668114cf84bbc9d7e56c2cadd641d`.

Local Python tests pass (20 passed, three CUDA/compiler skips); server passes all 23 tests.
Tests cover exact selected tensor values/shapes/dtypes, exact-ceiling acceptance, exhausted
budget fallback, and invalid configuration diagnostics. The final benchmark CLI completes
and verifies the configured budget modes and deterministic parameter equality.

`cargo check --workspace`, `cargo test --workspace`, and worktree/index artifact checks pass.
