# Full-factory ownership: baseline profile and historical comparison

The first profile identifies substantial repeated work outside Rust. In the
representative food factory, fresh generation takes **24.37 seconds**, while
its Rust constructor process takes about **0.14 seconds**. Initial randomization
recomputes the same physical-state identity for every offered candidate. The
profile records 5,723 physical-key calls, 8,945,275 JSON encodes and 2.22 GB of
cumulative encoded text. This is cumulative work, not peak memory or IPC volume.
The native physical validator is a small fraction of the measured collection cost.

The user-requested stages 1 (profile) and 2 (compare with the earlier Rust-owned
path) are complete. The implementation remains unchanged for this baseline.
Contract redesign and native reimplementation follow this evidence.

## Inputs and measurement

Use the completed `current-history-16`, seed-17, batch-4 screen. Restore its
actual batch-3 actor/critic checkpoint and retained action RNG seeds. Select the
lower median starting area within each of the four products, plus the largest
starting area if distinct. Selection was written before inspecting profiles.
The five cases cover 2, 3, 18, 23 and 26 facilities, belt and pipe commodities,
cycles and branching. They are representative retained examples, not a weighted
estimate of every training draw or a maximal factory stress test.

Server: Core Ultra 9 285K, Python 3.12.13, one PyTorch CPU thread per collector,
unchanged release Rust libraries. The baseline source is `aa5df04` plus standalone
profiling tools. The existing completed-run runtime and checkpoints are preserved.

Each serial case has one warmup and three uninstrumented repetitions. Clear only
the cross-replay description cache before each repetition; normal within-episode
cache behavior remains. Runtime opening and actor/checkpoint loading are outside
the collection timer. Collection includes 32 actions, inference, episode output,
experience compression and file hashing. Generation independently repeats the
retained fresh draw, constructor and initial randomization; it is outside training.
Every repetition checks exact request/initial geometry, sampled physical trace
and complete actor/critic experience identity after timing.

Separate runs use Python cProfile, nested boundary timers and Node V8 sampling.
Instrumentation materially increases runtime; its durations explain call structure
and must not be presented as ordinary throughput. Inclusive regions overlap.
Pipe waiting includes Node computation; do not add those times together.

## Confirmed costs

`random_factory_generation.generate` constructs action keys with a list
comprehension that calls `physical_key(best)` once per candidate. The key recursively
canonicalizes the complete factory and JSON-encodes records while sorting arrays.
For the food case's six setup selections, the instrumented generation took 77.57
seconds, of which 76.87 seconds were under `physical_key`. The uninstrumented
24.37-second median includes 24.05 seconds of setup, 0.23 seconds of admission,
and the remaining import/output work. The constructor's 0.14 seconds is nested
inside admission. This directly supports retaining identities once per immutable
native state rather than computing them inside candidate loops.

Ordinary collection already has bounded witness-identity reuse, but candidates,
observations and state transfers remain outside native ownership. For the food
case, its instrumented 5.54-second collection included:

| Region | Inclusive seconds |
| --- | ---: |
| Python observation arrays, 48 constructions for 32 actions | 2.078 |
| Describe RPC, including Node work and transfer | 1.143 |
| Python JSON encoding, across all callers | 0.770 |
| Selection mask, including nested identities/JSON | 0.690 |
| Actor plus critic CPU inference | 0.272 |
| Selected execute RPC | 0.203 |
| Rust proposal parsing, acceptance and commit | 0.023 |

These rows overlap and must not be summed. `current-history-16` uses current
world/history actor inputs; the independent critic also observes the retained
best world. Current and best observation work is shared where possible, but
best-world encoding still requests the broad description and reconstructs arrays.
Node's dominant non-idle sampled work includes movement-plan preflights, cloning,
terminal joining and geometry keys. The existing Rust validator remains authoritative
and passes all replayed proposals; slow collection is not evidence of slow native
validation.

Food collection transferred 6.27 MB of requests and 8.81 MB of responses through
Python/Node pipes and serialized 8.55 MB of native snapshots. Python JSON encoding
across all callers produced 101.04 MB cumulatively. The largest-area example
produced 135.11 MB of Python JSON text for 32 selections. This supports replacing
per-action full-state exchange with retained native state and observation arrays.

## Actual parallel collection

A separate execution used the real harness pool and worker, all 32 batch-4 draws,
the retained behavior checkpoint and 24 persistent workers. It performed no PPO
update or cloud export. All 32 factories were admitted, producing 1,024 actions.
All generation identities, initial geometry and physical/sampling traces matched
the original committed batch.

Worker startup took 2.06 seconds, collection 29.05 seconds and the complete owned
pool execution 32.16 seconds. Peak aggregate RSS was 30.38 GiB, with at most 59
observed processes. Summed worker generation was 139.64 seconds and summed episode
execution 56.59 seconds; these overlap across workers and are not wall-clock
components. The sampled food case completed last. This is one representative
parallel measurement, not a repeated throughput benchmark or a new learning run.

The first batch-profile invocation failed before creating a run because an
optional process-inspection package was absent. The final helper uses the existing
harness process table without adding a dependency. The complete invocation above
is the successful baseline.

## Comparison with the earlier native-owned pilot

The retained [2026-09-08 native results](2026-09-08.11-factory-edit-native-results.md)
and their raw summary hashes were rechecked. That migration had actually completed:
Rust owned catalogs, state, candidates, edits, scores, rewards and observations;
the ordinary boundary was arrays outward and an action handle/index inward.
Full JSON export was restricted to explicit evidence/checkpoint operations.

| Property | Earlier native-owned pilot | Current full-factory baseline |
| --- | --- | --- |
| Physical scope | Directed-path local-edit pilot | Complete mixed/branching/cyclic factories |
| Environment state | Retained in Rust | Rust acceptance plus Python witness copies |
| Candidates and selected edits | Rust | Node, including bounded reembedding |
| Observation assembly | Rust arrays | Python/NumPy |
| Action boundary | Handle/index | Full witness JSON plus selected action |
| Episode initialization | Retained pilot root/reset | Fresh request, constructor and setup edits |
| Inference in cited replay | CPU actor; 16 Torch threads | CPU actor and critic; one Torch thread |

The old controlled native replay took 23.03–56.99 ms for 256 actions without
inference, and 117.03–211.13 ms with its CPU actor. It reduced environment time
75–80% against that pilot's Python reference. Its 65,536-action full CUDA training
run took 45.93 seconds; native candidates, observations and array export accounted
for 2.46, 1.88 and 0.13 seconds respectively. These numbers must not be divided
into the new full-factory timings to claim a language-regression multiplier:
factory scope, actions, models, initialization and threading differ.

The architectural comparison is nevertheless definite. The full-factory extension
introduced a separate acceptance/proposal boundary rather than extending the old
owned observation/index engine. That reintroduced full-state serialization,
Python observation construction, Node proposal execution and repeated identities.
The completed PPO harness's durability and monitoring checks did not restore the
old environment ownership boundary. The next contract must cover the current
full-factory semantics, not route the new problem through the restricted old pilot.
