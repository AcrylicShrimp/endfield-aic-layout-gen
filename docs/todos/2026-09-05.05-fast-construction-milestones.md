# Fast complete construction: milestones

## Status

**M1-M4 complete; M5 runtime checkpoint and first improvement contract is next.**
This is the active near-term roadmap after `29b0b8a`, not a replacement for the accepted
[constructive-planner design](../designs/2026-09-02.00-constructive-layout-planner.md).

## Objective and context

The product goal is to construct a complete valid factory quickly, then improve that concrete
factory transactionally. The immediate objective is to reduce construction runtime while keeping
the same valid factory and search decisions. Layout compactness is the subsequent phase, not a
constraint on finding the initial factory.

The unchanged Heavy Xiranite request is the main regression workload, not the only supported input
or a source of hardcoded game limits. The [current baseline](../benchmarks/constructive-output-summary/report.md)
has 59 facilities, 89 internal and seven external requirements, 47 accepted states and 178 A* calls.
Its natural footprint is 165 x 140; this is an observed output, never a required canvas.

| Measured baseline | Approximate time |
| --- | ---: |
| Complete CLI, including full JSON and HTML | 23.3 s |
| Construction | 21.6 s |
| Existing-network path search, 79,779 calls | 10.3 s |
| Future-boundary accessibility, 92 calls | 8.3 s inclusive |
| Independent network validation, 200 calls | 1.55 s |
| Physical A*, 178 calls | 0.24 s |

Accessibility includes some crossing analysis; do not add inclusive parent/child timings.
Output already uses a short stdout summary and file-backed full diagnostics. Copying whole nodes
costs only about 0.14 s in this workload. Neither A* nor node copying is the first optimization target.

## M1 — indexed existing-network path queries

Input: an immutable transport network and directed endpoint query within the current candidate.
Output: the same segment-index path, or the same absence of a path, used by attachment enumeration.

1. Build outgoing adjacency once for the relevant immutable network view; preserve original segment
   order and BFS tie-breaking. Stop scanning the complete segment vector at every visited cell.
2. Re-profile after that change. Reuse searches from identical roots only if repetition is still
   significant. Do not assume a reverse-rooted search chooses the same path as the current BFS.
3. Specify index lifetime explicitly. No index or cached failure survives a changed network unless
   its validity is established. Keep the reference traversal in tests, not a second production mode.

Completion criteria:

- Differential path tests cover branches, convergence, equal-length alternatives, unreachable
  endpoints and directed cycles. Capacity/terminal/crossing tests remain in force.
- Full-workload accepted nodes, candidate order, placement attempts and A* counts are unchanged.
  Internal query counts may decrease through reuse; such counters must not be confused with search budgets.
- Record index construction/query cost, query calls and visited/scanned work with bounded aggregate
  counters. Demonstrate a repeatable reduction in path-query time and end-to-end construction time.
- If the candidate does not improve runtime outside observed variability, revise or reject it;
  do not mark the milestone complete merely because an index was added.

## M2 — efficient boundary accessibility screening

M1's [paired release measurements](../benchmarks/constructive-indexed-paths/report.md) reduced
median construction from 21.754 s to 11.718 s and full CLI time from 23.419 s to 13.400 s.
The separate candidate profile attributes 8.407 s inclusive / 7.572 s exclusive to boundary
screening. This is now the dominant construction operation; path-result caching is deferred.

Input: one immutable expanded candidate, remaining commodity boundaries and runtime crossing rules.
Output: the same sorted set of blocked requirements and the same accept/reject decision.

1. Replace repeated hash-based visited/occupancy work with an appropriate compact representation
   or reusable flood-fill workspace on the naturally derived envelope.
2. Reuse candidate-local occupancy and crossing information where compatibility permits. Preserve
   commodity distinctions, independent bridge axes and the exterior-reachability check.
3. Specify checked coordinate conversion, allocation/resource guards and reset/epoch behavior.
   Do not silently clip the envelope, weaken checks or enlarge budgets to obtain a faster result.

Completion criteria:

- Differential tests cover enclosure, legal and illegal crossings, multiple commodities, border
  and negative exterior coordinates, and reuse after geometry changes.
- Blocked requirements, accepted states and budgeted search choices match the reference.
- Record cells visited, screening calls, workspace memory and inclusive/exclusive timings.
  Screening and total construction become repeatably faster without unbounded memory growth.

## M3 — re-profile before choosing the next serial optimization

M2's [paired measurements](../benchmarks/constructive-boundary-screening/report.md) reduce median
construction from 11.697 s to 4.417 s and full CLI from 13.362 s to 6.091 s. Candidate profiles
place independent validation at 1.539-1.542 s exclusive, followed by all-caller crossing options
at 1.084-1.085 s. The dense flood itself is 0.302-0.305 s. Start by separating validator
reachability and component/geometry checks; repeated full-segment and component scans are visible
in code, but have not yet been independently timed. Do not bypass independent validation.

Re-run the full profile after M1 and M2. Rank exclusive operation time and investigate the next
dominant caller with a native sample or more specific aggregate counters when necessary.

Network validation is a candidate, not a predetermined rewrite: it currently repeats whole-segment
scans for connectivity and cell relationships. If still material, index the committed geometry
inside the independent validator. Do not trust constructor acceptance flags, cached validity or
constructor-owned mutable indexes as independent evidence of correctness.

Completion criteria:

- Publish the updated cost distribution, remaining hotspot and a specific change/defer decision.
- Any implemented validator change passes positive and deliberately corrupted-witness regressions,
  preserves diagnostics and still performs independent final validation and original-rate auditing.
- Do not start broad clone elimination, output-history redesign or A* rewriting without new evidence.

## M4 — bounded parallel analysis, measured explicitly

M3's [paired measurements](../benchmarks/constructive-independent-validation/report.md) reduce
median construction 4.434 -> 3.878 s and full CLI 6.109 -> 5.546 s. Crossing-option generation
now leads exclusive construction time at 1.090 s (867 calls); independent validation totals
0.988 s across smaller checks. Commodity screening totals 1.177 s including about 0.822 s of
crossing generation and 0.300 s of flood. Use these non-double-counted costs when selecting a
bounded worker experiment; parallel adoption remains conditional, not assumed by this milestone.

Candidate work: commodity-specific accessibility checks and independent network-local analysis of
the same fixed candidate. Growth transactions themselves depend on the previous accepted state.
Do not race growth commits or select whichever candidate finishes first.

Before implementation, define worker-count controls, bounded scheduling, per-worker immutable input
views, deterministic result/error ordering, cancellation and resource accounting. The current
profile is **calling-thread-only**: extend its coverage explicitly before measuring worker work.
Separate critical-path wall time from summed worker time; do not add overlapping worker durations
and report them as elapsed time.

Completion criteria:

- Benchmark one worker against bounded multi-worker configurations that fit the host, on the full
  workload and smaller regression workloads. Record worker utilization, memory and scheduling cost.
- Repeated runs have identical accepted states and ordered diagnostics. Placement/A* budgets and
  first-feasible decisions are unchanged; any speculative extra work has explicit bounded accounting.
- Adopt parallel execution only with repeatable end-to-end benefit. If the remaining independent
  work is too small after M1/M2, record the measured reason to defer it. Thread count alone is not success.

## M5 — runtime checkpoint and return to layout quality

Completion criteria for this runtime phase:

- Publish before/after planner and CLI distributions, operation counters and peak memory against
  M0. The full factory and all regression witnesses remain valid with unchanged search semantics.
- M1 and M2 have demonstrated useful reductions; M3 and M4 have evidence-backed decisions.
- Record remaining bottlenecks and the point at which further runtime work is no longer the next
  priority. No unmeasured promise of a particular second count or speedup is an acceptance criterion.
- Specify, but do not bundle into this runtime phase, one bounded layout-improvement transaction:
  candidate mutation, route repair, full validation, scoring, commit/reject and budget diagnostics.

The following phase improves the completed factory: area first, then physical belt/pipe tiles,
then turns. It must retain the current valid factory if a candidate fails validation or does not
improve that lexicographic score. Unlike M1-M4, this phase intentionally may change geometry;
equality to the old layout is replaced by validity, original-request coverage and score improvement.
No global exact fallback or caller-supplied W/H feasibility bound is introduced.

## Shared verification and measurement gate

- Keep catalogs, source plan, seed, budgets, build profile and output mode identical in comparisons.
  Record revisions, input hashes, host/toolchain, profile coverage and whether instrumentation is on.
- Use release builds. Finish compiler/tests before timed runs; never time compilation as construction.
  Capture native samples in separate runs. Re-establish a same-host baseline rather than comparing
  only against historical timings.
- For each accepted performance slice, collect at least five baseline and five candidate runs,
  alternating their order when practical; report median and range. Measure both unprofiled CLI/
  planner latency and separately instrumented operations. Investigate overlapping/noisy results.
  The existing OFF/ON/ON harness is a starting point, not this expanded before/after protocol.
- Keep the full JSON/HTML output enabled for the end-to-end comparison. Check stdout's short
  summary, file paths, complete coverage and exact accepted-state/search-choice hashes excluding
  elapsed-time and intentionally changed internal work counters.
- Include small chain, branch/convergence, cycle and crossing fixtures, plus structured failures.
  Add relevant controlled scaling cases from external fixtures so one large example is not the
  sole correctness/performance oracle. Investigate any new small-case or memory regression.
- Run `cargo fmt --all`, `cargo check --workspace`, `cargo test --workspace` and relevant manual CLI
  commands after implementation. Keep diagnostic/profiler output bounded and structured.
- Compare each slice with AGENTS.md and the accepted design; commit each verified unit separately.
