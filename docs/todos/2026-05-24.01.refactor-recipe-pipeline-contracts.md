# TODO: Refactor recipe pipeline contracts

## Current Status
- State: Finished
- Dropped Reason: 
- Last Status Update: 2026-05-24 17:41:08

## Context
The recipe implementation now supports JSON validation and target dependency graph resolution, but the main recipes module mixes raw data models, loading, validation, indexing, graph resolution, and tests in one file. The next milestone will add throughput logic, so recipe stages need explicit contracts before behavior expands.

## Why It Is Needed
Current verification passes, but the contract boundaries are implicit: RecipeBook is parsed but untrusted, resolve_graph re-runs validation internally, unique output producer assumptions are not encoded by type, and the validator and graph resolver build overlapping index structures.

## Completion Criteria
- [x] Recipe code is split into focused modules without changing CLI behavior
- [x] Raw parsed data and validated data are represented by distinct public types
- [x] Graph resolution accepts only validated/indexed recipe data
- [x] Validation diagnostics and graph JSON output remain compatible with current examples
- [x] Existing and new stage-contract tests pass
- [x] README and design notes reflect the final pipeline
- [x] Pseudo code diff is recorded before implementation begins

## Detailed Plan

1. Preserve the current behavior as the refactor baseline.
   - Run `cargo test --workspace`.
   - Run `cargo run -p aic-cli -- recipes validate --file data/examples/recipes.valid.json`.
   - Run `cargo run -p aic-cli -- recipes graph --file data/examples/recipes.graph.json --target originium-casing`.
   - Save the current JSON output shape as the compatibility target.

2. Split the recipes module by responsibility.
   - Keep `recipes.rs` as the module entry point and public re-export surface.
   - Move parsed data structs into `recipes/model.rs`.
   - Move stable ID syntax helpers into `recipes/id.rs`.
   - Move JSON file loading and `LoadRecipeBookError` into `recipes/load.rs`.
   - Move validation diagnostics and validation logic into `recipes/validate.rs`.
   - Move validated-data promotion and derived indexes into `recipes/validated.rs` or `recipes/index.rs`.
   - Move target dependency graph resolution into `recipes/graph.rs`.
   - Do not create `recipes/mod.rs`; repository rules require the `foo.rs` plus `foo/...` module layout.

3. Define the stage contracts explicitly.
   - `RecipeBook` is raw parsed data and is not trusted.
   - `validate_recipe_book(&RecipeBook) -> ValidationReport` performs diagnostics only and does not mutate the raw data or expose a trusted index.
   - Validation may build temporary analysis maps for diagnostics, but those maps are not a trusted graph-resolution contract.
   - `ValidatedRecipeBook::try_from_recipe_book(RecipeBook) -> Result<ValidatedRecipeBook, ValidationReport>` is the only promotion path from raw data to trusted data.
   - `RecipeIndex` is built only during successful promotion and encodes unique producer, external item, and recipe lookup invariants.
   - `ValidatedRecipeBook::resolve_graph(&self, target_item: &str) -> Result<RecipeGraph, RecipeGraphError>` resolves graphs without re-running full validation.
   - `RecipeBook::resolve_graph` should be removed from the public API instead of wrapping the validated resolver.
   - `RecipeGraphError::InvalidRecipeBook` should be removed once invalid data can no longer reach graph resolution.
   - `RecipeBook::validate` may remain only as a thin compatibility wrapper around `validate_recipe_book`, if keeping it does not blur the raw-data contract.

4. Keep validation invariants centralized.
   - Preserve all existing v1 checks: schema version, kebab-case IDs, duplicates, positive numbers, non-empty outputs, missing links, external/output overlap, ambiguous producers, and cycles.
   - Introduce an internal analysis/index-building path so producer-map construction is not duplicated between validation, promotion, and graph resolution.
   - Make each diagnostic code stable unless a breaking reason is documented.

5. Make graph resolution depend on validated data only.
   - Remove public graph resolution from raw `RecipeBook`.
   - Resolve external targets to a graph with the target in `external_items` and an empty `recipes` list.
   - Resolve produced targets to dependency-first recipes.
   - Preserve current graph output ordering: external items are sorted and recipes appear after their dependencies.
   - Keep `UnknownTargetItem` and `InvalidTargetId` as graph-stage errors.
   - Remove `InvalidRecipeBook` from graph errors if graph APIs can no longer receive invalid data.

6. Update the CLI without changing user-facing behavior.
   - `recipes validate` should load raw data, validate it, print the same validation report JSON, and fail on invalid reports.
   - `recipes graph` should preserve the current error priority: invalid target item IDs fail before recipe-book validation or promotion diagnostics.
   - `recipes graph` should load raw data, check target ID syntax, promote the book to validated data, print validation diagnostics on promotion failure, and otherwise print the same graph JSON shape.
   - Error messages should continue to include the failing file path or target item where relevant.

7. Reorganize tests around contracts.
   - Keep model parsing tests close to the model or loader.
   - Keep validation invariant tests in the validation module.
   - Add promotion tests for successful and failed `ValidatedRecipeBook` construction.
   - Keep graph tests focused on validated-data graph behavior.
   - Add compatibility assertions for graph JSON ordering, sorted external items, and external-target output.
   - Add or preserve parse compatibility tests for unknown fields on `RecipeBook`, `Recipe`, and `ItemAmount`.
   - Add CLI smoke checks only if the project gains an integration-test harness.

8. Update documentation after the code shape is final.
   - Update README command examples only if command syntax changes.
   - Update the recipe schema design doc with the explicit raw-to-validated pipeline.
   - Update this TODO activity log with the final verification result.

9. Final verification.
   - Run `cargo fmt --all`.
   - Run `cargo check --workspace`.
   - Run `cargo test --workspace`.
   - Run the recipe validate and graph example commands.
   - Inspect `git diff --stat` and confirm the refactor did not widen into throughput or layout behavior.
