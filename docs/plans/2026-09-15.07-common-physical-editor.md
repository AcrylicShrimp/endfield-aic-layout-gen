# Plan: Extract one common physical editor for factory and procedural layouts

## Current Status

- State: Completed
- Last Updated: 2026-09-15 19:43:00
- Blocker: None

## Goal and Scope

One outcome: both a validated recipe-bound factory witness and a validated
`aic-physical-layout-v1` procedural layout compile into one recipe-independent
physical problem/draft and execute through the existing native editor without
losing physical obligations or changing the established factory behavior.

This step establishes the shared state and editor boundary needed by outcome
pretraining. It does not collect a training dataset, add prediction heads, modify
PPO, optimize the generator, accept incomplete source layouts, or authorize a long
run. It extracts and reuses the current editor; it does not build a second
procedural simulator.

## Proposed Changes

Add compiled editor-domain types under `aic-layout`. The compiled problem contains
only physical facts needed by editing: stable source-local identities, catalog
facility/component references, typed transport/commodity equivalence, directed
incidence, exact rates, terminal roles, block/component ownership, channel
membership, baseline endpoint restrictions and permitted zero-length behavior.
It embeds one immutable, deduplicated catalog of the definitions actually used by
the problem: facility footprints, rotations and local ports; component footprints,
fixed rotations and channel descriptors; and transport capacities. Both source
compilers lower their already validated external catalogs into this same authority.
The editor reads no source-specific catalog in its action, routing, mask or feature
hot paths. The draft contains block poses, the complete selected terminal-to-port
mapping, external/channel anchor positions, mutable component positions and one
optional ordered path per compiled edge. Component definitions and rotations stay
fixed in the problem. Indices are dense and checked at construction; serialized
source IDs are metadata and never learned numerical features.

Keep factory recipe requirements, utilization records and witness-specific export
metadata in a factory admission owner. Keep the procedural `Problem/Solution` and
its connection-to-segment mapping in a procedural admission owner. Each owner
validates its source once, compiles the common form, and exports a complete draft
back to its own source schema. An unfinished draft returns an explicit
`pending-edge` diagnostic and is never fabricated into a complete layout.

Every source owner records a stable source binding separately from common physical
identity. Factory admission retains the current request/original digest. Procedural
admission accepts the bounded original JSON bytes (or a generated byte buffer from
the one normal serializer), verifies their SHA-256 while decoding/validating, and
retains that hash. It also records the checked occupied source-frame origin before
compiling a canonical origin-zero draft. An unchanged complete draft exports by
adding that origin back and must reproduce the same typed poses/routes/bridge
ownership after stable ordering. A translated source therefore compiles to the
same physical problem/action semantics and exports to its own translated frame;
the source-byte hash remains different. Edited exports use the same retained
source-frame offset. Common structural/root identities are calculated from the
canonical compiled form, never from that offset or byte hash.

Move the existing private `Blueprint`, `Draft`, topology, geometry and declarative
edit implementation into a single internal physical-editor module in
`aic-pilot-native`. Parameterize only the necessary source acceptance/export
boundary. Factory completion continues to call the full factory validator and
area-first metric authority. Procedural completion calls `aic_layout::validation`
and its physical metrics. The common engine retains its current local coordinate
frame, routing kernel, transactional repair, valid-best state and work counters.
Source adapters may have different final acceptance metrics, while action
selection and physical mutation use the same compiled state.

Write new native snapshots as `declarative-edit-checkpoint-v4`, containing the
common problem/draft, immutable used-definition catalog, tagged source owner,
source binding and existing limits/state/best/counters. Preserve the documented
cold-conversion boundary: readers accept physical v2 and v3 factory snapshots,
validate their original bindings and physical state with the old schema rules,
then compile them once into v4 in memory. They never upgrade learned tensors or
optimizer/replay state. Retain and exercise the actual v2 fixture at
`artifacts/physical-editor-extraction/before/legacy-checkpoint.json` and the actual
v3 fixture at
`artifacts/physical-editor-extraction/translation-final/legacy-checkpoint.json`.
Wrong source kind/hash, catalog or common-problem binding rejects before restored
payload use. There is no procedural legacy snapshot.

Procedural bridge compilation creates one channel node per declared
`(bridge, connection)` pair even when two channels occupy the same cell. Split
each affected connection route at its declared channel nodes and retain an
ordered mapping for exact recombination. Reject ambiguous repeated bridge visits,
missing declared users, incompatible component/transport definitions, unsupported
cycles, invalid zero-length joins and guarded materialization before publishing a
session. Branch/merge incidence remains explicit and is not inferred from cell
coincidence.

Use stable structured diagnostics with source, stage and entity. A source
validation failure, unsupported lowering, incomplete export, routing exhaustion
and internal invariant failure stay distinct. Do not call an exhausted local
route globally infeasible.

## Execution Result

Implementation is complete. `aic-layout` now owns the serialized compiled
problem, its embedded
used-definition catalog, mutable physical draft, standalone validation and
name-independent compiled identity. Factory admission compiles that form once;
the common draft is authoritative during edits and routing, while the legacy
factory state is one cached export projection used by the existing API and full
factory acceptance.

The native `physical_editor` module is the sole placement, band-edit, endpoint,
conflict, candidate-root and bounded-routing implementation. Both factory
learning and procedural sessions now enumerate through the same complete physical
extent and candidate authority, while retaining the factory's ordered joint port
groups and numerical feature order. The serialized boundary validates every
embedded definition and rejects overflowing or greater-than-1,000,000-cell
occupied spans during admission and restore, before candidate materialization.
The old private factory geometry implementation was removed, and the remaining
topology module keeps only source compilation/export duties.

Factory compilation retains both transport capacity definitions because the
established numerical schema has fixed belt and pipe capacity slots even when a
particular witness routes only one kind; those rows are therefore used physical
features. Procedural compilation, which does not yet build numerical features,
embeds only transports referenced by its networks.

Procedural admission validates and hashes bounded original
`aic-physical-layout-v1` bytes, compiles in an origin-zero frame, creates distinct
nodes for every declared bridge channel, retains ordered connection segments and
exports back into the retained source frame. Exact no-bridge and bridge fixtures,
translation and opaque relabeling, incomplete export, shared editing, masks,
candidate selection and source binding are covered by native tests.
