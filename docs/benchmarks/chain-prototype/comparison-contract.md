# Milestone 5: matched-budget comparison and completion audit

Status: established before implementation. This stage measures the completed experimental
constructors and writes the final research finding; it does not change generation policy or
replace production. Different inventories and external-boundary semantics remain separate.

## Experiment input

A schema-1 comparison plan lists explicit relative factory-request paths and identifiers,
increasing proposal-budget checkpoints, M3 first-family variants, M4 proposal orders/rankings,
and M4 routed-trial limits. A separate unchanged M4 policy supplies the common shortlist,
rollback, slice and fit allowances. All catalogs and the independent validator are explicit
CLI arguments. Reject malformed plans, duplicate identities/variants and checkpoints above an
original request's proposal cap; this comparison does not enlarge an existing work limit.

The primary plan uses the four original requests (battery, citron, nine-facility iron and
eight-facility iron), proposal caps 128/256/512/1024, all four fixed M3 family priorities, and
the M4 two proposal orders × two rankings × trial limits 1/8. This gives 192 runs. No variant
uses a recipe-specific policy or receives an uncharged warm start, previous winner or fixture.

## Equal-budget meaning

Each variant/checkpoint is a fresh algorithm execution with the same total proposal allowance
and the same fixed route-expansion, validation, elapsed and fit-check allowances for that
request. M4's slices and repeated trials draw down that single total account. M3 and Partial
receive the same fit allowance but do not use it. Do not add the best of four M3 priority runs
or several M4 controls and call that the result of one run. There is no free portfolio.

This is equal **allocated total work budgets**, not a false claim of equal consumed work or
equal CPU cost per primitive. Record the full used-work vector, construction elapsed time,
early termination and unused allowance. Do not burn dummy work to force equal counters. Sweep
the proposal allowance with the other ceilings fixed; do not claim every primitive has been
converted to one universal effort unit. A faster exhausted local domain does not prove global
infeasibility. Wall-clock comparisons are descriptive on this machine, not portable claims.

Independent post-run audits do not generate/select candidates. Their process work is recorded
separately from the algorithm budget, rather than hidden as construction or charged to only
one algorithm. Every success row must pass that original-request audit before entering a
quality comparison. Incomplete rows have no complete score.

## Comparison integrity and outputs

Freeze and hash the original requests, policy, catalogs, executable and comparison code. Derive
requests by changing only the explicit proposal allowance and the declared M3 family priority;
derive M4 policies by changing only the declared order/ranking/trial count. Verify the original
inventory/utilization/flow/boundary signature for each derived run. Input arrays are not pose
hints. Nine- and eight-facility iron are different comparison groups, never interchangeable.

Invoke the existing constructor CLIs, retaining immutable full decisions/validation artifacts
and stopped reports. Recompute every complete score with the M4 port-arm-inclusive metric;
do not compare its turns with historical M3 segment-only counts. Then invoke the standalone
verifier with the original request and selected witness. Any unexpected CLI/provenance/budget
or audit failure aborts the comparison visibly; do not exclude the offending row.

Emit machine-readable rows with case/variant/checkpoint, exact semantic signature, assigned
and consumed work, completion, common score, first/best completion evidence when reported,
termination/failure diagnostics, witness/report/audit identities and source provenance. Summary
tables and completion-versus-budget curves must be derived from those rows. Preserve all
failures and distinguish a local window limit from a global resource cap.

Factor comparisons isolate: family ordering within M3; M4 exhaustive/interleaved proposals
under a fixed ranking/trial count; Partial/Fit under a fixed proposal order/trial count; and
one/eight routed trials under fixed generation/ranking. The M3-to-M4 comparison changes multiple
mechanisms and must not attribute every difference to lookahead alone. No human reference
with omitted external routes enters the full-factory quality table.

## Verification and final gate

Tests cover plan validation, exact derived-request preservation, separate inventories, budget
accounting, common-score normalization, independent acceptance, explicit failures, immutable
CLI output, and reproducible summaries. Run all 192 primary rows, inspect the generated summary
and representative completion/failure artifacts, run broad Node/workspace verification, and
commit the completed research unit. Existing M4 rendered pages remain authoritative when an
identical witness is reused; inspect any newly selected geometry before presenting it visually.

The final report must identify what is reproduced, what fails or remains unsupported, and what
generalizes only within the measured graph class. Make an evidence-backed research recommendation
without changing production. Finish with a requirement-by-requirement audit of the original
goal: contracts/references, incremental chain/cycle/fan-in growth, fit and actual continuation,
bounded preserved-region replay, independently validated explicit-boundary factories, equal
budget comparisons, diagnostics/reproduction/tests/reports/commits, and the final findings.
Only mark the native goal complete after inspecting evidence for all requirements; historical
status statements alone are not completion proof.
