# Constructive Layout Planner

## Status

Accepted on 2026-09-02. This design replaces the global exact joint solver as the production layout-generation architecture. The global exact model remains available only through isolated research tooling.

## Goal

Generate a complete valid factory quickly, even when the first layout is large or visually poor, and improve that concrete factory for as long as the caller's budget allows.

The production lifecycle is:

```text
normalize production graph
-> place the target facility as the seed
-> add one connected upstream facility or atomic cycle
-> assign the ports required by that frontier edge
-> extend and route the affected commodity network
-> validate the expanded partial factory
-> repeat until the production graph is complete
-> validate the complete factory
-> iteratively improve local regions
-> return the best validated layout seen
```

The planner does not attempt to prove a global optimum. It must always distinguish a construction failure from a proof of infeasibility.

The production planner has no W/H feasibility limit. It constructs a complete factory at its natural footprint, reports that measured width and height, and treats smaller area as an improvement objective. Fixed W/H canvases belong only to explicit exact-solver research experiments.

## Production And Research Boundary

The production planner and the former global exact solver have different contracts.

- Production commands call the constructive planner only.
- Explicit research commands may call the global exact solver.
- The production planner must not fall back to the global exact solver.
- The global exact solver must not be used to validate ordinary production success.
- Research timeouts and `unknown` results must not appear as production planner failures.
- Neutral game data, production-graph data, geometry types, scoring, validation, and HTML rendering may be shared.
- Exact-model variables, Pumpkin propagators, exact search reports, and exact harnesses remain inside the research boundary.

The old exact code is preserved because it remains useful for small-instance baselines, local-oracle formulation research, and historical comparisons. It is not the authoritative factory generator.

## Complete Factory Contract

A successful initial construction contains:

- every required facility instance exactly once;
- a legal rotation and position for every facility;
- no overlap between facility footprints;
- legal directional port assignments;
- every internal material requirement connected through the correct transport kind;
- one synthesized logical network for compatible requirements of the same item and transport kind;
- capacity sufficient for every terminal rate;
- physical pipe and belt geometry that obeys layer occupancy and crossing rules;
- accessible external input and final-output connections;
- used bounds computed from actual facility, transport, and logistics-component geometry;
- a successful independent layout validation result.

Pipe and belt layers are physically independent from each other. A facility footprint blocks both transport layers. Same-layer transport conflicts require rerouting or a legal logistics component.

The constructor grows its working geometry as needed. A construction failure therefore identifies an exhausted local candidate or resource budget rather than a W/H limit. It must not label the request globally infeasible unless a separately scoped proof establishes that claim.

## Planner State

The mutable planner state owns one candidate that is complete for its currently covered production subgraph:

```text
LayoutState
  placements
  port assignments
  logical commodity networks
  physical routes
  derived logistics components
  facility occupancy
  belt-layer occupancy
  pipe-layer occupancy
  used bounds
  validation status
  score
```

Stable facility, terminal, requirement, and network identifiers must be preserved across improvement attempts so diagnostics and HTML history can explain what changed.

The constructor must not create a facility-only global placement and postpone routing. Each accepted growth step adds placement, relevant port assignments, and physical routing together. If a frontier expansion cannot be routed, the planner may try other local placements or ports without invalidating the previous accepted state.

This is the construction invariant: an accepted state is already a complete valid factory for the covered subgraph. Reaching the final frontier therefore implies a complete valid factory for the full graph; there is no deferred global routing phase that can invalidate all earlier placement work. An exhausted constructive retry or resource budget may still stop growth, in which case the report contains the last valid state and the exact unresolved frontier without claiming success.

### Local Construction Backtracking

Every frontier expansion is transactional. The constructor first retries alternative local positions, rotations, compatible ports, and routes for the new facility. If those candidates are exhausted, it may roll back a bounded number of recently accepted frontier steps and reconstruct that local region. Older unrelated validated regions remain intact.

The rollback window begins with the current expansion and may widen explicitly when a smaller window has no remaining candidates. Its size, attempted candidates, rollback count, and unresolved frontier are diagnostic outputs. This mechanism is constructive search over a local growth history; it is separate from later score-improvement passes and from the local CP oracle.

## Initial Construction

The first constructor favors reliability and debuggability over compactness. It grows from the final-product facility toward upstream input producers.

1. Place the final-product facility as the seed.
2. Select one unresolved input frontier, prioritizing pipe work in the initial implementation.
3. Place only the facility or atomic cycle that supplies that frontier.
4. Select the ports needed by the new connection.
5. Extend the matching commodity network and route it immediately.
6. Validate the expanded partial factory before accepting the step.
7. Repeat until every required facility and network is present.
8. Derive splitters, convergers, and legal crossings from the routed network topology.
9. Validate the whole factory.

Deterministic shelf, row, corridor, routing-order, port-selection, and path-selection strategies are allowed in this production constructor. They are implementation strategies, not proofs that omitted layouts are invalid.

## Commodity Network Synthesis

Logical wiring edges specify supply and demand. They do not require independent point-to-point physical paths.

Requirements may share a network only when item identity and transport kind are compatible. Network synthesis should build a trunk or tree connecting the selected terminals before grid embedding. Physical split and merge components are derived after embedding from topology and rate requirements.

The first implementation may use a simple deterministic tree that is extended with each frontier step. Later passes may merge trunks, change roots, or resynthesize a network.

## Route Engine

The route engine owns physical path search. It receives fixed obstacles, terminal candidates, the current layer occupancy, and a logical network to embed.

The first engine uses A* or Dijkstra. Its path cost is ordered around:

1. legal reachability;
2. added physical tile count;
3. route turns;
4. congestion and obstruction of future routes;
5. stable deterministic tie-breaking.

Routing failure identifies the failed network and preserves evidence about exhausted terminals, blocked regions, and attempted rip-ups.

Rip-up-and-reroute may remove a bounded set of already routed networks and retry them in another order. A retry budget must be explicit and diagnostic, not an unbounded loop.

## Local CP Oracle

Constraint solving is reserved for bounded local questions such as:

- choose ports for a small set of nearby facilities;
- relocate a small facility group while preserving its external boundary terminals;
- pack a bounded region more tightly;
- determine that one precisely defined local arrangement is impossible.

An oracle request contains a finite neighborhood, immutable boundary conditions, an objective, and a resource budget. An oracle result is one of feasible candidate, locally proven impossible, or unknown. `Unknown` leaves the current layout unchanged.

Local solver candidates are never trusted directly. They must be integrated into a copy of the current layout and pass full validation before acceptance.

## Iterative Improvement

Improvement passes include:

- compact a facility region;
- reroute one or more networks;
- relocate a facility or small facility group;
- merge compatible trunks;
- introduce a legal crossing when it reduces the score.

Each pass is transactional:

```text
clone current best
-> apply one bounded mutation
-> repair affected routes
-> validate complete factory
-> compute score
-> accept only if valid and better
```

The initial score order remains lexicographic:

1. used bounding-box area;
2. physical belt and pipe tile count;
3. total route turns;
4. later stable tie-breakers.

The report records the initial score, every accepted improvement, rejected-attempt counts by reason, elapsed budget, and final score.

## Failure And Diagnostic Contract

Diagnostics must identify the stage and the smallest useful entity scope. Initial stable categories are:

- invalid input;
- facility construction exhausted local candidates or resource budget;
- port assignment failed;
- commodity-network synthesis failed;
- pipe routing failed;
- belt routing failed;
- derived component placement failed;
- complete validation failed;
- local oracle unknown;
- locally proven impossible;
- improvement rejected because it was invalid;
- improvement rejected because it did not improve the score.

Partial construction state may be included for HTML diagnostics, but a partial factory must never be returned as a successful blueprint.

## Rejected Alternatives

- The global joint placement-routing model is rejected as the production generator because it did not produce useful complete layouts at the target scale within practical budgets.
- Separating placement and routing into unrelated final phases is rejected. Initial placement must deliberately provide routing clearance, and improvement passes may relocate facilities when routes cannot be repaired.
- Reporting a constructor failure as global infeasibility is rejected.
- Deleting the exact solver is rejected. It remains valuable as isolated research tooling.

## Implementation Slices

1. Build one minimal vertical slice: seed facility, one upstream facility, one assigned pipe connection, and one validated physical route.
2. Repeat the same growth contract across a pipe-only chain and expose every accepted state in the report and HTML history.
3. Extend an existing same-commodity pipe tree instead of creating independent point-to-point routes. If the representative graph has no internal pipe branch, begin the belt frontier attached directly to the completed pipe region.
4. Grow all pipe frontiers in a representative production graph.
5. Add belt frontiers and derived split/merge components to produce the first complete factory.
6. Isolate old exact APIs behind explicit research entry points and cut normal production commands over once the constructive path produces complete results.
7. Add bounded rip-up-and-reroute.
8. Add transactional improvement history and the first reroute/relocate passes.
9. Add the first bounded local CP oracle only after a concrete local blocker is measured.

## First Implementation Slice

Implement a controlled two-facility pipe fixture end to end. Place a seed facility, place its directly connected upstream supplier, select one compatible directional port on each facility, route one legal pipe path, validate the resulting covered subgraph, and report the accepted growth state. This slice must not include unrelated production-graph traversal, belts, splitters, rerouting, or optimization.

This first controlled slice derives a temporary local search canvas from the two facility footprints and reports only the resulting used geometry. The canvas is an implementation detail of A* and candidate enumeration, not a production W/H constraint.

The slice accepts the first feasible transaction and only measures its geometry. Candidate optimization begins after growth exposes future requirements. Its comparison is lexicographic rather than an arbitrary weighted sum:

1. minimize actual used bounding-box area;
2. minimize occupied transport tiles;
3. minimize route turns;
4. use remaining viable port-option count only as a stable late tie-breaker.

A candidate that leaves any currently represented uncovered requirement with no viable compatible
port option is rejected before scoring. This edge-level boundary rule is an interim conservative
contract. The target contract groups demand by facility, direction, item, and transport capacity;
unused catalog ports do not need to remain usable. This ordering is a constructive preference, not
a proof of global optimality; bounded local backtracking must still recover when a preferred
candidate blocks later growth.

## Pipe-Chain Growth Result

The second implementation slice grows the longest simple facility-to-facility pipe chain in output-first order. Every accepted page contains the cumulative placements and routes, while the newly introduced facility is highlighted. Existing facility and pipe geometry are immutable obstacles during the next local candidate search.

The real Heavy Xiranite graph exposes a three-facility, two-requirement pipe chain. Construction succeeds in two routed transactions. The result also demonstrates that preserving future port feasibility does not imply a short later route: a compact row can leave the required port usable while forcing the next pipe around an intervening facility. This is accepted initial-construction behavior. Physical transport is cheap, so compact factory area remains more important than route simplicity; relocate/reroute work may improve the route only without enlarging the factory.

## Immediate Belt-Frontier Growth Result

Heavy Xiranite has no additional facility-to-facility pipe requirement after the two-edge chain. Its remaining pipe requirements are external inputs or surplus outputs, which the planner marks but does not physically route. The next cumulative slice therefore adds the three belt suppliers connected directly to the completed pipe region.

The resulting five transactions contain six facilities, two pipe requirements, and three belt requirements. Belt and pipe occupancy are validated independently, so the two transport layers may legally share a world coordinate while neither may overlap a facility. The final used bounds are `32x7`, with 3 pipe tiles and 13 belt tiles.

The initial implementation exposed a construction-cost cliff: the release run performed 423,294 A* searches and took 62.13 seconds. Candidate evaluation now runs across scoped worker threads and shares the best proven area through an atomic incumbent. A candidate is skipped only when its facility-only or endpoint-inclusive bounding-box area lower bound is already strictly worse than that incumbent. This preserves the candidate set at the best area while avoiding unnecessary path search.

On the same five phases and the same final geometry, the parallel bounded run takes 0.62 seconds and performs 874 A* searches. Sixteen workers reject 56,773 placements and 2,588 endpoint pairs before routing. Exact endpoint-route memoization records zero hits, showing that safe incumbent pruning rather than caching supplies the improvement.

## Second Belt-Frontier Ring Result

The frontier-growth command now accepts an explicit cumulative belt depth. Depth two selects eleven internal requirements and attempts to grow twelve facilities. The Heavy Xiranite run completes nine requirements and ten facilities before exhausting the current committed prefix. Its last valid page is `39x8`, with 26 belt tiles and 3 pipe tiles.

The failed tenth phase performs 130,552 A* searches; only 14 find a physical path, and all 14 fail the exact future-port viability check. The run takes 113.96 seconds in release mode while using sixteen workers. This is a constructive dead end, not proof that the complete factory is impossible.

The result demonstrates that a single frozen chronological prefix is insufficient. Blind chronological backtracking is not adopted: the measured candidate fan-out would repeatedly replay an expensive suffix. The next experiment instead gives a small production subgraph a longer planning horizon, freezes the completed subgraph as a process module, and connects modules through explicit boundary interfaces.

## Process-Module Experiment Contract

The first hierarchical experiment replaces immediate chronological backtracking with an independently constructed process module. Its request identifies one facility-instance root and one facility-supplied input item. The selected internal subgraph contains the root and every facility instance directly supplying that item to the root. This explicit selector is an experiment input, not an automatic production-graph decomposition rule.

The module output contains:

- the member facility instances and internal logical requirements;
- a validated placement and routed internal transport network for every selected requirement;
- the actual used bounds and construction history;
- every logical edge crossing the member boundary;
- for each boundary edge, every currently exposed compatible facility-owned port with item, rate, transport, direction, position, and connection cell.

A successful module must route every selected internal requirement, preserve facility and same-layer transport occupancy rules, and expose at least one physical port option for every boundary requirement. Boundary requirements are interface domains and are not externally wired during module construction. The visualizer renders their arrows without counting them as transport tiles.

The first Heavy Xiranite module contains one Xiranite-powder oven and its two enriched-carbon furnaces. It completes in 0.62 seconds at `9x7`, using four internal belt tiles. Four boundary requirements remain exposed: two enriched-carbon-powder inputs, one clean-water input, and one Xiranite-powder output. This validates the black-box interface concept but does not prove local area optimality or yet deploy multiple modules as immutable macros.

## Recursive Composition Contract

Facilities and process modules implement one recursive constructive-node contract. A leaf facility is a node with one placement, no internal route, and a boundary domain for each incident unresolved logical edge. A process module is a node with multiple placements and routed internal requirements. A composite is itself another node with the same fields:

```text
ConstructiveNode
  exact occupied geometry
  member facility instances
  completed internal requirements
  immutable internal transport networks
  unresolved boundary requirements and port-option domains
```

`compose(source, target, requirement)` applies rigid transforms to the complete source node, selects one compatible source and target boundary option, routes the selected requirement, validates physical occupancy, removes the completed boundary, and returns another `ConstructiveNode`. A rigid transform updates facilities, internal routes, terminals, and every remaining boundary option together. The operation does not reopen or reconstruct either input node's internals.

Collision uses the exact occupied mask, not the node's rectangular bounds. Facility cells block both transport layers. Same-layer routes conflict, while belt and pipe remain independent layers. Every still-unresolved boundary must retain at least one usable port option before a candidate may be accepted.

The first real recursive composition connects the three-facility Xiranite-powder module to the final Xiranite oven. It produces four facilities and three routed requirements in `14x8`, using nine belt tiles and zero turns in 0.61 seconds. The source module's two original routes remain unchanged. This proves that one module can be deployed as a black-box node through the same local placement-and-routing operation used for leaves. It does not yet provide automatic graph partitioning, node cloning, or full-factory recursive assembly.

## Repeated Recursive Assembly Result

The assembly harness accepts a target facility and an ordered list of process-module requests. It constructs each module independently and repeatedly applies the generic composition operation against the current composite. A successful result from one step is therefore the unchanged target node of the next step; there is no separate macro-placement implementation.

The first Heavy Xiranite assembly attaches both three-facility Xiranite-powder modules to the final oven. Both steps succeed in 2.03 seconds total. The final composite contains seven facilities and six routed requirements in `22x9`, with 25 belt tiles and zero turns. Eight unresolved logical boundaries retain eighteen physical port options.

This demonstrates recursive closure of the constructive-node contract across two real growth levels. The harness still receives an explicit module list and order. Automatic production-graph decomposition, shared-subgraph ownership, mixed belt/pipe module selection, cyclic subgraphs, and exhausted-composition recovery are not yet implemented.

## Automatic Module Discovery Result

The first automatic discovery harness removes module roots, internal items, wiring requirements, and assembly order from the caller contract. Given a seed target and a step budget, it enumerates every unresolved facility-supplied input, derives one local process-module candidate for each distinct directly supplied input item of that producer, constructs and composes every candidate, and accepts the best valid result by the constructive score.

On Heavy Xiranite, two automatic steps evaluate three candidates each and succeed in 5.28 seconds. The planner first selects the two-facility liquid-Xiranite-poly process and then follows that branch upstream into a three-facility Xiranite-powder process. The mixed belt/pipe result contains six facilities and five routes in `27x8`, with 23 belt tiles and 12 pipe tiles. Four facility-supplied boundaries remain because the request intentionally stops after two growth steps.

This rule currently requires the candidate root to have a direct facility-supplied input item. Leaf producers, SCC modules, shared upstream ownership, and automatic recovery from an exhausted candidate set remain unsupported. The next experiment increases only the automatic step budget to identify which unsupported frontier appears first.

## Parallel Automatic Discovery Result

Automatic discovery candidates are independent until the winner is selected. Their whole-node composition is therefore evaluated concurrently, while module preparation and final score ordering remain deterministic. The planner still evaluates every candidate and uses the same score and tie-break tuple; concurrency changes wall time only.

On the Heavy Xiranite graph, the sequential implementation failed to finish the third attachment in 139.62 seconds. Concurrent candidate composition completed six attachments in 61.49 seconds, producing a valid 15-facility, `53x11` partial factory with 14 routed internal requirements. Per-step composition cost still rose from 0.667 seconds to 19.029 seconds as both the target block and frontier grew. Whole-node composition, rather than module discovery coverage, is the next measured constructive growth bottleneck.

## Dense Route Workspace Result

Sampling showed that repeated A* calls and routing-state SipHash dominated whole-node composition. Each search allocated hash maps for a small bounded `(x, y, heading)` state space. Composition now reuses one dense, generation-stamped routing workspace per candidate. This preserves shortest-path and turn ordering and does not remove any placement, port, or route candidate.

The six-step Heavy Xiranite run falls from 61.49 seconds to 26.72 seconds with an identical report after excluding elapsed-time diagnostics. Existing composite geometry was already immutable: only the new source node receives a rigid transform and one connecting route. A future additive optimization should therefore use adjacent placements to establish an early incumbent and apply sound lower-bound pruning, rather than freezing or moving the existing factory differently.

## Additive Shared-Bound Result

Composition now evaluates adjacent rigid placements first and publishes the best zero-blocked area across automatic-discovery workers. A placement whose facility-and-existing-route union area already exceeds that bound is rejected before A*. The route can only preserve or enlarge this geometry, so the reduction is sound. Equal-area candidates remain active, and canonical candidate ordering preserves deterministic ties.

The six-step Heavy Xiranite run falls again from 26.72 seconds to 8.45 seconds, with an identical final node and selected score sequence. Winning-composition A* calls fall from 78,818 to 35,468. Step four remains a 7.021-second outlier because every successful candidate loses at least one boundary-port option, so no zero-loss area incumbent exists. A lower bound for unavoidable boundary-option loss is the next measured pruning target.

## Area-First Objective Correction

The apparent boundary-option bottleneck exposed a contract error rather than a missing lower bound.
An unused catalog port may be blocked or ignored. Preserving optional ports therefore cannot outrank
factory compactness. Composition schema version 3 orders candidates by used bounding-box area,
transport tiles, route turns, and only then blocked optional boundary choices.

Because area is now the first score component, every valid candidate can publish its area as a
shared incumbent. A placement whose facility-and-existing-route area lower bound is already larger
than that incumbent is rejected before A*, independent of optional-port loss. On the same six-step
Heavy Xiranite request, the warm release run falls from 8.45 seconds to 0.84 seconds. Selected
composition A* calls fall from 35,468 to 1,832, and final partial-layout area falls from `53x11 =
583` to `42x11 = 462` while growing from fifteen to sixteen facilities.

All fourteen currently represented unresolved edge boundaries still retain at least one physical
option, so the interim validity check passes. This does not establish the correct number of ports.
The next contract slice must load transport line capacity and replace one-boundary-per-logical-edge
reasoning with capacity-grouped port demands. For each facility, direction, item, and transport
group, the required number of selected ports is `ceil(total rate / line capacity)`; extra catalog
ports may be unusable without penalty.

## Capacity-Grouped Port Demand Result

Automatic assembly now loads the runtime transport catalog and emits a separate port-demand
analysis without yet changing candidate validity. Boundary requirements are grouped by facility,
direction, item, and transport. The report compares the old one-port-per-edge implication with the
exact capacity count, reports distinct currently usable port choices per facility scope, and audits
already routed networks against one-line capacity.

The six-step Heavy Xiranite partial factory has fourteen unresolved edge boundaries and fourteen
capacity groups. No same-item boundary edges merge in this particular frontier. Capacity still
requires sixteen ports rather than fourteen: two belt input groups each carry `1 item/s`, while the
catalog belt capacity is `1/2 item/s`, so each group requires two lines. Every affected facility
scope currently exposes enough distinct port choices, but the interim edge-boundary contract does
not reserve both required ports.

The audit also finds one already routed plant-moss-powder belt at `1 item/s`. It requires two
parallel belt lines but the current constructor embedded one. Therefore the reported geometry is a
successful result only under the interim constructive validator; it is not valid under the accepted
transport-capacity contract. The next implementation slice must split requirements into the minimum
number of capacity-bounded lanes before port selection and routing, then permit compatible same-item
lanes to synthesize a shared commodity network.

## Capacity-Bounded Lane Construction Result

Constructive routing now loads the runtime transport catalog in every command that can create
transport geometry. Before selecting ports, each logical requirement is split into the minimum
number of positive lanes whose individual rates do not exceed one belt or pipe line. Those lanes
are routed as one atomic transaction with distinct source and target ports and disjoint same-layer
cells. A candidate is accepted only if the remaining boundary requirements still have sufficient
capacity-grouped port choices.

The previously invalid `1 item/s` plant-moss-powder belt is now constructed as two `1/2 item/s`
lanes using two distinct source ports and two distinct target ports. The controlled module occupies
`6x7`, uses four belt tiles, and completes in `0.01` seconds. The Heavy Xiranite six-step regression
again places sixteen facilities in `42x11`; its final capacity audit reports zero over-capacity
networks.

This is still a point-to-point lane implementation. Compatible same-item requirements are not yet
merged into the trunk/tree network required by the final architecture. Higher lane counts may also
require streaming candidate scoring rather than materializing every valid lane bundle. These are
constructive planner improvements, not reasons to weaken the capacity contract.

## Capacity-Valid Growth Cliff

A twelve-step Heavy Xiranite probe accepts eleven growth steps and reaches 28 facilities in
`68x16`, then exhausts all eight generated frontier candidates. Six candidates enter composition
and perform 505,325 A* calls. Of those, 216,173 find no route. Another 186,951 complete lane bundles
are rejected by the interim rule that every unresolved logical edge must retain its own unused port
option. No complete bundle reaches the grouped-capacity rejection or geometry rejection paths.

The result confirms that the edge-local boundary DTO now conflicts with the accepted commodity
network architecture. Compatible same-item requirements may share a facility port and trunk while
capacity permits, but an unresolved boundary can currently reference only unused facility ports.
The next contract slice must represent attachment to an existing compatible network and its
residual capacity before removing the conservative per-edge rule. Simply deleting the rule would
hide a constructor capability gap instead of implementing the shared-network semantics.
