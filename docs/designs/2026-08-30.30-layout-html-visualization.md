# Layout HTML Visualization

## Status

Implemented for successful integrated layout reports, including paginated iterative SCC histories.

## Purpose

Solver diagnostics and aggregate route counts cannot distinguish a compact logical layout from a valid witness with excessive detours. A spatial wireframe is required for manual solution-quality review and routing debugging.

## CLI Contract

Both `layouts solve` and `layouts solve-contextual` accept:

```text
--visualization-output <FILE>
--localization-catalog <FILE>
```

The localization catalog is optional and may only be supplied with a visualization output. When present, facility labels use localized facility names and item details show the localized name with the stable ID. Missing localization entries retain the stable ID according to the localization fallback rule.

When the solve succeeds, the CLI writes a standalone HTML document to the requested path in addition to writing the unchanged machine-readable JSON report to standard output. Failed layouts do not produce a misleading wireframe.

File write failures identify the requested output path.

## Rendering Contract

The document contains an SVG wireframe with:

- facility footprint rectangles with the full facility ID and a short stable instance label;
- belt routes as amber `1x1` occupied-cell tiles;
- pipe routes as blue `1x1` occupied-cell tiles;
- route endpoint markers, including distinct boundary endpoints;
- bridge, splitter, and converger markers;
- one-cell and ten-cell grid lines;
- hover titles containing full facility, recipe, item, endpoint, and route details.

Facility input ports use large circular markers and facility output ports use large diamond markers. Boundary terminals use square markers. Hovering a route tile or port opens an in-view details panel immediately; clicking pins that selection until it is closed or another target is selected. Route details include transport kind, localized item name and ID, exact rational rate with a decimal approximation, both endpoints, and occupied tile count. Port details include its input/output role, item, rate, exact port endpoint, and peer endpoint. The viewer does not rely on browser-native SVG title tooltips.

The toolbar reports used bounds, facility count, occupied transport-tile count split by belt and pipe, and bridge count. Logical route-line counts are intentionally omitted because they are an internal decomposition detail rather than an installation quantity. Belt, pipe, component, and label layers can be toggled independently. Pointer drag pans the SVG, the wheel zooms around the pointer, and reset restores the full used layout bounds.

When `IntegratedLayoutReport.phases` is populated, the viewer renders one page per successful cumulative SCC phase and opens on the authoritative final phase. Previous and next controls move through the growth history. The toolbar updates its metrics and view bounds for the selected phase, reports the selected anchor radius and route turns, and highlights facilities introduced by that phase in green. A report without phase history remains a single-page layout.

The generated file has no local asset dependencies, server calls, or build-time runtime requirements. It may be opened directly or served as a static file. The renderer escapes all report text before including it in SVG titles.

## Diagnostic Boundary

The visualization is a review surface, not a validity proof. The integrated witness validator remains authoritative for bounds, overlap, endpoint, layer, crossing, and route continuity constraints.
