# Layout HTML Visualization

## Status

Implemented for successful reports and failed reports with completed phase snapshots, including paginated iterative SCC histories.

## Purpose

Solver diagnostics and aggregate route counts cannot distinguish a compact logical layout from a valid witness with excessive detours. A spatial wireframe is required for manual solution-quality review and routing debugging.

## CLI Contract

Both `layouts solve` and `layouts solve-contextual` accept:

```text
--visualization-output <FILE>
--localization-catalog <FILE>
```

The localization catalog is optional and may only be supplied with a visualization output. When present, facility labels use localized facility names and item details show the localized name with the stable ID. Missing localization entries retain the stable ID according to the localization fallback rule.

Facility labels retain their natural glyph proportions when the estimated text width fits the footprint. `textLength` compression is applied only when a label would otherwise overflow; short localized names must never be expanded to fill the facility width.

When at least one renderable layout snapshot exists, the CLI writes a standalone HTML document to the requested path in addition to writing the unchanged machine-readable JSON report to standard output. A failed iterative solve renders every completed phase, marks the document as a failed partial history, and opens on the last valid snapshot. A failure before any snapshot exists returns `layout-visualization-has-no-snapshots` instead of writing an empty or misleading wireframe.

File write failures identify the requested output path.

## Rendering Contract

The document contains an SVG wireframe with:

- facility footprint rectangles with the full facility ID and a short stable instance label;
- belt routes as amber `1x1` occupied-cell tiles;
- pipe routes as blue `1x1` occupied-cell tiles;
- route endpoint markers, including distinct boundary endpoints;
- bridge, splitter, and converger markers;
- one-cell and ten-cell grid lines;
- click-selected details containing full facility, recipe, item, endpoint, and route information.

Facility ports use flow-oriented arrowheads. Input arrows use a green outline and always point from the connection cell into the facility footprint. Output arrows use a pink outline and always point from the facility footprint toward the connection cell. Their fill retains the belt or pipe transport color. Port direction is derived from the connection cell's position relative to the placed facility, never from the final route segment. Belt and pipe routes contain periodic arrowheads derived from the ordered route cells.

Clicking a route tile, port, facility, or logistics component opens and pins an in-view details panel until it is closed, an empty area is clicked, or another target is selected. Pointer movement below five screen pixels remains a click; larger movement pans the view. Selection styling changes only the selected geometry's stroke and opacity; it must not apply an SVG filter to a whole route group. Route details include transport kind, localized item name and ID, exact rational rate with a decimal approximation, both endpoints, and occupied tile count. Port details include its input/output role, item, rate, exact port endpoint, and peer endpoint. The viewer does not use hover behavior or browser-native SVG title tooltips.

The toolbar reports used bounds, facility count, occupied transport-tile count split by belt and pipe, and bridge count. Logical route-line counts are intentionally omitted because they are an internal decomposition detail rather than an installation quantity. Belt, pipe, component, and label layers can be toggled independently. Pointer drag pans the SVG, the wheel zooms around the pointer, and reset restores the full used layout bounds.

When `IntegratedLayoutReport.phases` is populated, the viewer renders one page per completed cumulative SCC phase and opens on the authoritative final or last-valid phase. Previous and next controls move through the growth history. The toolbar updates its metrics and view bounds for the selected phase, reports route-score delta, reused routes, moved facilities, prior placement hints, and route turns, and highlights facilities introduced by that phase in green. The final full-graph refinement is labeled separately. A report without phase history remains a single-page layout.

The generated file has no local asset dependencies, server calls, or build-time runtime requirements. It may be opened directly or served as a static file. The renderer escapes all report text before including it in SVG titles.

## Diagnostic Boundary

The visualization is a review surface, not a validity proof. The integrated witness validator remains authoritative for bounds, overlap, endpoint, layer, crossing, and route continuity constraints.
