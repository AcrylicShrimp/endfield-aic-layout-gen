# Physical action outcome pretraining and PPO integration

Status: integration objective accepted; the bounded
[I/O readiness gate](../plans/2026-09-15.06-integrated-io-learning-readiness.md)
is complete. The [gate report](../reports/2026-09-15-integrated-io-readiness.md)
records passing end-to-end contracts and a negative short cold-PPO screen. That
result leaves long training paused but clears the interface uncertainty that
blocked the first common-editor extraction slice. The I/O corrections in plans
00–05 are implemented. This document uses their native observation, action,
identity and checkpoint contracts; the historical
[I/O audit](../reports/2026-09-15-learning-io-audit.md) explains the replacement.
Generator optimization remains postponed. This design does not record completed
pretraining collection or authorize an unattended long run. The common physical
editor extraction is complete at revision `caf5893`; the shared numerical feature
boundary is the current integration slice.

## Objective and evidence

Learn useful geometric representations by predicting what the actual editor does
with a state and a fully specified action. Transfer those representations into
the existing PPO learner and test whether they improve area reduction. The target
is the environment's observed outcome under its declared work budget, not the
generator's original placement, an optimal layout, or global routability.

The [procedural generator](2026-09-15.00-procedural-layout-generation.md) already
publishes complete `aic-physical-layout-v1` examples. Its
[224-case evaluation](../reports/2026-09-15-procedural-layout-generation.md)
demonstrates physical validity and substantial size-dependent acceptance bias.
The new source reduces dependence on the old construction pattern; it does not
establish similarity to player layouts.

The [masked PPO comparison](../reports/2026-09-14-cold-masked-ppo-comparison.md)
showed an overall benefit but no demonstrated additional learning benefit for
large factories. It also showed frequent unfinished drafts despite improved valid
bests. Consequently the proposed dataset must include unfinished intermediate
states, and outcome prediction alone cannot establish long-horizon improvement.

## Existing implementation and the actual mismatch

The native declarative editor already owns joint placement/rotation/port actions,
band insertion/deletion, transactional automatic repair, full acceptance and valid
best retention. Its blueprint includes facility terminals, external anchors and
component channels, with fixed directed edges and exact flow rates. The procedural
format describes blocks, pairwise connections, complete paths and bridges. It
cannot directly impersonate a recipe-bound `FactoryEditRequest`/witness.

Relevant implementation authorities:

- `crates/aic-pilot-native/src/full_factory/blueprint/{topology,geometry}.rs`:
  chain decomposition, reconstruction, path checking and repair.
- `crates/aic-pilot-native/src/full_factory/blueprint/declarative{,/edit}.rs`:
  state changes, retained drafts, acceptance, scoring and resource charging.
- `crates/aic-pilot-native/src/full_factory/blueprint/declarative/learning/`:
  native candidate order, features, port domains and retained selection handles.
- `crates/aic-learning/src/model.rs`: width-40, two-round graph encoder, root,
  conditional-port and value heads; packed routing-cell inputs.
- `crates/aic-learning/src/{collection,training}/`: persistent collection,
  PPO/SIL, 80/10/10 curriculum, evaluation separation and actual-state recovery.

The implemented numerical widths are node 41, edge 37, global 15, root action 12
and port 11 (`declarative::learning::schema`). Observations contain typed physical
properties, exact commodity equality relations, directed paths, selected and
available ports, component channels, current and baseline route restrictions,
and finite work/decision allowances. Opaque ID fingerprints and wall time are
absent. Recipe obligations remain with the factory compiler; their physical
consequences, including utilization-adjusted rates, remain observable.

## Common state and ownership

Use one physical edit implementation with two admission/export boundaries.

```text
validated procedural Layout ── physical compiler ──┐
                                                 ├─ compiled problem + draft
validated factory request/witness ─ factory compiler┘           │
                                                     common native editor
                                                              │
                                               shared features + action domain
                                                    │                   │
                                             outcome pretraining     existing PPO
```

`aic-layout` owns typed compiled physical data in addition to its existing
complete-layout interchange. The compiled representation includes:

- Fixed blocks: stable identity, catalog facility and available rotations/ports.
- Fixed networks: opaque commodity-equivalence identity and transport; identity
  equality remains exact even when names are absent from learned features.
- Fixed nodes: facility terminal, external anchor or component channel; endpoint
  direction, exact demand, block/component ownership and channel association.
- Fixed edges: stable identity, network, source/target nodes, exact rate,
  component-facing direction restrictions and permitted zero-length semantics.
- Fixed component identities/definitions/rotations and channel ownership.
- Mutable draft: block poses, complete selected terminal-to-port mapping, anchor
  and component positions, and an optional path for every fixed edge.

A draft is a distinct type from a complete validated `Layout`. An absent route or
overlap is observable pending work, not permission to omit its obligation.
Recipe selection, utilization, product request and original production evidence
remain in the factory admission owner. They are immutable and are retained for
the existing full factory acceptance/export contract.

The new physical admission compiler splits procedural paths at their declared
bridge channels. The two crossing channels have separate node identities even
at the same coordinate; they cannot become a junction. Preserve the ordered
mapping from each published connection to its compiled edge segments so export
reconstructs that exact obligation. Coincident endpoints and adjacent components
require explicit zero-length/direction handling. Validate compilation by exact
directed segments, rates, port bindings and bridge usage, not just total area.

Keep the existing procedural interchange intact. Lowering two real input formats
once at admission is necessary source compilation, not a hot-loop DTO adapter.
There is no fabricated recipe, item catalog, utilization or external terminal.
Existing factory decomposition rejection conditions remain explicit; this work
does not claim to support every graph representable by arbitrary external input.

Extract the common editor inside `aic-pilot-native`, using `aic-layout` types and
the already shared `aic-routing` kernel. Reuse the actual implementation rather
than writing a procedural-only simulator. Factory-specific admission/export and
acceptance remain at their boundary. Keep acceptance at its current meaningful
frequency: changed, complete, conflict-free candidates. Do not add a second full
audit on every step or weaken the existing full factory validator.

Original components, including generated bridges, become fixed obligations for
this experiment, just as in the current editor. Band edits move them according to
the existing rules; placement edits cannot remove them. Free bridge relocation,
new junctions or topology changes would define a different action experiment.

## Shared actions, features and outcomes

Preserve all three current action families and their semantics:

| Action | Complete decision | Invariant |
| --- | --- | --- |
| place | Block, x/y, catalog rotation, joint mapping for every original terminal | No duplicate/incompatible ports or lost demand |
| insert_band | Axis, coordinate, positive width | Shift rigid entities without slicing them |
| delete_band | Axis, coordinate, positive width | Remove no block, component, anchor or obligation |

Retain native root order, structural band masks, conditional without-replacement
port selection and stale/foreign-handle rejection. Retain valid syntactic edits
when routing fails, transactional repair, pipe-first pending-edge order, shared
per-action work accounting and lexicographic valid-best scoring. An unchanged
edit consumes a decision without repeating routing or validation. Do not use
predicted feasibility as a hard mask or replace actual acceptance with a model.

Use the single implemented physical feature builder and native candidate authority.
Geometry is expressed in the occupied working frame, including unfinished paths
and overlaps. Signed proposals and symmetric repair padding preserve translations;
physical admission order preserves opaque-renaming equivalence. Preserve the exact
terminal-to-port mapping and its terminal-bound nonlinear prefix encoder. The root
policy divides by available family counts before masked normalization; conditional
port factors remain without replacement and contribute to the joint likelihood.

There is no legacy feature profile, zeroed-column adapter or parallel builder.
The native physical snapshot format is `declarative-edit-checkpoint-v4`, local edit
format is `declarative-edit-v2`, and learned training checkpoint version is
`aic-training-checkpoint-v8`. Use the existing single format version and settings
binding for learned compatibility; do not add separate component semantic IDs.
Old learned tensors, optimizer moments and feature replay require a cold restart.
Compatible actual physical snapshots can be cold-converted at the documented
native boundary without claiming old-policy or optimizer continuation.

The initial experiment uses one fixed catalog/budget configuration. It makes no
generalization claim across unseen transport capacities. Work allowances and
remaining decision/episode routing budgets are explicit outcome conditioning;
the same values apply when comparing predictions to executed outcomes. Wall
deadlines, cancellation and process failure are censored observations, not routing
negatives or learned time features.

Each training record refers to the owned **pre-action** input and the selected
complete action, followed by the measured outcome. Record status, pending/conflict
counts, charged routing work and actual candidate metrics when available.

| Observed outcome | Completion target | Geometry target |
| --- | --- | --- |
| Changed, complete and accepted; improved or non-improved | 1 | Actual current candidate area, transport tiles and turns |
| Changed, unfinished after the declared route budget/search | 0 for completion under this budget | Missing; regression loss masked out |
| Overlap preventing completion | 0 | Missing; never the retained best's area |
| Syntactic rejection or unchanged action | Retain separate status; omit from the main changed-action loss | Omit |
| Deadline, cancellation, internal validation invariant failure | Censored/error, separately counted | Omit |

Preserve router substatuses. Fixed-query `no-path`, search exhaustion and an
unfinished draft are not global problem infeasibility. A completed candidate that
is worse than the retained best remains a valuable positive completion example.
Never give failed drafts area zero, substitute best metrics for current metrics,
or include post-action routes/metrics in the input.

## Pretraining and transfer

Reuse the model's `nodes`, `edges`, `paths`, `messages`, `updates`, `context` and
terminal-bound `port_pair` parameters as the shared state-action encoder. Add
small disposable heads over one common state-action embedding. The action representation
must include its complete port assignment: bind each chosen port's physical
features to its terminal node embedding before aggregation, include assignment
count, and include the selected root features. Averaging unassociated port
coordinates would lose which demand was assigned where.

Encode each state once and batch selected action/terminal rows. The first fixed
multi-task target set is:

| Head | Target and loss | Label mask |
| --- | --- | --- |
| Completion under budget | Binary cross-entropy for a changed, complete candidate | Changed, physically observed actions only |
| Outcome flags | Independent binary cross-entropies for `changed`, `pending`, `conflict`, `unchanged`, and `rejected` | Every uncensored charged action; post-action state flags only when that state was observed |
| Pending/conflict | Two `log1p` count regressions | Changed actions with an observed post-action draft |
| Candidate area | Normalized score-component regression | Complete candidates only |
| Candidate transport tiles | Normalized score-component regression | Complete candidates only |
| Candidate turns | Normalized score-component regression | Complete candidates only |
| Routing budget exhaustion | Binary cross-entropy for exhausting the declared per-action routing allowance | Changed, uncensored actions |

The completion and outcome-flag targets are related but intentionally distinct:
the completion head supplies a calibrated downstream decision signal, while the
flags preserve simultaneous failure causes without arbitrary precedence. Map
native `validated` and `improved` to completion `1`; map an observed changed
`draft_accepted` state to completion `0`; and exclude deadline, cancellation,
process failure and internal-invariant failure from every outcome loss. A changed
action sets `changed`; `pending` and `conflict` are independent post-action-state
flags and may both be set. `unchanged` and `rejected` retain their native meanings
and do not fabricate a post-action state. Do not add an exact routing-work
regression in the first screen because exhausted searches are right-censored.
Keep each disposable head to one affine projection from the common embedding; a
large private head would weaken the pressure on the shared representation.

Normalize candidate metric targets by the initial valid layout's corresponding
score components (denominator at least one), and normalize pending/conflict counts
with `log1p` and the registered count scale. Compute each component loss as a mean
over its own valid labels before applying fixed configuration weights; an absent
label contributes neither a zero target nor a denominator. Keep per-head losses,
label counts, validation metrics and shared-encoder gradient norm observable.
Reject a batch with no primary completion/outcome labels, while allowing a masked
auxiliary head to have zero labels. Fix heads and weights in the experiment
configuration before training. Report area separately; auxiliary targets do not
change PPO's area-first goal.

The first transfer copies only the shared encoder tensors named above. Initialize root, port and
critic heads from the same cold tensors as the paired control. Start with empty
PPO Adam/replay and identical owned RNG seeds; pretraining optimizer moments and
the prediction head are not PPO state. Fine-tune the encoder through ordinary
PPO/SIL from the first update. Do not introduce freezing schedules, auxiliary
online losses, predicted rollout planning or behavior cloning in the first test.

The new heads still need to learn how to use the representation. The hypothesis
is faster/better learning, not immediate zero-shot control. A successful outcome
predictor is a prerequisite measurement, not proof that PPO benefits.

## Bounded data and comparison protocol

First establish source/editor parity before collecting the study dataset. Use
retained procedural and factory examples for this integration gate, including
bridges, branching, external anchors, immediate port turns, incomplete drafts
and separate-process restore. Existing viewed examples are engineering evidence,
not an untouched confirmation set.

The first supervised screen uses 96 newly generated roots with fixed block counts:
48 at eight blocks and 48 at sixteen. Within each size, allocate 32 training,
eight development and eight confirmation roots **before** collecting actions.
Use the generator's existing default settings with only fixed size overridden;
record bounded failures rather than substituting a smaller case. All descendants,
perturbations and reordered copies of a root stay in its split. Persist the split
manifest and reject cross-split structural physical identities and root ancestry
at admission. Reuse `aic-physical-identity-v1`: structural keys reserve equivalent
geometry/incidence independently of rates; exact keys additionally bind rates and
catalog constraints. Compute them at admission/publication under the configured
individualization budget. Retain exact source hashes separately for loading and
recovery; resource exhaustion cannot certify split separation.

Collect one sequential trajectory of at most 32 decisions per root (at most 3,072
records). Sample action families equally among available unmasked families,
then roots within that family; for placement, mix retaining compatible existing
ports with random compatible complete assignments at 1:1. Use separate recorded
action seeds. Keep unfinished drafts so later actions can recover them. Do not
filter trajectories on eventual improvement or repeatedly restore every proposal
from the original state. This is a small coverage screen, not the final corpus.

Use four persistent workers, the existing 50,000 per-action route expansion limit,
and explicit cumulative native and command limits. Cap the initial collection at
15 minutes and 4 GiB output; an incomplete screen reports achieved coverage and
stops. Register actual seeds, sizes, loss weights, epoch count and model settings
in external run configuration before execution. Size/port/action-family and
complete/pending coverage determine whether enough labeled cases exist; do not
claim accuracy for a stratum containing only one outcome class.

Measure held-out completion calibration/discrimination and per-root metric
errors, with constant-rate and simple geometric-feature baselines. Break results
down by size, action family and complete versus pending input state. Confirmation
is used once after the fixed training/development procedure. Split and aggregate
by root, not by correlated action rows. Learnability on this source is the limit
of the supervised claim; production/player transfer is a separate measurement.

After those gates, compare three matched short PPO arms:

1. Existing features, cold initialization: the retained baseline.
2. Physical features, cold initialization: effect of the feature change.
3. Identical physical features, pretrained encoder: additional pretraining effect.

Use the same existing recipe-bound production source, fresh-slot identities,
80/10/10 curriculum, masks, native budgets, PPO/SIL settings and held-out factory
panel. Preserve external/component coverage in this evaluation. Do not replace
the PPO source and pretrain the encoder simultaneously in the primary comparison.
Match fresh inputs and curriculum rules; policy-dependent inherited states will
legitimately differ. Reserve the evaluation geometries from every training source.

The initial downstream screen is two paired initialization seeds, 32 streams,
32 actions per chunk, 64-action episodes and 32 updates per arm. That is 32,768
new transitions per arm/seed, 196,608 across six runs. The final update is the
comparison endpoint; development checks at 0/16/32 do not select confirmation
results. Use a fresh balanced small/large confirmation panel with common action
seeds. Register its exact inputs and runtime/storage ceiling after the integrated
readiness measurement and before starting the six runs.

Report paired valid-best area reduction and improvement rate, conditional on
size, at equal fresh-transition counts; also report total runtime including
pretraining and data collection. Secondary metrics are tiles/turns, rejection,
unfinished drafts and work charged. Do not treat correlated action draws as
independent factories or two seeds as broad statistical evidence. A failed
supervised gate or nonpositive transfer result is a finding, not permission to
expand training automatically. Long runs remain a later decision.

## Continuity and recovery

| Established benefit | Preservation / required check |
| --- | --- |
| Valid production admission and immutable recipe/network obligations | Keep the full factory authority and exact source metadata; compare reconstructed witnesses and directed segments |
| Efficient bounded native routing and edits | Extract existing code, retain order/guards/drafts/best semantics; paired scripted and random selections |
| Persistent workers, typed owned history and bounded queues | Reuse the native pool; no per-action JSON, process launch or full catalog reload |
| Packed graph/root/conditional inference and optimized masked references | Reuse model packing, batching, indexed-backward fix and foreach Adam; CPU/CUDA numerical regression on the implemented physical inputs |
| Stable validation/cache identity | Load/hash/validate stable sources once at admission; reuse through unchanged identity |
| Sparse replay, true-terminal GAE and complete-wave curriculum | Preserve current PPO/SIL and storage; labels never replace real terminal credit |
| Reserved evaluation geometry and episode lineage | One admission reservation boundary; all root descendants stay in one partition |
| Resume from actual state | Reuse v8 direct learned restore and compatible native cold conversion; no old learned-state upgrade, seed regeneration or historical replay |
| Simple atomic publication and resource guards | Reuse the existing save mechanism; new supervised state saves encoder/head/Adam/RNG and dataset cursor at epoch boundaries |

Dataset publication uses bounded numerical chunks plus one copy of each admitted
source and split manifest. Do not serialize every full candidate domain into
every action record or save a complete physical checkpoint per transition. The
owned pre-action arrays and selected branch suffice for supervised updates.
Retain exceptional partial evidence through existing failure handling. Final
metrics and occasional retained examples support explicit audits outside normal
collection. Use the existing archive/checkpoint machinery; add no second journal.

New supervised artifacts must declare their format and bind their compiled
representation, source and encoder settings. Follow the established single learned
version/settings boundary, preserving direct restore for compatible actual state.
No silent upgrade of learned weights, no
synthetic-as-production fallback, and no automatic expensive trajectory replay.
Measure actual collection, validation, storage and learner cost before adoption.
Generator optimization remains outside this design.

## Stress cases and implementation order

- Moving a block into another retains the unfinished draft and valid best. A later
  clearance can repair it; both records retain their own pre-action input.
- Swapping two ports is atomic, preserving terminal identities and rates. Merely
  choosing the same root with different ports is a different supervised action.
- Crossing channels at one coordinate remain disconnected. Band edits move the
  component and both channel anchors together.
- A deletion that would remove an external anchor is masked/rejected identically
  for production inputs before and after extraction.
- A valid larger candidate supplies its actual geometry target even though it
  does not replace the best. A routing timeout supplies no fabricated geometry.
- Cold restore of a pending draft preserves actual paths, selected ports, best,
  counters and allowances. Incompatible learned versions/settings are rejected
  before payload restore.

The common compiled state and editor extraction is complete. The authorized next
integration slice is the shared numerical feature builder and retained candidate domain; verify
ID-relabeling, source-equivalent inputs and factory-path parity. Next add bounded outcome
collection and its independent dataset partition checks. Finally add the disposable
multi-head predictor, explicit encoder initialization and the staged comparisons above.

Remaining empirical questions are label balance, coverage of preparatory actions,
supervised generalization, production transfer and total compute benefit. They do
not change the fixed data/ownership/action contracts. There is no claim that the
small screen provides sufficient pretraining data or that an outcome predictor
alone solves long-horizon rearrangement.
