# Recipe-Dedicated Facility Requirements

## Design Goal

Define milestone 3: convert a successful throughput report into the recipe-dedicated facility instances required to run the production plan.

This stage intentionally does not share facility instances across recipes. Each required facility instance is assigned to exactly one recipe. Recipe switching, shared scheduling, and input/output rerouting are optimization concerns for later milestones.

## Pipeline

```text
RecipeThroughputReport
  -> FacilityRequirementReport
```

The stage consumes the throughput report from milestone 2. It does not load recipe JSON, validate recipe books, resolve graphs, or calculate throughput.

The CLI command that reaches this stage may still run earlier pipeline steps. Earlier failures are reported by their owning stage before facility calculation runs.

## Core Rule

For each recipe:

```text
required_facilities = ceil(work_seconds_per_second)
unused_capacity = required_facilities - work_seconds_per_second
```

`work_seconds_per_second` is the fractional workload metric from `RecipeThroughputReport.recipe_rates[]`.

Ceiling behavior is exact:

- zero work rate maps to zero facilities
- exact integer rates remain unchanged
- fractional positive rates round up by one

Examples:

- `0/1 -> 0`
- `3/10 -> 1`
- `1/1 -> 1`
- `7/5 -> 2`

## Report DTO

Successful reports use this shape:

```json
{
  "success": true,
  "recipe_requirements": [
    {
      "recipe": "grind-originium-powder",
      "facility": "grinding-unit",
      "work_seconds_per_second": { "numerator": 2, "denominator": 5 },
      "required_facilities": 1,
      "unused_capacity": { "numerator": 3, "denominator": 5 }
    }
  ],
  "facility_summaries": [
    {
      "facility": "grinding-unit",
      "required_facilities": 1,
      "unused_capacity": { "numerator": 3, "denominator": 5 }
    }
  ],
  "diagnostics": [
    {
      "stage": "recipe-facilities",
      "severity": "info",
      "code": "facility-requirements-calculated",
      "path": "/",
      "entity": null,
      "message": "facility requirements were calculated"
    }
  ]
}
```

Failure reports use the same top-level `FacilityRequirementReport` shape with `success: false`, empty requirement and summary arrays, and at least one error diagnostic.

## Output Fields

`recipe_requirements` lists one entry per recipe throughput rate. Order matches the input throughput `recipe_rates` order.

`recipe_requirements[].required_facilities` is the recipe-dedicated facility count for that recipe.

`recipe_requirements[].unused_capacity` is the exact unused work capacity for that recipe's dedicated facilities.

`facility_summaries` aggregates by facility ID, sorted by facility ID.

`facility_summaries[].required_facilities` is the sum of recipe-dedicated `required_facilities` for that facility ID. It does not imply that facility instances are shared across recipes.

`facility_summaries[].unused_capacity` is the sum of per-recipe unused capacity for that facility ID.

`diagnostics` lists deterministic, structured stage diagnostics.

## Diagnostics

Every facility requirement diagnostic has this shape:

```json
{
  "stage": "recipe-facilities",
  "severity": "error",
  "code": "upstream-throughput-failed",
  "path": "/",
  "entity": null,
  "message": "facility requirements require a successful throughput report"
}
```

`stage` is always `recipe-facilities`.

`severity` is `info`, `warning`, or `error`.

`code` is a stable kebab-case diagnostic code.

`path` is a JSON pointer into the input report or output report when possible.

`entity` is an optional stable ID for the recipe or facility most relevant to the diagnostic.

`message` is human-readable and not a stable programmatic key.

## Failure Modes

Facility-domain failures produce `FacilityRequirementReport` with `success: false`.

- `upstream-throughput-failed`
- `arithmetic-overflow`

The CLI should not wrap upstream throughput failures in a facility report. When the throughput pipeline fails, the CLI prints the upstream `RecipeThroughputReport` and exits with failure before this stage runs.

## CLI Failure Priority

The `recipes facilities` command uses this priority:

1. Load and parse the recipe file. File access and JSON parse errors are normal CLI errors.
2. Load and parse the throughput request JSON. Request JSON shape errors print `RecipeThroughputReport` with `success: false`.
3. Validate request schema version, target ID, quantity, and duration. Request field errors print `RecipeThroughputReport` with `success: false`.
4. Validate and promote the recipe book. Recipe data errors print `ValidationReport`.
5. Calculate throughput. Throughput-domain failures print `RecipeThroughputReport` with `success: false`.
6. Calculate facility requirements. Facility-domain failures print `FacilityRequirementReport` with `success: false`.

Any report with `success: false` maps to a failure exit status.

## Ordering Guarantees

- `recipe_requirements` follows input throughput `recipe_rates` order.
- `facility_summaries` is sorted by facility ID.
- `diagnostics` is emitted in deterministic stage order.

## Non-Goals

- No facility catalog joins.
- No recipe switching.
- No facility sharing across recipes.
- No scheduler semantics.
- No belt throughput calculation.
- No pipe throughput calculation.
- No wiring plan.
- No layout generation.
- No layout optimization.
