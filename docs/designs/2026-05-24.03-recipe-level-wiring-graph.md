# Recipe-Level Wiring Graph

## Design Goal

Define milestone 4A: materialize a successful throughput report into an explicit recipe-level wiring DAG.

This stage does not introduce facility instances. It makes implicit item producer and consumer relationships explicit as graph nodes and item-rate edges.

## Pipeline

```text
RecipeThroughputReport
  -> RecipeWiringGraphReport
```

The stage consumes the throughput report from milestone 2. It does not load recipe JSON, validate recipe books, resolve recipe dependencies, calculate throughput, calculate facility requirements, or join a facility catalog.

## Input Invariants

The stage accepts any `RecipeThroughputReport`, but only successful throughput reports are graphable.

A successful input report must satisfy these invariants:

- `target` is present.
- external graph sources are derived only from `external_input_rates`.
- every produced item in `recipe_rates[].output_rates` has exactly one producer recipe.
- every non-external recipe input item has exactly one producer recipe.
- every surplus item has exactly one producer recipe.

Malformed direct library inputs produce wiring-stage failure reports.

The CLI does not wrap upstream throughput failures. If throughput calculation fails, the CLI prints the upstream `RecipeThroughputReport` and exits before this stage runs.

## Report DTO

Successful reports use this shape:

```json
{
  "success": true,
  "nodes": [
    {
      "id": "external:originium-ore",
      "kind": "external",
      "recipe": null,
      "item": "originium-ore"
    },
    {
      "id": "recipe:grind-originium-powder",
      "kind": "recipe",
      "recipe": "grind-originium-powder",
      "item": null
    },
    {
      "id": "target:originium-powder",
      "kind": "target",
      "recipe": null,
      "item": "originium-powder"
    }
  ],
  "edges": [
    {
      "source": "external:originium-ore",
      "target": "recipe:grind-originium-powder",
      "kind": "external-input",
      "item": "originium-ore",
      "rate": { "numerator": 1, "denominator": 2 }
    },
    {
      "source": "recipe:grind-originium-powder",
      "target": "target:originium-powder",
      "kind": "target-output",
      "item": "originium-powder",
      "rate": { "numerator": 1, "denominator": 2 }
    }
  ],
  "diagnostics": [
    {
      "stage": "recipe-wiring-graph",
      "severity": "info",
      "code": "recipe-wiring-graph-built",
      "path": "/",
      "entity": null,
      "message": "recipe-level wiring graph was built"
    }
  ]
}
```

Failure reports use the same top-level `RecipeWiringGraphReport` shape with `success: false`, empty node and edge arrays, and at least one error diagnostic.

## Nodes

Node fields:

- `id`: deterministic graph node ID
- `kind`: node kind
- `recipe`: recipe ID for recipe nodes, otherwise `null`
- `item`: item ID for item-based nodes, otherwise `null`

Node kinds:

- `external`: externally supplied item source
- `recipe`: aggregate recipe node
- `target`: requested target item sink
- `surplus`: surplus item sink

Node ID format:

- `external:<item>`
- `recipe:<recipe>`
- `target:<item>`
- `surplus:<item>`

## Edges

Edge fields:

- `source`: source node ID
- `target`: target node ID
- `kind`: edge kind
- `item`: item flowing across the edge
- `rate`: exact item rate

Edge kinds:

- `external-input`: external source to consuming recipe
- `recipe-flow`: producer recipe to consuming recipe
- `target-output`: producer recipe or external source to target sink
- `surplus-output`: producer recipe to surplus sink

Each edge carries exactly one item. Multi-item flows are represented by multiple edges.

## Diagnostics

Every wiring diagnostic has this shape:

```json
{
  "stage": "recipe-wiring-graph",
  "severity": "error",
  "code": "missing-producer",
  "path": "/recipe_rates/0/input_rates/0/item",
  "entity": "missing-item",
  "message": "input item 'missing-item' has no external source or producer recipe"
}
```

`stage` is always `recipe-wiring-graph`.

`severity` is `info`, `warning`, or `error`.

`code` is a stable kebab-case diagnostic code.

`path` is a JSON pointer into the input throughput report or output graph when possible.

`entity` is an optional stable ID for the item or recipe most relevant to the diagnostic.

`message` is human-readable and not a stable programmatic key.

## Failure Modes

Wiring-domain failures produce `RecipeWiringGraphReport` with `success: false`.

- `upstream-throughput-failed`: input throughput report has `success: false`
- `missing-target`: input throughput report has `success: true` but `target` is `null`
- `missing-producer`: a required non-external item has no producer recipe
- `ambiguous-producer`: a produced item appears in more than one recipe output

## CLI Failure Priority

The `recipes wiring-graph` command uses this priority:

1. Load and parse the recipe file. File access and JSON parse errors are normal CLI errors.
2. Load and parse the throughput request JSON. Request JSON shape errors print `RecipeThroughputReport` with `success: false`.
3. Validate request schema version, target ID, quantity, and duration. Request field errors print `RecipeThroughputReport` with `success: false`.
4. Validate and promote the recipe book. Recipe data errors print `ValidationReport`.
5. Calculate throughput. Throughput-domain failures print `RecipeThroughputReport` with `success: false`.
6. Build recipe-level wiring graph. Wiring-domain failures print `RecipeWiringGraphReport` with `success: false`.

Any report with `success: false` maps to a failure exit status.

## Ordering Guarantees

Node ordering:

1. external nodes sorted by item ID
2. recipe nodes in throughput `recipe_rates` order
3. target node
4. surplus nodes sorted by item ID

Edge ordering:

1. input edges by consuming recipe order, then item ID
2. target edge
3. surplus edges sorted by item ID

Diagnostics are emitted in deterministic stage order.

## Non-Goals

- No facility instances.
- No facility catalog joins.
- No port selection.
- No belt throughput calculation.
- No pipe throughput calculation.
- No physical wiring geometry.
- No layout generation.
- No layout optimization.
