# Production hierarchical training dataflow

Status: accepted design for implementation.

## Goal

The production hierarchical curriculum must pass data produced inside one
generation directly through memory. Persisting a panel or MCTS collection is a
recovery side effect and publication boundary, not the normal transport between
the curriculum, search and generation trainer.

The change must resume the existing hierarchical search report v7 artifacts,
including the 110,988,756-byte generation-4 collection in the interrupted
canonical run. It must preserve frozen-model lineage checks, atomic collection
publication, epoch checkpoint recovery, curriculum promotion, held-out
separation and the standalone CLI commands.

## Current mismatch

The current curriculum creates a training panel on disk and reads it back to
check identities. Search reads the panel again, constructs its complete report
in memory, serializes that report into a second full-size `Vec<u8>`, publishes
`collection.json`, returns only a small JSON summary and drops the report.
Curriculum then reads and deserializes the collection into a reduced private
report for metrics. The generation trainer independently reads the same file
into another byte vector and deserializes a second private collection type.

This makes the filesystem the data bus between stages. It performs duplicate
parsing, retains overlapping report representations and adds an encoded copy of
the largest artifact at publication. The fixed 64 MiB input guard then rejects
a valid collection produced by the same process. Generation 4 exposed this at
110,988,756 bytes after completing search but before training began.

The fixed held-out panel and small configuration and checkpoint files do not
have the same role. They are stable external or generation-boundary inputs.
Model checkpoints also define the frozen search generation and the exact
recovery binding. This design keeps those durable boundaries.

## Shared owned artifacts

`hierarchical_search` remains the owner of the persisted panel and search-report
schemas. Its `Panel`, `SearchReport`, case, result and counter types become the
single crate-internal representation used by curriculum and generation. The
generation trainer and curriculum delete their partial duplicate panel and
collection report schemas.

A small crate-internal wrapper carries a published value and the identity of
its exact encoded file:

```text
Published<T> {
    value: T,
    sha256: String,
    encoded_bytes: u64,
}
```

`Published<Panel>` and `Published<SearchReport>` are process-local ownership
objects, not new wire formats. Existing panel v1 and search report v7 JSON stay
compatible. Fields that currently use `&'static str` may become owned strings
so the same type can deserialize a recovered report; this does not change their
JSON values or schemas.

Search exposes crate-internal operations with these contracts:

```text
prepare_and_publish_panel(...) -> Published<Panel>
collect_and_publish(..., &Published<Panel>, retain_roots) -> Published<SearchReport>
load_published_panel(path) -> Published<Panel>
load_published_report(path) -> Published<SearchReport>
```

The existing public CLI entry points remain thin path-based adapters. They load
their inputs, call the same owned core and return their current compact command
summary. This avoids a compatibility adapter inside the actual curriculum
loop.

## Fresh generation flow

For a newly sampled generation, the curriculum follows this ownership flow:

```text
prepare panel
  |-- atomically publish training-panel.json
  `-- retain Published<Panel> in memory
             |
             v borrow
search with frozen checkpoints
  |-- build SearchReport
  |-- atomically publish collection.json and compute its exact digest
  `-- return Published<SearchReport> without dropping or reparsing it
             |
             +--> borrow once to derive compact success, quality and throughput
             |    statistics and training problem identities
             |
             `--> move Panel + SearchReport into generation training
                         |
                         `-- consume cases and root records into examples
```

The trainer core accepts owned generation inputs containing parsed config,
panel and search report plus their exact durable digests. It validates all
lineage before conversion. Example construction then consumes collection cases
and root records in order. Each record is released after its outer and lower
examples are built; the complete report is not retained for all training
epochs. Panel cases are likewise owned by the conversion rather than cloned
into a second panel representation.

Held-out evaluation uses the same rule. The fixed held-out panel is loaded once
when the curriculum starts. A newly produced held-out report is returned after
publication and summarized in memory. A held-out report is read only when a
new process finds that it was already committed.

Small generated configuration files may use the same parsed value passed to the
trainer while retaining their exact published digest. Frozen source model
configs, parameter order and checkpoint files remain durable inputs and are
verified by the existing lineage contract. Reusing live inference model
objects as optimizer state is outside this change because it would couple the
search runtime and trainer lifetime without addressing the large-data defect.

## Publication and recovery I/O

Large JSON publication must not call `serde_json::to_vec` or
`to_vec_pretty`. A buffered writer serializes directly to the dot-prefixed
temporary file. A counting SHA-256 writer observes the same bytes in that one
pass. After a successful flush and close, rename publishes the complete file.
Serialization failure leaves no final path; the known temporary path is safe to
remove or replace on retry.

Recovery uses a buffered reader and a counting SHA-256 reader so parsing and
exact content hashing happen in one pass without retaining the encoded bytes.
The parser must consume the complete document and reject trailing content. The
returned `Published<T>` therefore has the same identity whether it was just
created or recovered.

The 64 MiB guard remains for small external configuration and model-definition
inputs where it is a meaningful corruption check. It is removed from the
hierarchical collection loader because collection size grows legitimately with
cases, roots and retained action witnesses. A recovered collection is instead
validated against its declared schema, training partition, panel digest,
catalog and frozen checkpoint identities, exact case IDs, nonempty training
roots and search-controlled case/root structure. Standalone generation uses
this same streaming collection loader. This is a content contract rather than
an arbitrary encoded-size contract.

The collection remains committed before optimizer work starts. Publication is
therefore still the recovery boundary even though a fresh process does not read
the file it just wrote.

## Restart state transitions

The curriculum chooses acquisition from the presence of committed artifacts:

| Durable state | Action in the current process |
| --- | --- |
| No panel | Deterministically prepare and publish it; keep the returned panel. |
| Panel, no collection | Load the panel once, collect and publish search output; keep the returned report. |
| Collection, no completed training | Load panel and collection once, validate and move both into the trainer. |
| Pending trainer before first epoch checkpoint | Load panel and collection once, discard the incomplete pending trainer state and restart from frozen source checkpoints as today. |
| Pending trainer with a complete epoch checkpoint | Load panel and collection once to reconstruct examples, then restore model and Adam state from the latest complete checkpoint as today. |
| Completed training, no held-out result or summary | Load the collection once for generation statistics, continue evaluation or summary publication; do not invoke the trainer. |
| Committed generation summary | Advance curriculum state from the summary without loading panel or collection. |

A crash while the collection temporary file is being written leaves no
committed collection, so recovery recollects. A crash after collection rename
can reuse it. A crash after summary publication but before curriculum state
publication replays only the small summary-to-state transition. These are the
existing logical boundaries; the new path changes neither promotion timing nor
model visibility.

The current interrupted generation 4 has a committed v7 collection, no
completed trainer output and no reusable trainer checkpoint. Its first run with
this design takes the third row: deserialize and hash that collection once,
validate its frozen lineage, build examples and continue training. Later fresh
generations remain entirely on the in-memory handoff path.

## Invariants

1. A training collection is durably published and has an exact SHA-256 identity
   before any optimizer update derived from it.
2. The normal fresh path never opens its just-published panel, training
   collection or held-out report for reading.
3. A restarted stage deserializes each required large artifact at most once and
   passes that owned value to the same core used by the fresh path.
4. Curriculum metrics are derived before the training report is moved; only
   compact statistics and success bits outlive example conversion.
5. Example conversion consumes the report, so training does not retain both a
   full witness collection and the complete derived example set.
6. Search report v7, panel v1 and current generation recovery bindings remain
   readable. Exact raw JSON digests retain their current meaning.
7. Training and held-out partitions, case identity, frozen model, catalog,
   search configuration and panel lineage checks remain mandatory.
8. A model becomes the source for the next generation only after the complete
   generation output is atomically published. Curriculum promotion still waits
   for the generation summary.
9. Held-out root records remain omitted. They are neither training data nor
   needed for metrics.
10. Standalone search and generation commands use the same persistence,
    validation and training cores as curriculum execution.

## Continuity checklist

| Existing benefit | Reuse or replacement | Check |
| --- | --- | --- |
| Native session replay and independent validation | Reuse unchanged while consuming records | Existing replay diagnostics plus one real generation |
| Batched compiled search inference and persistent routing pool | Reuse search engine unchanged | Fresh CUDA smoke throughput and completion |
| Frozen lower/outer model lineage | Carry exact hashes in `Published` inputs and existing recovery binding | Reject a changed source checkpoint; resume existing generation 4 |
| Complete root-action witnesses for lower and outer distillation | Preserve report v7 wire content; move records during conversion | Compare sample/root/action counts with the source collection |
| Atomic collection and model publication | Replace only collection encoding buffer with buffered temporary-file serialization and rename | Interrupt/failure boundary check and digest comparison |
| Epoch model and Adam recovery | Reuse existing pending directory and checkpoint path | Resume from one complete epoch checkpoint |
| Training/held-out separation and promotion window | Reuse curriculum state and summary logic | One bounded curriculum generation and retained identities |
| Standalone CLI behavior | Keep path adapters over the shared owned core | Run the relevant search/generation command |
| Compact held-out artifacts | Reuse `retain_root_records = false` | Confirm held-out report has no root records |

## Rejected alternatives

- Raising or deleting the 64 MiB constant alone leaves the disk data bus,
  duplicate deserialization and full encoded buffer in place.
- Streaming a freshly written collection back from disk into the trainer still
  makes persistence part of normal computation and performs unnecessary I/O.
- Omitting collection persistence prevents recovery between expensive search
  and training and removes the immutable input named by trainer checkpoints.
- Starting optimizer work before atomic collection publication can leave a
  reusable epoch checkpoint whose training data was never committed.
- Keeping the borrowed report while constructing every example preserves the
  largest avoidable peak. Ownership must reach the conversion loop.
- Incremental case journals or a new binary artifact format add recovery and
  migration machinery that is unnecessary for this defect. The current JSON
  schemas can be streamed.
- Passing live search model objects into the optimizer expands the cutover into
  a model-lifecycle redesign. Frozen checkpoint reload is small, occurs once per
  stage and remains useful for independent CLI and recovery execution.

## Implementation slices

1. Make the existing panel and search report hierarchy the shared serializable
   and deserializable crate-internal schema. Add buffered publish/load helpers
   that return exact digest and byte count, with a wire-compatibility and digest
   check against an existing v7 fixture.
2. Split panel preparation and search into owned cores plus current public CLI
   adapters. Return published values from fresh training and evaluation search
   without changing search semantics.
3. Split generation into a path adapter and an owned core. Validate before
   moving, then make example construction consume panel cases and root records.
   Preserve all current recovery binding and checkpoint behavior.
4. Change curriculum acquisition to retain fresh values, load each recovered
   value once and compute compact statistics before ownership transfer. Remove
   duplicate reduced report types and the collection byte cap.
5. Verify locally with formatting, workspace checks and focused serialization
   tests. On the training server, run a small fresh CUDA curriculum smoke to
   exercise the memory handoff, then resume the retained 110,988,756-byte
   generation-4 collection to prove v7 compatibility, single recovery loading
   and unchanged sample identities before continuing the canonical run.

The first implementation slice is the shared artifact representation and
streaming JSON boundary. It enables the later ownership changes without
temporarily weakening persistence or recovery.
