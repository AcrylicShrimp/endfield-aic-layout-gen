# Facility Catalog V1

## Design Goal

Define the first external facility catalog schema needed by facility-only layout.

V1 intentionally contains only stable facility IDs and rectangular footprints. It does not define ports, channels, rotations, placement, wiring geometry, or optimization constraints.

## Pipeline

```text
facility catalog JSON file
  -> FacilityCatalog
  -> FacilityCatalogValidationReport
  -> ValidatedFacilityCatalog
```

The loader reads and parses JSON. The validator checks semantic catalog rules and returns a structured validation report.

`FacilityCatalog` is raw parsed data. `ValidatedFacilityCatalog::try_from_catalog` is the only promotion path to trusted facility data. Successful promotion stores a deterministic facility-ID lookup for downstream layout stages. Failed promotion returns the existing `FacilityCatalogValidationReport`; downstream stages therefore do not need to repeat catalog validation.

## JSON Schema

Successful parse uses this shape:

```json
{
  "schema_version": 1,
  "facilities": [
    {
      "id": "grinding-unit",
      "footprint": {
        "width": 3,
        "height": 2
      }
    }
  ]
}
```

All objects reject unknown fields during JSON parse.

Fields:

- `schema_version`: facility catalog schema version. V1 supports only `1`.
- `facilities`: list of facility definitions.
- `facilities[].id`: stable kebab-case facility ID.
- `facilities[].footprint.width`: positive integer grid-cell width in canonical, unrotated orientation.
- `facilities[].footprint.height`: positive integer grid-cell height in canonical, unrotated orientation.

The catalog may be empty. Layout stages that need a facility absent from the catalog will fail in their own stage.

## Stable IDs

Facility IDs use the same stable ID rule as recipe and item IDs:

```text
^[a-z0-9]+(-[a-z0-9]+)*$
```

Implementation should share this rule through a crate-private helper instead of duplicating the logic in each data module.

## Validation Report DTO

Successful validation reports use this shape:

```json
{
  "valid": true,
  "diagnostics": []
}
```

Failed validation reports use the same shape with `valid: false` and at least one error diagnostic.

## Diagnostics

Every facility catalog diagnostic has this shape:

```json
{
  "stage": "facility-catalog-validation",
  "severity": "error",
  "code": "invalid-facility-id",
  "path": "/facilities/0/id",
  "entity": "Grinding Unit",
  "message": "facility id 'Grinding Unit' must match ^[a-z0-9]+(-[a-z0-9]+)*$"
}
```

`stage` is always `facility-catalog-validation`.

`severity` is `info`, `warning`, or `error`.

`code` is a stable kebab-case diagnostic code.

`path` is a JSON pointer into the parsed catalog when possible.

`entity` is an optional stable or raw ID most relevant to the diagnostic. It is serialized as `null` when no entity is available.

`message` is human-readable and not a stable programmatic key.

## Failure Modes

Loader failures are normal CLI errors:

- file access failure
- malformed JSON
- JSON shape errors, including unknown fields and missing required fields

Semantic validation failures produce `FacilityCatalogValidationReport` with `valid: false`:

- `unsupported-facility-catalog-schema-version`
- `invalid-facility-id`: path `/facilities/{index}/id`
- `duplicate-facility-id`: path `/facilities/{index}/id`
- `non-positive-footprint-width`: path `/facilities/{index}/footprint/width`
- `non-positive-footprint-height`: path `/facilities/{index}/footprint/height`

`unsupported-facility-catalog-schema-version` uses path `/schema_version`.

## CLI Failure Priority

The `facilities validate` command uses this priority:

1. Load and parse the facility catalog file. File access, JSON parse errors, unknown fields, and missing required fields are normal CLI errors.
2. Validate the parsed facility catalog. Validation failures print `FacilityCatalogValidationReport` with `valid: false`.

Any report with `valid: false` maps to a failure exit status.

## Ordering Guarantees

- Validation diagnostics are emitted in catalog order.
- Duplicate ID diagnostics are emitted at the repeated facility entry.
- Successful validation emits no diagnostics.

## Non-Goals

- No facility ports.
- No belt or pipe channel data.
- No rotation model.
- No recipe joins.
- No facility instance joins.
- No placement calculation.
- No wiring calculation.
- No layout constraints.
- No optimization.
