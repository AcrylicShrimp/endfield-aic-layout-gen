# Procedural routed layouts and a shared physical format

Status: implemented; bounded quality evaluation completed. See the
[experiment report](../reports/2026-09-15-procedural-layout-generation.md) and
[CLI/API guide](../../crates/aic-layout-gen/README.md).
The user authorized an independent crate experiment and clarified that its output
must include routing: one call produces the whole physical layout. A shared data
crate is a prerequisite. This concludes the generator design discussion; learner
pretraining remains a later design and is not launched by this work.

## Goal and boundary

Generate seeded, diverse rectangular-block layouts with compatible directed ports,
capacity-carrying connections and actual legal paths. The agreed abstraction has
no recipe semantics. A physically validated synthetic layout is not a claim of
production balance, optimality, or compatibility with the current recipe-bound
PPO admission format. The current production/training workflow stays functional.

`aic-layout` owns the physical catalog types, exact rates, geometry, a versioned
problem/solution format and independent physical validation. Existing catalog and
rate implementations move here, with existing public `aic-data` module exports
referring to the same types. No second catalog parser or game-data constants.

`aic-routing` owns the existing bounded native A* and necessary reachability
preflight, extracted without changing route ordering or cost semantics. Existing
editing and the generator both use it. Crossing candidates use borrowed physical
route views and the external logistics catalog, without a factory/recipe owner.

`aic-layout-gen` owns procedural construction, port selection, routing orchestration,
acceptance, explicit work limits, seeded batches, quality summaries and a standalone
CLI/gallery. Callers provide validated catalogs, settings and seed; they receive a
complete validated layout or a bounded generation failure, never an unrouted success.

## Model and generation

The immutable problem identifies blocks by catalog definition and connections by
stable source/target block identity, transport, commodity label and exact rate.
The solution assigns block poses, compatible ports and paths, including actual
catalog crossing components. Changing a pose or port cannot silently delete an
obligation. A catalog identity binds persisted samples to external inputs.

Sample block types, allowed rotations and two independent permutations. Sequence
pair constraints determine left/below relationships; nonnegative sampled gaps
yield nonoverlapping coordinates. The canvas is derived within an explicit cell
guard, not an asserted game limit. Random permutations are not uniform sampling
of physical layouts and do not remove distribution bias.

Grow the connection graph by selecting compatible free port pairs and routing
them, prioritizing links between disconnected components until weak connectivity
is established, then adding links up to the sampled target. Include distant as
well as local candidates; expose density, degree and transport controls. Accept
only routed links while the new problem is being constructed. Freeze all links
once the generated problem is published. Failure to reach requested quality/count
conditions within limits is generation exhaustion, not global infeasibility.

Routes obey body occupancy, port directions/compatibility, exact capacities,
transport layers and catalog-backed crossings. Preserve legal immediate turns
on the cell adjacent to a facility port. Validation independently checks the
published problem and solution; it does not trust a `validated` flag or metrics.

## Continuity checklist

| Existing benefit | Reuse / check |
| --- | --- |
| Validated external facilities, transports and logistics | Move parsers/types/tests intact to the shared crate; existing catalog CLI/tests; item/recipe ownership stays in `aic-data` |
| Exact rate arithmetic and diagnostics | Move implementation intact, retain old exports and behavior tests |
| Bounded deterministic A*, preflight and crossing semantics | Extract actual kernel and its reference tests; native regression suite and a fixed-query timing comparison |
| Native compact typed geometry and batched ownership | Shared geometry types; no JSON conversion between generator/router; immutable catalogs shared across batch workers |
| Existing generation RNG and draw semantics | One shared SplitMix64/Fisher-Yates implementation; existing generator behavior tests |
| Stable-input validation and economical persistence | Validate/hash catalogs once per command; one completed sample publication, no per-edge writes |
| Required failure distinctions and validity | Structured diagnostics; work exhaustion differs from fixed-query no-path; final independent validation |

## Verification and quality evidence

Test sequence-pair nonoverlap, deterministic generation, exact obligation coverage,
port/flow/layer/crossing rejection, invalid configuration, and bounded failure.
Run actual release CLI generation across a small/medium/larger matrix and retain
all seeds/statuses rather than selecting successful examples. Measure successful
layouts per second including validation/publication, attempts, routing expansions,
graph density, branching/merging, long links, transport mix, footprint diversity,
aspect ratio and occupancy. Inspect a gallery of ordinary seeds visually.

Generated inputs/results/gallery remain under ignored `artifacts/`; commit compact
configuration, reproduction commands and findings. No quality claim is based only
on a successful build or on one attractive seed. This experiment must establish a
useful source of varied routed examples; transfer to real-player layouts remains
an empirical question for the later pretraining comparison.

## References and tradeoffs

[Sequence pair representation](https://arxiv.org/abs/1708.09779) supplies a general
nonoverlapping rectangle representation. Sampling gaps and growing graph edges
with the existing router are this project's procedural proposal. They guarantee
neither uniformity nor successful completion of every requested random sample.
Routing-aware edge acceptance can favor easier graphs; record requested versus
achieved graph properties and failed attempts explicitly.

Rejected: hardcoded factory templates; coordinates-only output; silently dropping
fixed obligations; replacing optimized routing with a new naive grid search;
calling a route budget failure global infeasibility; resuming PPO before verifying
the actual generated-data integration and defining its separate admission contract.
