# Facility Catalog V3 Directional Port Contract

## Scope

Facility catalog schema version 3 adds the directional belt and pipe ports required by later routing stages. It does not route logistics, reserve transport cells, enforce throughput capacity, or change the current footprint-only placement objective.

This is a hard cutover from schema version 2. Every facility must add a `ports` array and change `schema_version` to `3`. Facilities without logistics ports use an empty array.

## Input DTO

```json
{
  "schema_version": 3,
  "facilities": [
    {
      "id": "grinding-unit",
      "footprint": { "width": 3, "height": 3 },
      "allowed_rotations": [0, 90, 180, 270],
      "ports": [
        {
          "id": "solid-input",
          "direction": "input",
          "transport": "belt",
          "position": { "x": 1, "y": 2 },
          "edge": "south"
        },
        {
          "id": "solid-output",
          "direction": "output",
          "transport": "belt",
          "position": { "x": 1, "y": 0 },
          "edge": "north"
        }
      ]
    }
  ]
}
```

Port coordinates use the facility's canonical zero-degree footprint with `(0, 0)` at the north-west cell and positive `y` toward the south. `edge` identifies the outward-facing footprint edge. `direction` is `input` or `output`; `transport` is `belt` or `pipe`.

Port IDs are stable only within their facility. An input and output may occupy the same boundary cell when the source data explicitly models that arrangement, but their IDs must remain distinct.

## Rotation Semantics

Facility rotation rotates the footprint, port position, and port edge clockwise as one unit. For a canonical `width = W`, `height = H` footprint:

- `0`: `(x, y)`
- `90`: `(H - 1 - y, x)`
- `180`: `(W - 1 - x, H - 1 - y)`
- `270`: `(y, W - 1 - x)`

Edges rotate by the same quarter turn. The routing stage will apply these transforms. The current placement stage still ignores ports and may collapse rotations with identical rectangular geometry.

## Invariants

- Facility IDs and port IDs use the stable ID pattern.
- Port IDs are unique within one facility.
- Port positions are inside the canonical footprint.
- `north` ports have `y = 0`.
- `east` ports have `x = width - 1`.
- `south` ports have `y = height - 1`.
- `west` ports have `x = 0`.
- Empty port arrays are valid.

## Diagnostics

Validation continues to return `FacilityCatalogValidationReport`. V3 adds:

- `invalid-facility-port-id`
- `duplicate-facility-port-id`
- `facility-port-position-out-of-bounds`
- `facility-port-edge-mismatch`

Parse failures, including missing required fields, unknown fields, or unknown enum values, remain loader errors because no reliable raw DTO exists to validate.

## Research Mapping

The public game-table backup exposes facility footprint dimensions under `range.width` and `range.depth`, port coordinates under `trans.position.x` and `trans.position.z`, input/output lists, and the belt/pipe distinction through `isPipe`. The MIT-licensed IndustrialPlanner provides a second normalized implementation for cross-checking those facts.

Game data remains external. This repository defines and validates the contract but does not vendor a complete extracted game-data snapshot or game assets.
