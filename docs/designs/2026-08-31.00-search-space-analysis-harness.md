# Search-Space Analysis And Experiment Harness

## Status

Accepted design. This document extends, but does not replace, the exact-joint experiment in
`2026-08-30.32-exact-joint-incremental-solver.md`.

The next implementation work is analysis and measurement only. It must not change solver
semantics, add a search-space restriction, or silently move placement or routing decisions out of
the solver.

## Research Goal

The primary research target is the complete Heavy Xiranite production request represented by
`data/examples/source-plan.game-heavy-xiranite-forge.request.json`. The target item is
`item-xiranite-enr-powder`, known to the Korean user as `중식양`. This workload is the fixed
end-to-end baseline for the current research program. Producing a validated, compact layout for
this entire graph within a practical interactive runtime is the first meaningful success target.

The workload identity is fixed; its experimental layout bounds and time or memory budgets are not.
Every bound and resource budget remains an explicit scenario input. No particular diagnostic grid,
including 50 by 50 or 500 by 500, is a project invariant or acceptance condition.

The immediate objective is to discover, phase by phase, how and why the exact search explodes as
the Heavy Xiranite graph grows. The harness must separate the contribution of:

- production-graph structure;
- facility placement choices;
- rotations and directional port choices;
- routing-grid and directed-flow choices;
- splitter, converger, and bridge choices;
- placement-routing coupling constraints;
- symmetry;
- formulation-specific auxiliary variables and constraints.

The evidence will then be used to design and test ways to divide the problem, reformulate it, or
change what the solver must decide. A proposed change is not considered quality-preserving merely
because it is fast. It must either have a correctness argument that preserves every legal solution
and the lexicographic objective, or remain an explicitly labeled heuristic experiment whose quality
loss is measured against an exact baseline.

The long-term experimental loop is:

```text
production graph
  -> static problem analysis
  -> complexity estimate
  -> solver strategy selection
  -> instrumented exact solve
  -> quality and proof evidence
  -> revised analysis and strategy hypotheses
```

The first release of the harness ends at measurement and report-only strategy recommendations. It
does not automatically select a different solver architecture.

## Invariants

1. The current baseline remains one joint Pumpkin model per cumulative graph. Facility placement,
   rotation, directional port selection, belt and pipe routing, commodity flow, and logistics
   components remain solver decisions.
2. The current lexicographic objective remains unchanged: used area, physical transport tiles,
   turns, maximum used side, and logistics-component count.
3. A prior exact solution may be supplied as a non-binding solver hint. It may not restrict the
   enlarged model.
4. Search-space explosion, timeout, memory exhaustion, and `unknown` are valid results. The harness
   must preserve and report them.
5. Request bounds are hard ceilings for one experiment, not blueprint dimensions or game limits.
6. Every successful incumbent must pass the independent witness validator.
7. Safe and heuristic experiments must never share an ambiguous flag or result namespace.
8. Analysis data is observational. Collecting a metric must not change variable ordering, domains,
   constraints, or solver decisions except for separately measured instrumentation overhead.
9. Static feature definitions, formulation versions, solver versions, and experiment configurations
   must be versioned so results remain comparable.

## Current Baseline Evidence

The current Heavy Xiranite graph contains 59 facility instances, 6 non-facility nodes, and 96
logical wiring edges. Its current cumulative SCC harness reaches an `unknown` result in the first
one-facility phase for a 50 by 50 diagnostic request with a five-second search budget.

That first phase already constructs approximately:

- 8,464 placement variables;
- 132,480 endpoint-choice variables;
- 7,500 route-cell variables;
- 29,400 directed route-arc variables;
- 29,400 integer flow variables;
- 60,000 branch-component variables;
- 7,500 route-order variables;
- 5,000 bridge variables and 20,000 bridge-rotation variables;
- 15,000 crossing-owner variables;
- 404,960 crossing constraints.

Model construction took approximately 1.9 seconds and the five-second search produced no complete
incumbent. These figures are a useful observation, not yet a diagnosis. Existing metrics count
selected variable and constraint families, but do not describe domain volume, constraint arity,
factor-graph structure, symmetry, or placement-routing coupling. The new harness must make those
causes separable.

## Analysis Layers

Analysis is split into three reports so callers can distinguish cheap pre-build estimates from the
model actually handed to Pumpkin and from search behavior.

### 1. IR Complexity Report

This report is computed after normalizing the facility-instance wiring into commodity networks and
before allocating Pumpkin variables. It must be cheap enough to run for every request, including a
request that would be too large to construct.

It describes the production graph, facility and port choices, request grid, normalized terminal
lanes, and closed-form estimates for the current formulation.

### 2. Model Complexity Report

This report is recorded while the exact model is constructed and is finalized before search starts.
It describes actual variable domains, actual posted constraints, and the variable-constraint factor
graph. It is authoritative for the constructed formulation; the IR estimates are retained so their
prediction error can be measured.

Instrumentation must be implemented through one model-building recorder used by the authoritative
builder. Constraint formulas must not be duplicated in a separate analyzer because those copies
will drift. The recorder assigns a stable family to every variable and constraint as each is
created, accumulates summary statistics, and optionally retains full incidence data for small
models.

### 3. Solve Observation Report

This report records model-build time, search progress, proof status, validated incumbents, objective
stages, termination, and process-level resource observations. It must use explicit null values when
Pumpkin does not expose a statistic or bound. It must never infer infeasibility from timeout or
`unknown`.

## Architecture

```text
Benchmark suite manifest
  -> existing recipe/source-plan/wiring pipeline
  -> normalized ModelInput
       |-> IR analyzer -----------------------> IR complexity report
       |-> instrumented exact model builder --> Model complexity report
                                                  |
                                                  v
                                             Pumpkin search
                                                  |
                                                  v
                                             solve observation
  -> isolated experiment runner
  -> JSON/JSONL artifacts + compact summary tables
  -> offline correlation, comparison, and report-only strategy recommendation
```

The boundaries are:

- the existing pipeline owns recipe resolution and the logical production graph;
- the IR analyzer owns only read-only feature extraction and formulation-size estimates;
- the exact builder owns all solver variables and constraints;
- the model recorder observes builder calls but has no authority to prune them;
- the solver adapter owns Pumpkin configuration and search;
- the experiment runner owns budgets, repetitions, process isolation, and artifacts;
- the analysis layer compares results but cannot alter a solve request.

The instrumented path and an instrumentation-disabled path must build identical models. A small
model fingerprint derived from stable variable families, domains, and constraint families will be
used to detect accidental differences.

## Static And Construction-Time Metrics

The following tables define the initial metric catalog. “Decision value” means usefulness for a
future orchestration decision, not permission to make that decision automatically.

### Production Graph And Facility Metrics

| Metric | Meaning | Why it may predict difficulty | Cost | Decision value |
| --- | --- | --- | --- | --- |
| Facility count and type histogram | Number of instances by flattened facility definition | More instances create placement choices, non-overlap coupling, ports, and terminal constraints | Linear | High; basic size and workload stratification |
| Footprint area and dimension histogram | Minimum occupied facility area and shape distribution | Determines packing pressure and the number of legal origins/rotations | Linear | High; distinguishes many small facilities from a few large ones |
| Request width, height, and cell count | Caller-supplied search ceilings | Current dense routing families scale with every grid cell and adjacency | Constant | High; expected to dominate the current formulation |
| Facility-area slack | Grid area minus required facility area | Low slack indicates packing difficulty; very high slack increases translation and route choices | Linear | Medium; interpret together with candidate counts |
| Rotation count per facility | Number of distinct legal rotated definitions | Multiplies placement and directional-port alternatives | Linear | High |
| Legal placement candidates | Exact legal `(rotation, x, y)` choices per facility, plus sum/min/max/percentiles | Direct size of the enumerated placement domain | Linear in facilities and rotations using closed forms | Very high |
| Placement log volume | Sum of `log2(candidate_count)` for facilities | Upper bound on independent placement-choice encoding volume | Linear | High for relative comparisons; not a feasible-solution count |
| Compatible port count per endpoint | Port definitions matching transport and input/output direction before coordinates | Captures local choice and impossible endpoints | Linear in terminals times facility ports | High |
| Endpoint option count | Legal placement-port combinations with an in-domain outside cell | Current endpoint literals scale placement choices by compatible ports | Linear in emitted options, or exact closed form where proven | Very high |
| Port-choice entropy proxy | Sum of `log2(endpoint_option_count)` and distribution | Separates endpoint ambiguity from facility origin ambiguity | Linear | High; diagnostic only |

### Logical Network Metrics

| Metric | Meaning | Why it may predict difficulty | Cost | Decision value |
| --- | --- | --- | --- | --- |
| Logical wiring edges | Supply/demand requirements before capacity splitting | Measures production-graph connectivity | Linear | Medium |
| Capacity-split lane count | Independent terminal lanes after transport capacity splitting | Each lane requires one terminal selection and exact flow | Linear | High |
| Commodity-network count | Networks grouped by item and transport | Current dense route variables scale by network count times grid size | Linear | Very high |
| Belt/pipe network counts | Commodity networks by independent transport layer | Different collision and bridge interactions occur per layer | Linear | High |
| Terminals per network | Supply/demand lane count distribution | Larger fungible networks increase flow allocation and branching choices | Linear | Very high |
| External terminal count | Dangling external supplies and demands | Adds boundary-direction choices but no facility origin | Linear | Medium |

| Facility-network incidence | Bipartite links between facilities and commodity networks | Direct logical coupling before spatial modeling | Linear | Very high |
| Shared-network coupling | Pairs or groups of facilities connected through the same commodity network | Fungible flow can couple terminals without fixed pairings | Linear to quadratic per network; aggregate without materializing pairs | High |

### Graph Structure Metrics

| Metric | Meaning | Why it may predict difficulty | Cost | Decision value |
| --- | --- | --- | --- | --- |
| Weak connected components | Independent components of the logical facility/network graph | Proven independence may permit exact decomposition if spatial/objective coupling is also handled | Linear | High |
| Degree distribution and density | Mean, max, p95 degree and edge density | High-degree hubs tend to create port, branch, and flow coupling | Linear | High |
| Articulation points and biconnected blocks | Single vertices whose removal separates the logical graph | Candidate exact interfaces or phase boundaries | Linear | High |
| SCC count and sizes | Directed production cycles and their atomic sizes | Large cyclic blocks cannot be topologically separated without an interface treatment | Linear | Very high |
| Condensation depth and width | Longest dependency depth and maximum frontier size | Predicts cumulative-growth phase count and frontier breadth | Linear | High |
| Phase growth deltas | Facilities, networks, terminals, and logical cut added at each SCC phase | Shows exactly when model growth accelerates | Linear after SCC construction | Very high for Heavy Xiranite diagnosis |
| Frontier cut size | Terminal lanes and commodity networks crossing an included/excluded graph boundary | Large cuts imply strong coupling between subproblem and remainder | Linear per candidate phase | Very high for decomposition experiments |
| Small-separator candidates | Exact articulation separators and bounded-size graph cuts | Possible master/subproblem interfaces | Linear for articulation; more expensive for bounded cuts | High, but decomposition must preserve spatial coupling |

### Formulation Size And Domain Metrics

| Metric | Meaning | Why it may predict difficulty | Cost | Decision value |
| --- | --- | --- | --- | --- |
| Variables by family | Boolean and integer counts for placement, endpoint, route cell, arc, flow, component, bridge, order, and objective families | Identifies the source of model growth | Constant work per created variable | Very high |
| Domain cardinality by family | Sum/min/max/p50/p95 and histogram of each variable domain size | Equal variable counts can represent radically different searches | Constant work per variable | Very high |
| Log-domain volume | `sum(log2(domain cardinality))` overall and by family | Compact upper bound on unconstrained encoding volume | Constant work per variable | High, with explicit caveat below |
| Boolean/integer ratio | Number of binary choices versus bounded integer values | Suggests whether branching or propagation on arithmetic domains dominates | Constant | Medium |
| Routing-grid candidates | Cells and directed orthogonal arcs per network and layer | Direct closed-form driver of dense routing variables | Constant or linear in networks | Very high |
| Component candidates | Splitter, converger, bridge position/rotation/topology choices | Measures branch and crossing overhead | Linear in emitted candidates | Very high |
| Constraints by family and relation | Count of equalities, inequalities, implications, cardinalities, multiplication/max, and formulation-specific families | Identifies which rule creates propagation load | Constant work per posted constraint | Very high |
| Constraint arity and term count | Min/max/mean/p95 number of variables or linear terms | Large global constraints can behave differently from many binary constraints | Linear in posted terms | High |
| Coefficient magnitude and big-M range | Min/max magnitude and family of large coefficients | Weak relaxations or large integer ranges can reduce propagation quality | Linear in terms | High |
| Estimated model bytes | Recorder-owned conservative byte estimate by family | Warns before process memory exhaustion | Constant per object | High after calibration |

`log-domain volume` is not the number of legal layouts. It is the product of independent variable
domains before constraints, expressed in bits. Correlation, reification, and propagation make the
true feasible space much smaller. The metric is useful for relative comparisons between equivalent
formulations only when reported beside constraint and coupling metrics.

### Constraint-Graph And Coupling Metrics

| Metric | Meaning | Why it may predict difficulty | Cost | Decision value |
| --- | --- | --- | --- | --- |
| Factor-graph vertices and incidences | Variables, constraints, and variable-constraint edges | Captures actual structural size beyond raw counts | Linear in posted terms | Very high |
| Variable/constraint degree | Mean, max, p95 degree by family | High-degree variables couple distant choices and may dominate propagation | Linear in incidences | Very high |
| Factor-graph density | Incidences divided by possible variable-constraint pairs | Coarse coupling measure; mainly comparable within formulation versions | Constant after counts | Medium |
| Factor connected components | Components after all constraints are posted | Reveals actual independence missed by the logical graph | Linear in retained incidence graph | High |
| Articulation and separator summary | Small boundaries in the factor graph | Candidate exact decomposition interfaces | Full graph can be expensive; enable for small/medium models | High for research |
| Cross-family constraints | Constraints containing variables from more than one major family | Directly locates placement-routing-component coupling | Linear in incidences | Very high |
| Placement-routing cross incidences | Number and ratio of incidences joining placement/port variables to routing/flow variables | Estimates how tightly those decisions are bound in the actual formulation | Linear | Very high |
| Network-network collision coupling | Constraints joining two commodity networks on one layer/cell | Dense pairwise resource competition can dominate routing | Linear in emitted constraints | Very high |
| Objective coupling | Variables and constraints connected to used bounds and lexicographic objectives | A globally coupled area objective can prevent otherwise independent decomposition | Linear | High |

For large models, summary incidence counts are mandatory but storing the full graph is optional.
`summary` mode accumulates family-to-family matrices and degree statistics without retaining every
edge. `full-small` mode retains exact incidences under an explicit analyzer memory ceiling and runs
component/separator algorithms. Exceeding that ceiling produces a structured partial-analysis
diagnostic, not a solver change.

### Symmetry Metrics

Symmetry detection is initially descriptive. A reported symmetry is not automatically broken.

| Metric | Meaning | Why it may predict difficulty | Cost | Decision value |
| --- | --- | --- | --- | --- |
| Identical facility groups | Instances with identical flattened facility, recipe behavior, and incident network signatures | Permuting indistinguishable instances can multiply equivalent solutions | Sorting/hashing plus refinement | Very high |
| Identical lane/terminal groups | Equal-rate terminals with identical semantics and incidence | Capacity splitting can create interchangeable lanes | Linear plus grouping | Very high |
| Equivalent port groups | Ports related by an exact facility automorphism with identical semantics | Port permutations may create duplicate branches | Small graph automorphism per facility | Medium to high |
| Commodity-network automorphisms | Networks with identical item-independent structure where identity is semantically irrelevant | May create equivalent flow assignments | Graph refinement; exact automorphism optional for small cases | Medium |
| Grid translation status | Whether canonical `min_x = 0`, `min_y = 0` is active and applicable | Unbroken translation creates many duplicate layouts | Constant | High validation check |
| Grid reflection/rotation candidates | Geometric transformations preserving request shape, facilities, directional ports, and external semantics | Can multiply equivalent layouts, but only when the complete problem is invariant | Cheap necessary checks; exact proof more expensive | Medium |

## Solve Observation Metrics

Every experiment run records:

- upstream graph-build time;
- IR-analysis time;
- Pumpkin model-construction time;
- search time and total process wall time;
- first validated feasible time when available;
- validated incumbent count;
- incumbent objective at the configured search budget;
- best bound and proof status for the active lexicographic stage when Pumpkin exposes them;
- per-stage objective, bound, time, and proof state;
- final lexicographic objective vector;
- termination reason, including timeout, resource limit, cancellation, infeasible proof, optimal,
  feasible, and unproven unknown;
- peak resident memory and process exit status when supported by the runner platform;
- validation result and artifact paths;
- solver version, formulation ID, source revision, configuration hash, and random seed if the solver
  exposes one.

Conflict, decision, propagation, restart, or learned-clause counts are useful only if Pumpkin's
public API exposes stable values. Their initial schema fields remain optional. The harness must not
scrape unstable debug text or fabricate them.

Pumpkin currently may not expose a useful best bound for a stopped non-optimal stage. That field is
`null` in such a result. Optimality gap is computed only when the incumbent and a comparable valid
bound for the same lexicographic stage both exist.

## Heavy Xiranite Growth Profile

The Heavy Xiranite workload is measured at every cumulative SCC phase and in a direct full-graph
solve. Each phase produces a growth row containing:

- introduced SCC IDs and cycle status;
- cumulative and newly introduced facilities, edges, lanes, networks, and terminals;
- frontier cut size to the unresolved graph;
- every IR estimate;
- every actual model metric reached before failure;
- delta and ratio from the previous phase;
- build, search, memory, incumbent, objective, bound, proof, and termination observations.

The report highlights the first phase at which each cost family grows superlinearly relative to
facilities, grid cells, or networks. It also reports the largest absolute delta. This allows the
project to answer questions such as:

- Did endpoint literals grow because one new facility has many placements and many compatible
  ports?
- Did a new item create an entire dense routing grid?
- Did one branch introduce splitter/converger candidates across every cell?
- Did network collision or bridge constraints introduce pairwise coupling?
- Did a graph cut become large enough that iterative SCC growth stopped providing a useful warm
  start?
- Is time spent constructing the model, finding the first incumbent, or proving an objective?

The direct full-graph run remains necessary. Cumulative growth is a strategy under test and cannot
be the only view of the target.

## Reduction And Architecture Experiment Catalog

Every strategy has one of three machine-readable classifications. A strategy may move to a safer
class only after its proof obligation is documented and tested.

### Semantics-Preserving / Proven-Safe

Candidates in this class must preserve every legal solution or provide an exact transformation
between original and reduced witnesses with the same objective vector.

- Remove placement-port values proven impossible by footprint, directional-port, transport, and
  request-bound constraints.
- Tighten integer flow, order, used-bound, and objective domains using sound lower and upper bounds.
- Remove component position/rotation values only when local topology and catalog rules prove that
  they cannot participate in any legal solution.
- Deduplicate identical constraint terms and eliminate variables algebraically fixed by hard
  constraints.
- Add redundant valid capacity, conservation, packing, or cut constraints that improve propagation.
- Replace dense variables with a sparse or symbolic exact formulation only when all legal grid paths
  remain representable.
- Apply solver presolve and solver-native exact search configuration.
- Decompose truly independent factor-graph components while combining their used geometry and
  lexicographic objective exactly.
- Decompose across a separator only when every interface state is represented exactly and the
  combination algorithm is complete.
- Use exact dynamic programming, branch-and-price, Benders-style decomposition, or another master
  and subproblem architecture only with a proof that no legal solution or objective vector is lost.

Each candidate needs a proof note, witness round-trip test, model-count delta, and small optimal
equivalence suite before it can be enabled outside experiments.

### Symmetry-Breaking Only

Candidates in this class remove only provably equivalent solutions.

- Lexicographically order truly interchangeable facility instances.
- Canonically order identical capacity-split lanes and identical terminals.
- Canonically choose among ports related by a proven facility/problem automorphism.
- Preserve the current canonical translation of used geometry.
- Break reflection or rotation symmetry only when the request rectangle, all facility and port
  semantics, external terminals, and objective are invariant under that transformation.
- Canonically label interchangeable commodity or logistics-component variables.

The proof obligation is an automorphism from every removed solution to a retained solution with an
identical objective and valid witness.

### Heuristic / Potentially Excludes A Legal Or Optimal Solution

These candidates are never automatically applied by the analysis layer or default solver. They may
appear only in explicitly enabled benchmark suites after user approval.

- Cropping the grid, active windows, corridors, or tighter bounds not supplied by the caller.
- Keeping only the nearest or top-ranked placement, rotation, or port candidates.
- Limiting route length, bends, component count, or distance from a prior phase.
- Freezing prior-phase placement, ports, routes, or components.
- Greedy, shelf, constructive, randomized, learned, or template-based placement/routing.
- Solving placement first and routing afterward without an exact complete combination method.
- Finalizing an SCC so later phases cannot move or reroute it.
- Dropping low-ranked commodity interactions or replacing exact shared flow with fixed pairings.
- A learned predictor that prunes domains or chooses a lossy decomposition.
- A weighted objective approximation that can change the accepted lexicographic order.

Heuristic results must report the exact strategy, excluded domain fraction, baseline comparison,
and lexicographic quality loss. “No solution found by the baseline within the budget” is not proof
that a heuristic result has zero quality loss.

## What The Solver May Stop Deciding

The harness is specifically intended to identify decisions that can be moved out of one monolithic
solve. There are three acceptable outcomes:

1. **Analytically fixed:** a value has one legal choice after sound propagation, so omitting its
   variable preserves semantics.
2. **Exactly decomposed:** a master or interface model represents every relevant interaction, and
   complete subproblems recover placement/routing choices without losing an objective vector.
3. **Experimentally delegated:** a heuristic chooses or removes values. This can be faster and may
   be worth adopting later, but it is not quality-preserving until measured evidence and explicit
   approval justify that tradeoff.

The intended research question is therefore not “how much can be removed from the solver?” It is
“which decisions create the observed coupling, and what is the smallest exact interface required
to preserve their effect on feasibility and objective quality?”

Examples of interfaces to investigate after measurement include:

- terminal placement and capacity summaries across an SCC frontier;
- per-commodity boundary flow states;
- occupied boundary cells and layer ownership;
- bounding-box contribution and packing envelopes;
- separator facility placements and port selections;
- exact route-column or route-row states for bounded-width decomposition.

None of these is accepted as an implementation architecture by this document. The analyzer will
show whether an interface is small enough to test and whether it captures the observed coupling.

## Benchmark Suite

### Workload Families

The suite uses externally declared workloads and scenarios.

1. **Micro optimum:** one facility with external inputs/outputs and a two-facility chain. Small
   enough to prove the full lexicographic optimum.
2. **Routing primitives:** directional-port gap, shared trunk, splitter, converger, belt/pipe
   coexistence, bridge crossing, and external terminal cases. Each isolates one formulation rule.
3. **Cycle cases:** a small seed or byproduct cycle and a multi-facility cyclic SCC.
4. **Heavy Xiranite growth:** every cumulative SCC phase derived from the fixed production graph.
   These phases are observations of the real graph, not handcrafted replacements for it.
5. **Heavy Xiranite full graph:** the primary end-to-end target, including a direct full-graph solve.

Micro and primitive cases require proven optimum or the strongest available proof and serve as
quality baselines. Larger cases may legitimately end with a validated incumbent, bound, timeout,
or `unknown`.

### Scenario Identity

A benchmark case identity includes:

- workload and source-data hashes;
- recipe/source-plan selections;
- graph projection or cumulative SCC phase;
- explicit request width and height;
- formulation and strategy IDs;
- solver configuration;
- search budget and outer process resource limits;
- repetition index.

The Heavy Xiranite workload is stable across scenarios. Trying several bounds does not create
several definitions of the baseline recipe.

### Budgets And Repetition

Initial search checkpoints are 100 ms, 500 ms, 1 second, and 5 seconds. Because the current solver
adapter does not expose a reliable callback snapshot at arbitrary times, the first harness runs an
isolated fresh process for each budget. It records model construction separately and applies a
larger outer wall-clock limit to catch construction hangs or process failure.

Each small or medium case is repeated enough to expose variability; the initial default is five
runs when runtime permits. Large Heavy Xiranite scenarios may use fewer repetitions under an
explicit suite resource budget. Reports show individual runs, median, range, and timeout rate. A
single lucky incumbent is not presented as typical behavior.

### Required Comparison Fields

For every baseline or strategy/budget pair, the runner records:

- model build time;
- first validated feasible time;
- objective at 100 ms, 500 ms, 1 second, and 5 seconds through separate budgeted runs;
- best bound and active objective stage when available;
- optimality gap when validly computable;
- final objective vector;
- lexicographic solution-quality loss against the exact baseline;
- variable, domain-volume, incidence, and constraint reductions;
- peak memory and termination distribution.

Solution-quality loss is lexicographic, not a weighted scalar. The report identifies the first
objective component that differs, then gives absolute and relative deltas for that component and
all later components. A strategy that improves a later component while worsening an earlier one is
reported as worse.

## Experiment Matrix

The experiment runner evaluates:

```text
workload
  x graph phase or full graph
  x explicit layout-bound scenario
  x formulation/strategy
  x search budget
  x repetition
```

The initial matrix contains only the unchanged baseline. Safe reductions and symmetry breakers are
added one at a time and then in explicitly named combinations. This permits attribution of model
and runtime changes. Heuristic strategies, when approved, are placed in a separate suite and never
replace the baseline rows.

Every comparison checks:

- identical normalized input hashes;
- identical legal-solution and objective contract for safe strategies;
- identical validation rules;
- instrumentation mode and overhead;
- whether both runs reached comparable proof stages.

## Complexity Prediction And Strategy Selection

The first analysis release does not collapse all metrics into an invented “complexity score.” It
stores raw features and outcomes. After enough benchmark data exists, offline analysis will test:

- rank correlation between each feature and build time, first feasible time, memory, and proof time;
- censored outcomes, where timeout means only that the event exceeds the budget;
- small interpretable models using log-scaled counts and interaction terms;
- prediction stability across workload families and formulation versions;
- whether phase-growth deltas predict the first intractable Heavy Xiranite phase better than total
  counts.

Candidate predictors include routing cells times networks, endpoint options, crossing constraints,
factor incidences, maximum degree, placement-routing cross incidences, symmetry-group log size, SCC
size, and frontier cut size. Their value is determined empirically rather than assumed.

The first strategy selector is shadow-only. It emits:

```text
predicted difficulty
supporting metrics
candidate semantics-preserving strategies
confidence and training-data coverage
what it would choose
```

It does not alter the requested solve. Automatic selection among proven-equivalent exact
formulations may be proposed after reproducible evidence and user approval. A heuristic choice
always requires an explicit opt-in policy even if a predictor expects it to be faster.

## Failure And Overhead Handling

- If IR analysis overflows checked arithmetic, report `analysis-domain-overflow` and do not emit a
  misleading estimate.
- If full factor-graph retention exceeds its analyzer ceiling, preserve summary metrics and emit
  `factor-graph-detail-skipped`.
- If model construction times out or exhausts memory, the isolated process records the last
  completed analysis stage and exits without claiming search failure.
- If search ends without an incumbent, preserve model metrics, active stage, bound if available,
  and the exact termination reason.
- If an incumbent fails validation, record the artifact for debugging but never use it as a quality
  baseline.
- Instrumentation overhead is measured by paired instrumented/uninstrumented micro runs. If full
  incidence capture distorts results, production benchmark runs use summary mode and separate
  diagnostic runs use full-small mode.
- Reports from different schema or formulation versions are not combined silently.

## Stress Tests For The Framework

1. **Loose request bounds:** one facility under increasingly large ceilings must reveal dense-grid
   growth without treating the ceiling as used footprint.
2. **Same variable count, different domains:** verifies that domain metrics distinguish Boolean and
   large integer models.
3. **Same counts, different coupling:** disconnected and highly connected networks verify factor
   metrics.
4. **Port ambiguity:** equal facility counts with different compatible directional ports isolate
   endpoint-choice growth.
5. **Network introduction:** adding one new item should expose the incremental cost of a full routing
   network.
6. **Branch/crossing introduction:** isolates component and network-collision constraint growth.
7. **Interchangeable facilities and lanes:** validates symmetry detection without changing the
   solution set.
8. **Cycle SCC:** verifies atomic cycle reporting and frontier cuts.
9. **Analyzer ceiling:** a deliberately large factor graph must degrade to summaries without
   changing the solve model.
10. **Unproven timeout:** verifies that missing bounds and gaps remain null and are not reported as
    infeasibility.

## Rejected Shortcuts

- Using variable count alone as the complexity model: it hides domains, arity, and coupling.
- Treating log-domain volume as the true legal search space: constraints make that interpretation
  false.
- Defining Heavy Xiranite by one chosen grid size: bounds are scenario inputs.
- Automatically applying a crop or constructive layout when the analyzer predicts timeout: this
  deletes the research subject.
- Calling a phase successful because it produces any placement before routing: the authoritative
  baseline is joint and independently validated.
- Freezing prior SCC results to make later phases small: this can remove the optimum and even all
  feasible layouts.
- Building a second copy of formulation counting logic: it will drift from the authoritative model.
- Choosing a single reduction before collecting a baseline growth profile: it prevents causal
  attribution.

## Completion Criteria

This design is implemented when the project can:

1. reproduce the exact Heavy Xiranite workload identity under multiple explicit bound/resource
   scenarios;
2. produce a phase-by-phase report even when phase zero or model construction fails;
3. attribute growth to domains, constraint families, graph structure, symmetry, and actual
   placement-routing coupling;
4. compare estimates with the model actually constructed;
5. run isolated budgeted experiments and retain partial evidence;
6. establish proven small-case baselines and report lexicographic quality loss honestly;
7. classify every tested reduction as safe, symmetry-only, or heuristic;
8. identify evidence-backed decomposition interfaces and solver responsibility choices without
   silently adopting them;
9. produce a shadow strategy recommendation that leaves the requested solve unchanged.

The first useful deliverable is earlier: after Slice 5, the project should be able to explain where
the Heavy Xiranite search first explodes, which model families cause it, and whether the dominant
cost is construction, first-feasible discovery, or optimization proof. That evidence determines
what exact or heuristic architecture should be tested next.
