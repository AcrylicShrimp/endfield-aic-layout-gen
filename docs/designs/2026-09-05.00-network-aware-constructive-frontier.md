# Network-Aware Constructive Frontier

## Status

Proposed next production-planner slice. This contract is not implemented yet.

The measured input is the capacity-valid Heavy Xiranite constructive-growth result at commits
`49831d1` and `9fd989e`. The supporting measurements and generated layout are stored in
`docs/benchmarks/constructive-growth-cliff-diagnosis/`.

Branch topology follows `docs/designs/aic-game-rules-mathematical-model.md`: an ordinary line cell
cannot fork or merge, and splitter/converger definitions, rotations, arms, and capacities come from
the validated external logistics-component catalog.

## Why This Slice Exists

The current constructor represents every logical production-graph edge as an independent
point-to-point physical route. When it connects one edge, it consumes one or more facility ports
and creates separate `TransportNetwork` values. Every still-unresolved edge must then retain at
least one unused compatible facility-port option.

That rule is deliberately conservative, but it is not the accepted factory-network semantics.
Logical edges describe material supply and demand. Compatible edges may use the same physical
port and trunk when the shared physical segments have enough transport capacity.

A minimal fan-out illustrates the mismatch:

```text
Current point-to-point interpretation:

producer OUT-0 ------> consumer B
producer OUT-1? -----> consumer C

If OUT-1 does not exist or is blocked, the second logical edge is rejected.

Accepted commodity-network interpretation:

producer OUT-0 ---- [splitter] ----> consumer B
                         |
                         +----------> consumer C

The producer port and common trunk are shared. Each consumer still uses its own input port.
```

This is not free duplication of throughput. Sharing is legal only while the load on every shared
segment remains within the runtime line capacity.

## Measured Evidence

The release-mode twelve-step Heavy Xiranite probe accepts eleven steps and then stops with a valid
partial factory containing 28 facilities and 27 capacity-valid point-to-point networks in `68x16`
used bounds. The exhausted frontier produces the following composition work:

| Event | Count |
| --- | ---: |
| Rigid placements considered | 41,502 |
| Facility collisions rejected | 28,244 |
| Port pairs considered | 592,269 |
| A* calls | 505,325 |
| A* calls with no route | 216,173 |
| Complete lane bundles rejected by the per-edge boundary rule | 186,951 |
| Successful A* calls in incomplete multi-lane branches | 102,201 |
| Complete bundles rejected by grouped capacity | 0 |
| Complete bundles rejected by geometry validation | 0 |
| Valid composition candidates | 0 |

The final four A* categories account for every A* call:

```text
216,173 + 186,951 + 102,201 = 505,325
```

The immediate cliff is therefore not merely slow pathfinding. A large set of complete lane
bundles reaches the post-route check and is rejected because some other logical boundary edge has
no separate unused port left. These bundles are not proven complete-factory solutions: the current
representation cannot yet prove that the unresolved demand can attach to the routed network with
sufficient residual capacity. The result identifies a missing constructive capability and an
overly narrow boundary DTO, not permission to delete validation.

## Terms

- **Logical requirement:** one production-graph supply-to-demand edge with an item, rate, and
  transport kind.
- **Commodity network:** the physical belt or pipe network used by compatible logical requirements
  for one item and one transport kind.
- **Trunk:** a physical segment shared by more than one logical requirement.
- **Branch:** the route from a trunk to one additional supply or demand terminal.
- **Residual capacity:** the unused capacity on a physical segment after summing the rates assigned
  to that segment.
- **Boundary requirement:** an unresolved connection between the already constructed subgraph and
  a facility outside it.
- **Boundary attachment:** a concrete way to keep a boundary requirement constructible. It may be
  an unused compatible facility port or a catalog-valid splitter/converger attachment to a
  compatible existing commodity network without exceeding capacity.
- **Attachment anchor:** an existing network cell that can be replaced by a catalog-valid branch
  component, or an existing compatible branch component with a free arm. A plain line cell or
  facility terminal is not itself a legal branch point.

For a segment `s` with runtime line capacity `C` and logical requirements `R(s)` using that segment:

```text
load(s) = sum(rate(r) for r in R(s))
residual(s) = C - load(s)
legal(s) iff load(s) <= C
```

Residual capacity is segment-local. A network with spare capacity on one branch can still have a
full upstream trunk, so a single network-wide number is insufficient for final validation.

## Current Contract Mismatch

`ConstructiveProcessModuleBoundary` currently stores:

```text
requirement
item
transport
rate
direction
inside_instance
port_options[]
```

It can say only, "this unresolved edge may use one of these currently unused facility ports." It
cannot say, "this unresolved edge may join network N through a catalog-valid branch-component
anchor, and the shared path still has enough capacity."

`combine_nodes` removes consumed or geometrically blocked port options and rejects the candidate
immediately when any individual boundary has an empty `port_options` list. Only afterward does it
run the capacity-grouped port-demand analysis. This ordering and representation explain the
`186,951` post-route rejections in the measured frontier.

## Proposed Stage Contract

### Input

The network-aware composition stage receives:

- two individually valid constructive nodes;
- the logical requirement currently joining them;
- all unresolved boundary requirements from both nodes;
- existing routed commodity networks and their segment loads;
- the validated runtime transport catalog and logistics-component catalog;
- fixed facility, belt-layer, pipe-layer, and logistics-component occupancy;
- the normal bounded candidate-search budget.

### Decisions

For the current connection and every boundary whose old unused-port support disappears, the stage
may select one of two attachment families:

1. **New-port attachment:** use a distinct unused compatible facility port and create the required
   capacity-bounded lane or lanes.
2. **Existing-network attachment:** join a network with the same item and transport kind at a
   directionally reachable attachment anchor. A new consumer branch inserts or reuses a
   catalog-valid splitter; a new producer branch inserts or reuses a catalog-valid converger. The
   stage routes only the new branch and reserves capacity on every shared and added segment.

An ordinary transport cell may be replaced by a branch component only when the component's kind,
transport, rotation, arm directions, footprint, and capacity all match the resulting topology.
The stage must not model an unplaced logical junction and add the component afterward.

The implementation DTO should use a discriminated attachment type rather than overloading
`port_options`. Exact Rust names are intentionally left to the implementation slice, but the
observable alternatives must remain explicit in reports.

### Output

On success, composition returns one valid `ConstructiveNode` containing:

- merged facility placements;
- commodity networks normalized by item and transport kind;
- every logical requirement assigned to a network;
- terminal-to-port assignments;
- explicit logistics-component placements with catalog component IDs, positions, and rotations;
- per-segment load sufficient to recompute residual capacity;
- updated unresolved boundaries with all currently realizable attachment alternatives;
- actual used bounds and the existing lexicographic composition score;
- structured statistics for new-port and existing-network attempts.

The statistics contract includes at least `new_port_attempts`, `existing_network_attempts`,
`attachment_anchors_considered`, `splitter_candidates_considered`,
`converger_candidates_considered`, `attachment_capacity_rejections`,
`component_topology_rejections`, `branch_route_failures`, and
`network_attachment_candidates_validated`.

On failure, the report uses stage `constructive-planner`, severity `error`, and one of these stable
codes:

| Code | Meaning |
| --- | --- |
| `constructive-network-attachment-unavailable` | No compatible unused port or catalog-valid network attachment exists. |
| `constructive-network-attachment-capacity-insufficient` | A compatible network exists, but no candidate anchor and shared path has sufficient capacity. |
| `constructive-network-branch-route-unavailable` | A valid branch component can be selected, but the new branch cannot be routed. |
| `constructive-network-attachment-geometry-invalid` | The candidate branch component, route, terminal, or occupied layers fail independent geometry validation. |
| `constructive-network-attachment-budget-exhausted` | The bounded local candidate search ended before finding an accepted attachment. |

Each diagnostic path identifies the affected boundary requirement, and `entity` names the network,
facility instance, or component candidate when one is available.

A failure remains a constructive dead end, not proof that the complete factory is infeasible.

### Hard Cutover

The implementation adds required `--logistics-component-catalog` input to the constructive process
module, composition, recursive assembly, and automatic assembly CLI commands. It also adds
`logistics_components: Vec<PlacedLogisticsComponent>` to `ConstructiveNode` and replaces the
`port_options`-only boundary contract with the discriminated attachment DTO. Every report schema
that embeds either changed DTO must increment its schema version in the same slice. There is no
empty-catalog default, legacy boundary adapter, or silent conversion of old serialized reports.

## Required Invariants

1. Only equal item IDs and equal transport kinds may share a commodity network.
2. Belt and pipe occupancy remain separate layers.
3. A facility footprint blocks both transport layers.
4. Every facility terminal uses a compatible port with the correct input/output direction.
5. Different consumer facilities still require their own input terminals and ports. Sharing a
   producer trunk does not erase consumer terminals.
6. The sum of assigned rates on every physical segment must not exceed that segment's runtime line
   capacity.
7. Ordinary transport cells have at most one incoming and one outgoing arm. Fan-out and merge use
   explicit catalog-valid splitters and convergers with allowed rotations and flow-conserving arm
   topology.
8. A branch component and every new branch must be physically contiguous with the selected existing
   network and facility terminal. Component aggregate flow must not exceed catalog capacity.
9. Same-layer physical conflicts remain illegal unless represented by a catalog-valid logistics
   component; its occupied cell participates in normal collision checks.
10. Composition is transactional: the prior valid node remains unchanged unless the expanded node
   passes independent validation.
11. Candidate scoring remains area first, transport tiles second, and route turns third. Network
    reuse is a capability, not a higher-priority score that may enlarge the factory.

## Narrow Implementation Sequence

The cutover should stay bottom-up and produce an inspectable HTML result after each accepted slice.

1. Add a controlled one-producer/two-consumer fixture where both logical demands fit one line.
   Load the external logistics-component catalog, preserve the current point-to-point result as a
   comparison, then place a catalog-valid splitter so one output port and trunk serve both
   consumers.
2. Add segment load and residual-capacity reporting. Independently validate every segment sum.
3. Replace boundary `port_options`-only reasoning with explicit new-port and existing-network
   attachments for the controlled fan-out. The latter must identify its attachment anchor and
   selected component placement.
4. Add a capacity-overflow fixture where the combined rate does not fit one trunk. It must create a
   second physical lane or reject that attachment; it must never silently overload the first line.
5. Add the symmetric same-item merge fixture for multiple producers feeding one consumer, if the
   game-data port and direction contract permits that topology.
6. Re-run the exact twelve-step Heavy Xiranite command from the benchmark report. Compare the same
   frontier counters and inspect every accepted HTML growth page.
7. Only after this cliff is remeasured, decide whether bounded rollback or multi-path lane-bundle
   enumeration is the next blocker.

## Acceptance Criteria

The first production slice is accepted when all of the following hold:

- the controlled fan-out uses one compatible trunk without exceeding capacity;
- the fan-out contains an explicit catalog-valid splitter; no ordinary cell or facility terminal
  acts as an implicit branch;
- the overload control cannot place excessive flow on a shared segment;
- existing single-edge and two-lane capacity tests still pass;
- the independent constructive validator accepts every committed result;
- the report exposes attachment type, network identity, component ID/rotation, segment load,
  capacity, and residual;
- generated HTML makes the shared trunk and both terminal rates inspectable;
- the Heavy Xiranite frontier is remeasured with the same release target and prior data inputs,
  plus the explicit external logistics-component catalog;
- constructive CLI commands load that catalog through `--logistics-component-catalog`;
- no old exact-solver path is introduced into production planning.

Success on the controlled fixture does not imply that the full Heavy Xiranite factory will finish.
The Heavy Xiranite rerun determines whether this contract mismatch was the active cliff or merely
reveals the next one.

## Non-Goals

This slice does not add global optimality, a global CP solve, unrestricted backtracking, trunk
resynthesis, rip-up-and-reroute, or general local improvement. It also does not optimize A* before
fixing the boundary representation that currently rejects complete routed bundles.

The known secondary issue remains: multi-lane enumeration asks A* for only one shortest path per
endpoint pair. The first chosen lane may block a later lane even when an alternate first path would
complete the bundle. Address that only if the network-aware rerun shows it as the next measured
cliff.

constructive CLI does not load that catalog and cannot produce a legal branch. The implementation
cutover must add the required CLI input. Its Heavy Xiranite remeasurement uses the same command
with this additional argument:

```bash
--logistics-component-catalog data/game/normalized/logistics-components.json
```

That post-cutover command is not expected to parse at this design-only commit.

The observed wall time is host-local evidence, not a stable performance assertion. The failure
stage, counters, last valid state, and generated artifacts are the durable reconstruction record.
