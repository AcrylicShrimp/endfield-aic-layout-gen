# Throughput Request V3 Producer Selections

## Scope

Throughput request schema version 3 adds an explicit recipe-selection boundary before dependency graph resolution. This is a hard cutover from version 2: every request must use `schema_version: 3` and include `producer_selections`, which may be empty.

The spatial solver still never chooses recipes. A successful selection check produces a fixed recipe graph for throughput calculation, facility expansion, placement, and routing.

## Input Contract

```json
{
  "schema_version": 3,
  "target": {
    "item": "item-xiranite-enr-powder",
    "quantity": 1,
    "duration_ms": 10000
  },
  "external_inputs": [],
  "producer_selections": [
    {
      "item": "item-xiranite-enr-powder",
      "recipe": "xiranite-oven-xiranite-enr-powder-1"
    }
  ]
}
```

Each selection binds one produced item to one recipe. Item and recipe IDs must be stable IDs. Selection items must be unique, cannot also be request-level external inputs, and must name a recipe that produces the selected item.

## Selection Check Contract

`aic recipes check-selections --file <recipes.json> --request <request.json>` runs before graph resolution. Its report contains:

- `ready`: whether graph resolution may proceed;
- `status`: `ready`, `selection-required`, or `invalid-input`;
- `producer_selection_groups`: currently reachable ambiguous items that need a choice;
- structured diagnostics owned by the `recipe-selection-check` stage.

Each selection group contains the ambiguous item and complete recipe option DTOs. Every option exposes its recipe ID, facility ID, input amounts, output amounts, and duration so a web client can render a choice without parsing human-readable diagnostic messages.

The check traverses unique and explicitly selected producers. When it reaches an unselected ambiguous item, it reports that frontier group and does not explore behind its alternatives. Independent ambiguous inputs at the same reachable frontier are returned together. After the caller submits selections, running the check again reveals any ambiguity newly reachable behind those choices.

`selection-required` is a successful check result rather than malformed input. The standalone command exits successfully so an API caller can treat the report as a normal user-interaction state. Throughput and later pipeline stages stop until `ready` is true.

## Invariants

- External-input cutoffs take precedence over recipe traversal.
- A reachable item with one producer is selected automatically.
- A reachable item with multiple producers requires an explicit selection.
- Graph resolution starts only after the selection check reports `ready`.
- Graph resolution retains its ambiguity error as an internal safety invariant, not as the normal discovery mechanism.
- Recipe option ordering and selection-group ordering are stable by ID.

## Diagnostics

- `producer-selection-required`: a reachable ambiguous item needs a selection;
- `invalid-producer-selection-item-id`;
- `invalid-producer-selection-recipe-id`;
- `duplicate-producer-selection`;
- `external-input-producer-selection-conflict`;
- `unknown-producer-selection-item`;
- `unknown-selected-recipe`;
- `selected-recipe-output-mismatch`;
- `unknown-target-item`.
