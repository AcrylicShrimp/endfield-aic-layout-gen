# Same-Server CPU and CUDA Pilot Comparison

Status: implementation and experiment authorized on 2026-09-07.

Run under `/home/ashrimp/Srv/endfield-aic-layout-gen` on the user's Arch Linux server,
accessed through SSH. Keep the existing fixed factory, model dimensions, seed 17, PPO
hyperparameters, 65,536 commands, 4,096 updates, and five 32-rollout evaluation checkpoints.
Keep all generated logs, checkpoints, and figures in ignored `artifacts/`.

## Execution contract

The existing `device` configuration accepts `cpu` or `cuda`. It selects the PPO learner's
device. The environment, independent factory validation, observation/candidate construction,
and action sampling remain on CPU. A CPU policy snapshot supplies all rollout actions and
evaluation; refresh it after every completed CUDA update before collecting more observations.
The CPU path uses the learner itself. This avoids a device transfer for every environment
command and preserves a frozen behavior policy throughout each on-policy rollout.

Use float32 without AMP or TF32 for this first comparison. CUDA availability and device
identity must be explicit; unavailable CUDA is an error, never a CPU fallback. Record the
CUDA runtime, GPU name, configured precision, learner and actor devices, peak CUDA allocation,
and CUDA RNG state in retained metadata/checkpoints. CPU/CUDA numerical trajectories may
diverge; do not require identical trained weights or infer learning superiority from one seed.

Measure CPU preparation/validation, model inference, learner updates, and snapshot transfers
separately. GPU work is asynchronous: device timing must use CUDA events or synchronization,
never label host dispatch time as completed GPU computation. Include transfer and bookkeeping
costs in the end-to-end update clock. Preserve finite-loss/gradient checks.

## Comparison and acceptance

Run the same source/environment on the server with CPU and CUDA learners sequentially.
First select server CPU threads using the retained fixed-input benchmark; the Mac's four-thread
setting is not assumed optimal here. Also compare CPU and CUDA updates on identical saved
observations, weights, optimizer state, and minibatch order to separate kernel performance
from diverging training trajectories. A benchmark checkpoint is an explicit external input,
never hidden training data or a source fixture.

Verify finite CPU/CUDA loss and gradients, close outputs on the same padded observations,
correct CPU snapshot refresh, and complete acceptance of exported layouts. Show both outcome
and reward curves, including failure to learn if it occurs. Report full training and evaluation
times, Python-side work, and fixed-input update times separately. Language migration of the
environment is outside this comparison; the user's Mojo suggestion is a future profiling-led
option, not authorization to mix a second implementation change into the device comparison.

The pre-run CPU matrix covered 1/2/4/8/16 threads, followed by a paired 16/24-thread check.
Twenty-four threads won the latter (0.152 s update, versus 0.170 s at 16). The CPU and CUDA
full-run configs both use 24 threads to keep the actor/environment execution setting matched.
The GPU fixed-input update at 24 threads took 0.064 s. Warm-up and repeated-run timing spread
are retained with the raw records; these short timings do not predict total training time.
