# Parallel on-policy experience collection

## Status and scope

Proposed next implementation slice following the user's request to collect more
training experience in parallel. Report 30's frozen training audit and registered
evaluation continue unchanged. Do not launch this timed study alongside them.
This contract is not an implemented worker pool or a measured speedup.

Start with concurrent collection of the existing four-episode update group.
Keep the relative-return objective, group size, 32-action horizon, sampling
distribution and one optimizer step per group unchanged. Increasing total training
experience or episode horizon requires a separate study configuration and analysis.

## Inputs and outputs

The coordinator supplies one immutable behavior-policy checkpoint and hash, the
frozen runtime/catalog/configuration identities, reset case, group identifier,
four explicit attempt/seed pairs, a fresh output directory, worker count from
`1, 2, 4`, and declared episode, group and study resource bounds.

Each worker owns its runtime, episode state, random generator and attempt directory.
It returns the existing episode summary and retained trace/state/best artifacts,
plus attempt identity, behavior-policy hash, worker identity and timing. Workers
must not update parameters or write shared progress/checkpoint files. The
coordinator records results in attempt order regardless of completion order.

Report requested and completed episodes/actions, worker count, group collection
wall time, gradient-replay/update time, total group time, actions per wall second,
worker failures and resource-bound termination. Measure total worker/coordinator
memory with an explicitly named method; observation-array bounds are not RSS bounds.
Retain source identities and the original group/episode evidence.

## Invariants and failures

All four episodes use the same policy version and reset case. Compute relative
returns only after all four complete, then replay gradients in the original
attempt/action order and apply one update. Do not overlap the next policy version's
collection with this update. A persistent process pool may reuse processes, but
must reset runtime caches, episode history, seeds and policy state explicitly.

Reject duplicate/missing attempt identities, policy/source mismatches and
incomplete episodes. On failure, apply no partial-group update, stop and reap owned
workers, preserve completed and partial evidence, and keep the previous checkpoint
and valid incumbents. Do not replace failed or slow samples with fresh draws.
Diagnostics must include a stable code, severity, stage, group/attempt reference
and underlying cause. Proposed codes are `on-policy.worker-failed`,
`on-policy.worker-identity`, `on-policy.group-incomplete` and
`on-policy.parallel-resource-bound`.

The worker's episode clock includes its assigned startup and environment work;
the group/study clock also charges dispatch, queueing and cleanup. Concurrent
contention may change time-bound outcomes and must be reported rather than hidden.
Assign a bounded CPU thread count per worker and prevent library oversubscription.
Memory pressure or timeout is not evidence of factory infeasibility.

This is on-policy collection. Retaining more old episodes does not authorize their
reuse as fresh gradients after the policy changes. Asynchronous stale-policy
learning or off-policy replay would change the algorithm and need another contract.

## Verification and measurement

Before a larger training run, compare worker counts 1, 2 and 4 using frozen policy,
case and attempt seeds with nonbinding wall limits. Compare selected actions,
probabilities, physical state/best hashes, terminal scores, relative returns and
the resulting optimizer checkpoint in fixed accumulation order. Time fields and
process identities are excluded from semantic equality. Exercise a worker failure
and incomplete episode: no update may occur and all owned processes must terminate.

Measure the matrix without unrelated timed work. Keep group size and action count
fixed so concurrency is the changed variable. Choose worker count using measured
throughput and memory, not hardware core count alone. Then register a larger
experience-budget study with initial/checkpoint comparisons. Any prospective case
opened by report 30 must be disclosed as previously evaluated in that later study.

## Existing cost evidence

The random arm recorded 5288.906 seconds across 64 complete groups, including
2919.401 seconds of sequential episode collection. The remaining 2369.505 seconds
include gradient replay and other group work; this is not an isolated gradient
benchmark. With zero overhead and perfectly four-way collection, keeping the
remainder unchanged would yield about 1.71 times group throughput, not four times.
This is an arithmetic illustration, not a prediction or benchmark result.
The current machine reports 10 physical/logical CPUs and 24 GiB memory, which
supports testing a bounded pool but does not establish safe per-worker RSS.

## Completion criteria and activity

This slice completes only when the bounded collector is implemented, semantic and
failure checks pass, the isolated throughput/memory comparison is recorded, and
the chosen execution mode supports a separately frozen larger-experience study.
It does not establish learned factory improvement by itself.
