# Logical Facility Instance Wiring

## Design Goal

Define milestone 4B: expand aggregate recipe-level wiring into logical facility-instance-level wiring.

This stage introduces recipe-dedicated facility instances, but it does not introduce facility catalog data, physical ports, belts, pipes, coordinates, rotations, or layout geometry.

## Pipeline

```text
RecipeThroughputReport
  + FacilityRequirementReport
  + RecipeWiringGraphReport
  -> FacilityInstanceWiringReport
```

The stage consumes successful reports from earlier stages. It does not load recipe JSON, validate recipe books, calculate throughput, calculate facility requirements, or rebuild the recipe-level wiring graph.

The CLI command that reaches this stage may still run earlier pipeline steps. Earlier failures are reported by their owning stage before instance wiring runs.

## Input Invariants

A successful input set must satisfy these invariants:

- `RecipeThroughputReport.success` is `true`.
- `FacilityRequirementReport.success` is `true`.
- `RecipeWiringGraphReport.success` is `true`.
- `RecipeThroughputReport.target` is present.
- facility requirements contain exactly one requirement for each recipe in `RecipeThroughputReport.recipe_rates`.
- every facility requirement recipe has the same facility ID as the corresponding recipe throughput rate.
- every facility requirement work rate matches the corresponding recipe throughput work rate.
- every facility requirement count matches `ceil(work_seconds_per_second)`.
- every recipe-level wiring endpoint references a known recipe or a known logical endpoint from the throughput report.
- every recipe-level wiring edge kind matches the kind implied by its source and target endpoint pair.
- every recipe-level wiring edge rate is treated as the aggregate source of truth for this stage.

Malformed direct library inputs produce instance-wiring-stage failure reports.

## Instance Model

Facility instances are recipe-dedicated. A facility instance never runs more than one recipe and is never shared across recipes.

Facility instance IDs use this format:

```text
facility-instance:<recipe>:<index>
```

`index` is zero-based and scoped to the recipe. Recipe IDs are stable kebab-case IDs, so the colon separator is reserved for this graph namespace.

For a recipe with `required_facilities = N`, the stage creates `N` facility nodes:

```json
{
  "kind": "facility",
  "id": "facility-instance:grind-originium-powder:0",
  "recipe": "grind-originium-powder",
  "facility": "grinding-unit",
  "index": 0,
  "runs_per_second": { "numerator": 1, "denominator": 5 },
  "work_seconds_per_second": { "numerator": 2, "denominator": 5 },
  "unused_capacity": { "numerator": 3, "denominator": 5 }
}
```

For `N > 0`, per-instance rates are evenly divided:

```text
instance_runs_per_second = recipe_runs_per_second / N
instance_work_seconds_per_second = recipe_work_seconds_per_second / N
instance_unused_capacity = 1 - instance_work_seconds_per_second
```

When `N = 0`, no facility instances are created for that recipe.

## Logical Endpoints

External sources, target sinks, and surplus sinks remain logical non-facility endpoints.

Node variants:

- `facility`: recipe-dedicated facility instance; fields are `kind`, `id`, `recipe`, `facility`, `index`, `runs_per_second`, `work_seconds_per_second`, `unused_capacity`
- `external`: externally supplied item source; fields are `kind`, `id`, `item`
- `target`: requested target item sink; fields are `kind`, `id`, `item`
- `surplus`: surplus item sink; fields are `kind`, `id`, `item`

Logical endpoint ID formats are the same as recipe-level wiring:

- `external:<item>`
- `target:<item>`
- `surplus:<item>`

## Edge Splitting

Each recipe-level wiring edge is expanded into one or more instance-level wiring edges. Each expanded edge carries exactly one item and an exact rate.

Endpoint expansion rules:

- external to recipe: split the aggregate edge rate evenly across target recipe instances.
- recipe to target: split the aggregate edge rate evenly across source recipe instances.
- recipe to surplus: split the aggregate edge rate evenly across source recipe instances.
- recipe to recipe: use balanced linear split across source recipe instances and target recipe instances.
- external to target: keep a single logical edge.

Balanced linear split for recipe-to-recipe edges:

1. Let `R` be the aggregate edge rate.
2. Let `S` be the source recipe instance count.
3. Let `T` be the target recipe instance count.
4. Each source instance supplies `R / S`.
5. Each target instance demands `R / T`.
6. Walk source instances and target instances in ascending index order.
7. Emit an edge with `min(source_remaining, target_remaining)`.
8. Advance a source when its remaining supply is zero.
9. Advance a target when its remaining demand is zero.
10. Stop when all source supply and target demand are consumed.

This produces deterministic, compact edges while preserving the aggregate rate. It is not a physical routing plan.

Successful reports use this shape:

```json
{
  "success": true,
  "nodes": [
    {
      "kind": "external",
      "id": "external:originium-ore",
      "item": "originium-ore"
    },
    {
      "kind": "facility",
      "id": "facility-instance:grind-originium-powder:0",
      "recipe": "grind-originium-powder",
      "facility": "grinding-unit",
      "index": 0,
      "runs_per_second": { "numerator": 1, "denominator": 2 },
      "work_seconds_per_second": { "numerator": 1, "denominator": 1 },
      "unused_capacity": { "numerator": 0, "denominator": 1 }
    },
    {
      "kind": "target",
      "id": "target:originium-powder",
      "item": "originium-powder"
    }
  ],
  "edges": [
    {
      "source": "external:originium-ore",
      "target": "facility-instance:grind-originium-powder:0",
      "kind": "external-input",

      "item": "originium-powder",

    {
      "stage": "facility-instance-wiring",
      "severity": "info",
      "code": "facility-instance-wiring-built",
      "path": "/",

    }
  ]
}
```

Failure reports use the same top-level `FacilityInstanceWiringReport` shape with `success: false`, empty node and edge arrays, and at least one error diagnostic.

## Diagnostics

Every instance wiring diagnostic has this shape:

```json
{
  "stage": "facility-instance-wiring",
  "severity": "error",
  "code": "missing-facility-requirement",
  "path": "/recipe_requirements",
  "entity": "grind-originium-powder",
  "message": "recipe 'grind-originium-powder' has no facility requirement"
}
```

`stage` is always `facility-instance-wiring`.

`severity` is `info`, `warning`, or `error`.

`code` is a stable kebab-case diagnostic code.

`path` is a JSON pointer into the input report or output report when possible.

`entity` is an optional stable ID for the recipe, item, facility, or node most relevant to the diagnostic.

`message` is human-readable and not a stable programmatic key.

## Failure Modes

Instance-wiring-domain failures produce `FacilityInstanceWiringReport` with `success: false`.

- `upstream-throughput-failed`: input throughput report has `success: false`
- `upstream-facility-requirements-failed`: input facility requirement report has `success: false`
- `upstream-recipe-wiring-failed`: input recipe wiring report has `success: false`
- `missing-target`: input throughput report has `success: true` but `target` is `null`
- `duplicate-facility-requirement`: more than one facility requirement exists for one recipe
- `missing-facility-requirement`: a recipe throughput rate has no facility requirement
- `unexpected-facility-requirement`: a facility requirement references no throughput recipe
- `facility-id-mismatch`: a facility requirement does not match the throughput recipe facility ID
- `facility-work-rate-mismatch`: a facility requirement does not match the throughput recipe work rate
- `facility-count-mismatch`: a facility requirement count does not match the expected ceiling of the work rate
- `unknown-wiring-endpoint`: a recipe-level wiring edge references an unknown node
- `edge-kind-mismatch`: a recipe-level wiring edge kind does not match its endpoint pair
- `missing-facility-instances`: a recipe-level wiring edge needs recipe instances, but the recipe has none
- `arithmetic-overflow`: exact rate arithmetic overflowed while splitting edges

## CLI Failure Priority

The `recipes instance-wiring` command uses this priority:

1. Load and parse the recipe file. File access and JSON parse errors are normal CLI errors.
2. Load and parse the throughput request JSON. Request JSON shape errors print `RecipeThroughputReport` with `success: false`.
3. Validate request schema version, target ID, quantity, and duration. Request field errors print `RecipeThroughputReport` with `success: false`.
4. Validate and promote the recipe book. Recipe data errors print `ValidationReport`.
5. Calculate throughput. Throughput-domain failures print `RecipeThroughputReport` with `success: false`.
6. Calculate facility requirements. Facility-domain failures print `FacilityRequirementReport` with `success: false`.
7. Build recipe-level wiring graph. Recipe-wiring-domain failures print `RecipeWiringGraphReport` with `success: false`.
8. Build facility-instance wiring. Instance-wiring-domain failures print `FacilityInstanceWiringReport` with `success: false`.

Any report with `success: false` maps to a failure exit status.

## Ordering Guarantees

Node ordering:

1. external nodes sorted by item ID
2. facility instance nodes in throughput `recipe_rates` order, then ascending instance index
3. target node
4. surplus nodes sorted by item ID

Edge ordering:

1. expanded edges in recipe-level wiring edge order
2. for each expanded aggregate edge, source endpoints in ascending index order
3. for each source endpoint, target endpoints in ascending index order

Diagnostics are emitted in deterministic stage order.

## Non-Goals

- No facility catalog joins.
- No port selection.
- No belt throughput calculation.
- No pipe throughput calculation.
- No physical wiring geometry.
- No layout generation.
- No layout optimization.
- No recipe sharing across facility instances.
- No scheduler semantics.
