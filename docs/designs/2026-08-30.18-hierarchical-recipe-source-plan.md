# Hierarchical Recipe Source Plan

## Scope

The web-facing planning contract must choose material sources per consumption context, not globally per item. The same material may be supplied externally to one recipe input and produced internally for another recipe input in the same target plan.

This slice defines a dedicated source-plan request before throughput calculation. It does not adapt the flat throughput-request version 3 producer map. Once contextual production multigraph projection is implemented, throughput request version 4 will embed this source plan and hard-cut the flat fields.

The hierarchy is a planning contract. The spatial solver still receives only a fully resolved facility-instance graph and never chooses recipes or external-input cutoffs.

## Request Contract

```json
{
  "schema_version": 1,
  "target": {
    "item": "item-xiranite-enr-powder",
    "quantity": 1,
    "duration_ms": 10000
  },
  "source_selections": [
    {
      "path": "/target",
      "source": {
        "kind": "recipe",
        "recipe": "xiranite-oven-xiranite-enr-powder-1"
      }
    },
    {
      "path": "/target/recipe:xiranite-oven-xiranite-enr-powder-1/input:item-xiranite-powder",
      "source": {
        "kind": "external-input"
      }
    }
  ]
}
```

`path` identifies one material demand in the hierarchy. `/target` is the root target demand. A recipe child path appends `/recipe:<recipe-id>/input:<item-id>`. Stable recipe and item IDs contain no slash, so generated paths are deterministic and unambiguous.

`source` is a tagged union:

- `external-input`: stop expanding this material demand and expose it as an external boundary input;
- `recipe`: produce this material demand through the named recipe at this context only.

The root target cannot be selected as an external input. A non-root material node always exposes the material itself as an `external-input` choice, including when it has one unique producer.

## Hierarchy Report

`aic recipes check-sources --file <recipes.json> --request <source-plan.json>` returns:

- `ready`: whether every active ambiguous source has been resolved;
- `status`: `ready`, `selection-required`, or `invalid-input`;
- `root`: the active nested material-source hierarchy;
- `source_catalog`: every reachable material and its complete source options;
- `required_selection_paths`: active unresolved paths;
- structured diagnostics owned by `recipe-source-check`.

Every material node contains:

- its stable `path` and `item`;
- whether external input is allowed at that context;
- `resolution`: `automatic`, `explicit`, or `selection-required`;
- the selected source when one exists;
- child material demands for the selected recipe branch;
- an ancestor path reference when a selected recipe closes a cycle.

`source_catalog` is a finite DAG keyed by item ID. Every catalog group exposes `external_input_supported` and embeds every complete producer recipe DTO. The web client can therefore expand all alternatives locally in one screen and derive their deterministic context paths without requesting another check after each choice. The report does not duplicate every alternative subtree because doing so grows combinatorially on the official recipe graph.

Only the explicitly or automatically selected recipe branch appears under `root`. A sole recipe is selected automatically unless the caller explicitly chooses external input for that material. All path selections for a chosen branch may be submitted together in one request.

Both `ready` and `selection-required` are successful CLI outcomes because the latter is normal user-interaction state. Only `invalid-input`, unreadable data, and malformed data return a failing process status.

## Context Independence

Paths, rather than item IDs, own source selections. Two nodes with the same item but different paths are independent. One may select `external-input` while the other selects a recipe. No compatibility adapter collapses these decisions into a global item-to-producer map.

## Cycles

Hierarchy expansion tracks ancestor recipe choices. If a selected recipe would repeat an ancestor recipe, the material node contains `cycle_to_path` and does not recursively repeat its inputs. This finite reference represents the selected production cycle. External input remains available at every non-root material context as a cutoff or bootstrap-oriented source choice.

## Validation And Diagnostics

- source-selection paths must be unique and must exist in the generated hierarchy;
- root external-input selection is invalid;
- a selected recipe must be one of the recipes producing that node's item;
- recipe IDs must use stable ID syntax;
- a selection path must belong to the branch selected by the same request;
- `source-selection-required`: an active material node has multiple recipes and no explicit source;
- `duplicate-source-selection-path`;
- `unknown-source-selection-path`;
- `invalid-source-selection-recipe-id`;
- `selected-recipe-output-mismatch`;
- `external-target-selection`;
- `unknown-target-item`.

## Follow-on Projection

A ready hierarchy must next be projected to a contextual production multigraph. Recipe occurrences are identified by hierarchy path, so the same recipe and item may appear more than once with different upstream sources. Throughput, facility expansion, wiring, and spatial routing must preserve those occurrence IDs. Only after that projection exists may the flat throughput-request version 3 contract be removed.
