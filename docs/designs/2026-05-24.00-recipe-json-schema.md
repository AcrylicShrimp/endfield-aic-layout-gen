# Recipe JSON Schema

## Design Goal

Define the first external JSON data contract for AIC recipe graph resolution.

The schema must support milestone 1: given a target final item, resolve every intermediate recipe dependency until all leaf inputs are external items. It does not need throughput scaling, facility placement, wiring, layout generation, or cycle handling yet.

## Constraints

- All repository content is written in English.
- All application input and output data is JSON.
- No facility, recipe, item, belt, pipe, or game-balance data may be hardcoded in application code.
- Runtime data is loaded from external files on each execution.
- JSON field names use `snake_case`.
- Stable identifier values use `kebab-case`.
- The root Cargo package remains unrelated to this schema decision; this document is design-only.

## External Context

The current public community data suggests that recipes are not limited to a single-output shape. End Wiki lists production recipe groups by facility and shows recipe rows with ingredients, outputs, and duration. Endfield DB also models raw materials as non-crafted inputs and calls out circular production loops as a separate advanced concern.

These references are useful context, not authoritative schema inputs for this project.

- End Wiki recipes: <https://end.wiki/en/factory/recipes/>
- Endfield DB calculator: <https://endfielddb.com/calculator/>

## Agreed Model

The v1 recipe file is a recipe book with a schema version, a list of externally supplied items, and a list of recipes.

```json
{
  "schema_version": 1,
  "external_items": ["originium-ore"],
  "recipes": [
    {
      "id": "grind-originium-powder",
      "facility": "grinding-unit",
      "inputs": [
        { "item": "originium-ore", "quantity": 1 }
      ],
      "outputs": [
        { "item": "originium-powder", "quantity": 1 }
      ],
      "duration_ms": 2000
    }
  ]
}
```

## Field Semantics

`schema_version` is a positive integer identifying the recipe file format version.

`external_items` is an array of item IDs. These items are leaf inputs supplied from outside the factory graph, such as natural resources. They are not recipes and do not have quantities in the recipe book.

`recipes` is an array of recipe definitions.

`recipe.id` is the stable recipe ID.

`recipe.facility` is a stable facility ID reference. Facility details are intentionally out of scope for v1 and will be joined from a future facility catalog.

`recipe.inputs` is an array of item amounts consumed by the recipe.

`recipe.outputs` is an array of item amounts produced by the recipe.

`recipe.duration_ms` is the positive integer process duration in milliseconds.

`ItemAmount.item` is a stable item ID reference. Item display names and item metadata are intentionally out of scope for v1 and will be joined from a future item catalog.

`ItemAmount.quantity` is a positive integer. Fractional quantities are represented by scaling units in the data.

## Identifier Rules

All stable ID strings use this grammar:

```text
^[a-z0-9]+(-[a-z0-9]+)*$
```

This applies to:

- recipe IDs
- item IDs
- facility IDs
- `external_items` entries

The rule permits lowercase ASCII letters, digits, and single hyphens between segments. It rejects leading hyphens, trailing hyphens, uppercase letters, underscores, spaces, and repeated hyphens.

## Validation Invariants

- `schema_version` must be `1` for the v1 loader.
- `external_items` must not contain duplicate item IDs.
- `recipes` must not contain duplicate recipe IDs.
- Every recipe must have at least one output.
- Every `quantity` must be a positive integer.
- Every `duration_ms` must be a positive integer.
- Every item referenced by `inputs` must be either:
  - produced by at least one recipe output, or
  - listed in `external_items`.
- An item must not be both listed in `external_items` and produced by a recipe.
- If an input item is neither produced nor external, the data has a missing link error.
- If a requested target item is neither produced nor external, target resolution fails.
- If more than one recipe can produce an item, v1 graph resolution reports an ambiguity error.
- Cyclic recipe dependencies are invalid in v1 and must be reported as data errors.

## Rejected Alternatives

Single-output recipes were rejected because public community recipe data already suggests that multiple-output recipes exist or may be needed.

Object-shaped `external_items` entries were rejected for v1. Item metadata belongs in a future item catalog and can be joined by ID.

Fractional quantities were rejected for v1. Data should scale units into positive integers instead.

Cycle support was rejected for v1. Circular production loops, including container return patterns, are important but should be researched and designed separately after the acyclic graph resolver works.

Hardcoded item or facility display names were rejected. The recipe file should use stable IDs only.

## Open Issues

- The exact filename and directory layout for recipe JSON files is still open.
- The item catalog schema is still open.
- The facility catalog schema is still open.
- Multi-recipe selection policy is deferred until alternate recipes need to be supported.
- Cyclic recipe math is deferred until circular production loops become an explicit milestone.

## Next Implementation Slice

Implement the v1 recipe data loader and validator.

The first implementation slice should:

- add JSON deserialization for the v1 recipe book shape
- validate stable ID formatting
- validate duplicate IDs
- validate positive quantities and durations
- build an index from output item ID to producing recipe ID
- report missing input links
- report ambiguous output producers
- report dependency cycles
- expose a CLI command that loads a recipe JSON file and validates it

The first graph resolver should remain acyclic and quantity-agnostic. Throughput scaling belongs to the next milestone.
