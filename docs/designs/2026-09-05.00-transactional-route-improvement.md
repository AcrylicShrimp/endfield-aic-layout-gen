# First transactional route-improvement pass

## Status and scope

Specified by M5 of the [runtime roadmap](../todos/2026-09-05.05-fast-construction-milestones.md).
Implementation is the next quality milestone, Q1; this document does not claim that improvement
already runs. It specializes the accepted [constructive design](2026-09-02.00-constructive-layout-planner.md),
without replacing its connected-growth or complete-factory contracts.

Update after user visual inspection: Q1 is deferred, not the immediate next implementation.
The [Q0 placement experiment](../benchmarks/constructive-nearby-placement/report.md) found that
local compactness alone does not preserve full-graph completion. Bounded recent-growth continuation
and reconsideration is the next question. This route-improvement contract remains a later proposal.

Q1 reroutes one ordinary directed chain at fixed endpoints within an already complete factory.
It establishes mutation, repair, validation, scoring and rollback as one reusable transaction.
It does not relocate facilities, move terminals, change ports, resynthesize commodity networks,
add/remove junctions or crossings, call a local CP oracle, or invoke the global exact solver.
Consequently it can improve transport length/turns without necessarily shrinking factory area.
Facility/group relocation with bounded route repair is a separate subsequent milestone, Q2.

## Stage input and output

The library stage receives these typed inputs, not constructor acceptance flags:

| Input | Contract |
| --- | --- |
| `ConstructiveNode` incumbent | Complete geometry, placements, terminals, requirements and component identities |
| Original `FacilityInstanceWiringReport` | Original facility/requirement identities and exact terminal commodity rates |
| Validated facility/item/transport/component catalogs | Loaded externally on this execution; no embedded game data |
| `RouteImprovementRequest` schema 1 | `max_attempts`, `max_route_searches`, `max_expanded_states_per_search` |

The request has no width/height target or feasibility ceiling. Zero attempts is an explicit disabled
pass. When enabled, route/search-state budgets must be positive; invalid settings yield structured
invalid input. Attempt and route counters are local to improvement, not construction counters.
An attempt counts one eligible chain selected for mutation; each A* invocation consumes one search,
including failures. State budget counts dequeued search states, including the goal if dequeued.

Output is `RouteImprovementReport` schema 1 plus the best independently validated node:

- `status`: `not-run`, `no-improvement`, `improved`, `budget-exhausted`, `invalid-input`, or
  `resource-failed`. `budget-exhausted` may still include accepted improvements.
- `incumbent_valid`, `initial_score`, `final_score`, requested budgets, attempts, route searches,
  expanded states, accepted count, rejection counts by stable code, and elapsed milliseconds.
- Accepted transactions in commit order: ordinal, network ID, chain endpoints, old/new scores,
  removed/added cells and segments, and consumed work. Store deltas, not full rejected candidates.
- Bounded diagnostics with code, severity, stage, message, entity/path and attempted transaction
  ordinal when applicable. Repeated equivalent rejections aggregate counts rather than duplicate text.

If initial independent checks fail, return invalid input and do not label the supplied node a valid
incumbent. If an enabled pass has established a valid incumbent, every later return retains it or
a strictly better validated replacement. Operational failure never masquerades as infeasibility.

## Candidate identity and immutable boundary

Enumerate maximal directed chains in deterministic order: pipes before belts, decreasing segment
count, then network ID and lexicographic endpoint coordinates. Require at least one removable
interior cell. Every interior cell must:

- Have exactly one incoming and one outgoing segment in this commodity network.
- Be ordinary transport: no terminal, component, crossing channel or branch/convergence.
- Carry the same strictly positive exact `Rate` through the chain.
- Have no same-layer occupancy belonging to another network.

Stop at the first terminal, topology junction or component boundary. Exclude closed chains with
no distinguished endpoint and chains whose interior overlaps special topology. Endpoints remain
fixed, including the direction of the chain's incident arm at each endpoint. All existing external
terminals, facility port assignments, component placements/rotations/IDs, and other segments are
immutable. Facility, requirement, terminal and commodity-network IDs retain their meaning.

Re-enumerate after each accepted mutation, because coordinates and chain candidates may change.
Within one unchanged incumbent, attempt each eligible chain at most once. Stable ties never use
wall-clock arrival order. A pass with no eligible chains is a valid no-improvement outcome, not a
construction failure or an assertion of local/global optimality.

## Mutation and bounded route repair

1. Clone the valid incumbent into one private candidate. Remove only the selected chain segments
   and exclusively owned interior cells; keep endpoint cells and all immutable geometry.
2. Ask the dedicated route engine for a simple directed replacement between the same endpoints,
   preserving endpoint arm directions and constant flow. Carry incoming direction in the search
   state so turns are represented. Use deterministic length, turn and tie ordering.
3. For Q1, search within the incumbent's measured used envelope. This is an explicit heuristic
   neighborhood, not a caller W/H limit or a completeness claim. It cannot rule out improvements
   involving wider temporary geometry or facility movement; those belong to later passes.
4. Facilities block both layers. Same-layer retained transport, even the same commodity, blocks new
   interior cells; different-layer occupancy follows existing validated layer rules. Existing
   logistics cells cannot become new interior cells. Q1 introduces no new crossing, merge or split.
5. Enforce checked coordinates, finite expanded-state/search budgets and explicit workspace
   allocation failures. Do not run unbounded search when no replacement is found. No parallel
   candidate winners or speculative commits are needed for this first pass.
6. Add replacement cells/segments with the old exact flow and network ownership. Rebuild derived
   segment capacity reports from the candidate, not copied stale geometry. Preserve construction
   attachment events as history; do not reinterpret them as a current route cache.

No route or budget exhaustion discards the incumbent. The modified candidate is never externally
visible before acceptance. The route engine's cost is a proposal heuristic; only the global score
and complete acceptance gate decide whether that proposal is useful.

## Full acceptance gate and score

Validate independently using actual candidate geometry and current catalogs, including placement,
ports, cells, directed segments, terminals, component topology/channels, conservation, connectivity,
capacity and external-connection rules. Separately audit exact original-wiring identity/rates.
Explicitly check that the full original facility and internal/external requirement sets are present
exactly once and no unresolved boundaries remain: a partial-subgraph coverage audit alone does not
establish complete original-request coverage. No constructor cache or previous validity flag suffices.

Recompute used bounds from all actual facility, transport and logistics geometry. Q1 preserves
coordinates; it does not translate the whole incumbent merely to normalize its origin. Score only
independently validated candidates using the lexicographic tuple:

1. Used bounding-box area.
2. Number of unique physical `(transport layer, x, y)` cells, not logical requirement path length.
3. Total route turns, using the existing constructive `network::turns` metric.

The tile and turn definitions match the first three fields of current composition scoring. Do not
carry the fourth incomplete-boundary preference into the complete-factory objective. Area/products
and aggregate counters require checked arithmetic; overflow is a diagnostic, not a saturating score
that could accept a wrongly ranked candidate. Prefer a neutral score helper shared by constructive
consumers over an adapter to research scoring or a new incompatible definition.

Commit only when full validation succeeds and the tuple is strictly smaller. Equal scores reject,
even when geometry differs; fewer tiles cannot compensate for larger area, and fewer turns cannot
compensate for more tiles. After rejection, retain the byte-equivalent incumbent. After acceptance,
only then replace the incumbent and record the delta. Every reported accepted score strictly descends.

## Stable diagnostics

Stage identifier: `constructive-improvement`. Existing detailed validator diagnostics remain nested
evidence; the transaction summary uses stable categories with the network/chain entity when known.

| Code | Severity / meaning |
| --- | --- |
| `improvement-input-invalid` | Error; malformed request or incomplete/invalid initial factory |
| `improvement-no-eligible-chain` | Info; this restricted pass has no candidate |
| `improvement-route-unavailable` | Info; no replacement in the stated local neighborhood |
| `improvement-budget-exhausted` | Info; attempt/search/state bound reached; retain incumbent |
| `improvement-workspace-failed` | Error; coordinate/allocation representation failed |
| `improvement-candidate-invalid` | Warning; independent geometry validation rejected candidate |
| `improvement-coverage-invalid` | Warning; original-request identity/rate audit rejected candidate |
| `improvement-score-overflow` | Error; score could not be represented safely |
| `improvement-score-not-better` | Info; valid candidate did not strictly improve |

Resource errors terminate the pass with the last valid incumbent; ordinary route or score rejections
continue within budgets. A failed candidate validation is retained as actionable evidence rather
than silently counted as an ordinary no-route result. No category claims global infeasibility.

## CLI/report integration for Q1

Add explicit opt-in improvement flags to `layouts construct-production`, initially disabled by
zero attempts. Positive attempts enable the pass only after complete construction; incomplete
construction retains its original failure and does not enter improvement. Select and document
conservative finite search/state defaults during Q1's fixture measurements.

Use a hard report cutover to production report schema 3 when this feature lands: `steps` remains
construction history, `final_node` becomes the best current validated factory, and `improvement`
contains the new report. Update renderer and tests directly; do not create old/new internal adapter
paths. Document that `final_node` can differ from the last construction step. Output `status=complete`
still describes the factory, while `improvement.status` describes optimization termination. Operational
improvement errors produce nonzero CLI exit with the complete incumbent report; disabled/no-gain or
budget-exhausted passes that preserve valid completion are normal successful returns.

Full geometry/history and diagnostics stay in JSON files; HTML distinguishes construction from
accepted improvements. Stdout remains one short completion record pointing to outputs. Profile
operations separate candidate selection, route repair, independent validation, scoring and commit;
failed attempts count toward bounded work. Do not accumulate rejected full-layout snapshots.

## Q1 verification gate

- Add external controlled detour fixtures; preserve facility, recipe and transport values outside
  application code. Demonstrate a strict tile/turn improvement without increasing area.
- Test pipe/belt layer independence, same-layer blockers, endpoint direction preservation,
  branch/convergence and bridge exclusions, capacities, exact rates, and original coverage.
- Deliberately corrupt candidates and confirm rejection plus unchanged incumbent. Test an invalid
  initial node separately; it must not become a claimed valid no-improvement result.
- Test disabled/no-eligible/no-route/equal-score outcomes, search/state/attempt exhaustion,
  checked-arithmetic failures, deterministic ordering and repeated accepted mutations.
- Assert every accepted history entry is complete, valid and strictly better, and report/HTML
  final geometry agrees. Test report schema 3 and short stdout manually.
- Run release full/small workloads and record score before/after, all attempted/accepted work,
  elapsed time and RSS. Full Heavy Xiranite may legitimately have no Q1 improvement; never enlarge
  scope silently just to force a better result. Identify the next quality bottleneck from evidence.
- Run formatting, workspace check/tests and manual CLI verification, compare with AGENTS.md and
  the accepted design, then commit Q1 separately. Q2 requires its own relocation/repair contract.
