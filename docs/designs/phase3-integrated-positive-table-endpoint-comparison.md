# Phase 3 Integrated Positive-Table Endpoint Comparison

## Status

Accepted experiment contract. This is a research-only formulation comparison and does not change
the authoritative endpoint encoding used by normal layout solves.

## Falsifiable question

When the actual Heavy Xiranite cumulative Phase 3 joint placement-routing model is otherwise
unchanged, does replacing only the nested facility endpoint Element chain with complete positive
tables materially improve first-feasible search within the standard five-second candidate budget?

The hypothesis is supported if the table case finds a validated incumbent where the baseline does
not, or produces a large and repeatable reduction in decisions, backtracks, conflicts, or measured
CPU work without causing model construction or memory to become the new cliff. Pumpkin's
`propagations` statistic counts registered propagator calls, not atomic inferences or clause work,
so it is contextual evidence only and cannot establish improvement by itself.

## Controlled formulation

- Workload: minimum-rate Heavy Xiranite.
- Cumulative phase: Phase 3, containing four facilities.
- Exact used dimensions: `16 x 16`.
- Search mode: feasibility only.
- Per-run search budget: 5,000 ms.
- Solver stack: current possible-graph reachability, watched unique-support/local-continuation, and
  grouped guarded item-intersection propagators.
- Prior solution hint: none in either case. Hints are non-binding, but excluding one keeps the
  isolated comparison independent from a separate prefix solve.
- Placement, rotation, logical port selection, boundary terminals, belt/pipe routing, item
  assignment, flow, capacity, occupancy, crossing, and topology remain solver decisions.

The only matrix axis is the facility endpoint channel:

1. **Nested Element baseline**: the current production research formulation.
2. **Positive table**: one complete allowed `(placement, port, geometry)` table per facility
   terminal. External boundary terminals remain unchanged.

Both encodings accept the same complete endpoint tuples. No coordinate, port, route, corridor, or
candidate is fixed or removed heuristically.

## Execution matrix

Run three isolated release processes per encoding. Every process builds one fresh exact model and
receives the same five-second search limit. A timeout remains `unknown`.

Each process writes:

- structured JSON, including the complete layout failure or incumbent report;
- self-contained HTML for the result;
- `/usr/bin/time -l` process statistics on macOS.

## Measurements

Record per run:

- endpoint encoding and exact legal table-row count;
- model construction time;
- variables, constraints, incidences, and placement-routing incidences;
- search time and first incumbent time;
- branch decisions, backtracks, conflicts, learned clauses, and registered propagator calls;
- termination reason, proof status, and witness validation;
- final objective vector when an incumbent exists;
- maximum RSS, retired instructions, and CPU cycles.

Report medians and all individual outcomes. Enumerate the integrated relation directly for this run.
For the positive-table case, report one hidden row literal per legal row and the clauses generated by
Pumpkin's table encoder separately from the generic model-recorder totals. The nested-Element case
has no such table-specific overhead. The preceding channel-only report validates the counting method
but is not the source of this integrated model's row count.

## Stopping point

This checkpoint ends after the six-run comparison and one evidence-backed next experiment:

- table improves integrated search: retain it only as a research candidate and identify its next
  scale or cost cliff;
- table causes a build/RSS cliff: propose a sparse semantic support propagator;
- table strengthens root propagation but integrated search remains unchanged: return to the next
  residual routing/flow cliff instead of micro-optimizing this channel.

No production cutover or custom propagator is implemented in this checkpoint.
