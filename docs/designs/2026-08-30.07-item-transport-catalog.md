# Item Transport Catalog

## Scope

Every routable item has exactly one fixed transport kind: `belt` or `pipe`. Facility ports independently have a fixed transport kind and direction. Neither property is a solver decision.

The item catalog is external runtime data so game data is not compiled into application code.

## Schema Version 1

```json
{
  "schema_version": 1,
  "items": [
    { "id": "originium-ore", "transport": "belt" },
    { "id": "clean-water", "transport": "pipe" }
  ]
}
```

- `schema_version` must be `1`.
- `items` contains zero or more item definitions.
- `id` is a stable kebab-case ID and must be unique.
- `transport` is exactly `belt` or `pipe`.
- Unknown fields are rejected.

## Shared Transport Type

`TransportKind` is shared by item definitions and facility port definitions. The former facility-specific transport enum is removed rather than retained through a compatibility alias.

For a logical edge carrying item `m` through source port `s` and target port `t`, routing may create an endpoint candidate only when:

```text
m.transport = s.transport = t.transport
s.direction = output
t.direction = input
```

## Facility Mode Boundary

Mode-dependent recipe and port setups are flattened during external data preparation. Each mode is represented by a dedicated facility ID. A recipe references that ID directly, so the validated facility definition always has one fixed port setup and the layout solver does not carry a mode variable.

Recipe graph resolution is also upstream of layout solving. A unique producer may be selected automatically; multiple producers are reported as ambiguous unless a later planning request explicitly selects one. The spatial solver only receives the resulting fixed facility-instance graph.
