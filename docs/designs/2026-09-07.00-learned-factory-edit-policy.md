## Why an edit policy

A fixed router can consistently undo a useful detour: the policy may need to route around a
corridor now so that a facility can occupy it later. Selecting a placement while a router always
rebuilds the central path cannot express that plan. The policy need not imitate the router, but
it must optimize against its responses and cannot request paths outside its output choices.

The proposed boundary gives the model control of paths, ports, intentional branch/merge
connections, and changed facility placements. Code expands specified geometry, derives the
required logistics components, updates indexes, and checks rules.
There is no implicit shortest path, automatic repair, snapping to a nearby destination,
heuristic candidate substitution, or exact-solver fallback.

Structured commands avoid regenerating unchanged geometry. They are not a text-generation
requirement: a decoder may select an operation, point to an input entity, and select typed
parameters. Human-readable command text is a trace rendering, not the learning interface.

## State and stage contracts

Names below are proposed logical DTOs, not implemented schemas or required final interfaces.
Their invariants describe how this candidate would work if selected for a particular comparison;
the interfaces and invariants can be revised between comparisons. Version any implemented
serialized inputs, observations, actions, and reports independently of model weights.

### Episode input

`EditEpisodeInput` contains:

- schema version, original request identity/content hash, complete initial layout and hash;
- explicit runtime catalog paths/hashes and validation/score contract versions;
- immutable required facilities, rates, terminals, and commodity networks;
- episode and command resource budgets, declared seed, and split/provenance identity.

Input admission independently validates initial geometry and original-request coverage. Missing
files, unsupported semantics, catalog mismatches, or invalid initial layouts are admission errors,
not episodes in which an invalid root is silently repaired. Rejected roots remain in admission
statistics. No constructor-success-only sampling claim represents the full requested distribution.

### Environment state

Keep three distinct objects:

| Object | Invariant | Purpose |
| --- | --- | --- |
| `best` | Complete, independently valid, best exact score seen; initially the input. | Only source of the final exported factory. |
| `working_base` | Complete, independently valid; may be worse than `best`. | Starting point for the current edit transaction and valid detour exploration. |
| `draft` | Explicit private edits over `working_base`; may have unresolved connections. | Model-visible multi-command work in progress. |

Also retain immutable production obligations, a monotonic observation revision, channel/anchor handles,
terminal bindings, pending obligations, a work ledger, and an edit trace. Do not collapse `best`
and `working_base`: doing so would reject valid detours. Do not score a disconnected draft as
a successful area improvement or use its missing transport as a density win.

Each command is atomic: either all its specified changes occur or the state is unchanged.
An unsuccessful command still consumes its charged budget. The draft can be topologically
incomplete, but accepted commands maintain defined geometry, entity identity, and mechanically
representable channel occupancy. Examples include unattached route ends, temporarily unbound
terminals, and explicitly separate crossing channels with an unfinished arm. Pending topology
is visible and must have a legal local completion under the declared rules. This does not permit
lost facilities, changed recipes, or ambiguous connectivity between overlapping channels.

### Observation

`EditObservation` exposes the current revision, complete immutable request/network information,
draft placements and transport topology, bindings and unresolved obligations, available anchors,
remaining budgets, last command outcome, and current best/working-base score summaries.
The initial score must be visible if rewards normalize by it. Transaction mode is visible.

Facility and terminal references point into the current input entity tables rather than using
memorized training IDs. Created geometry receives explicit handles. Erased handles become invalid;
coordinates alone do not resolve two crossing channels. A stale revision or deleted reference is
rejected instead of resolving to a different object. A rejected command does not change geometry;
the observation revision still advances because budget/outcome information changed.

The logical observation contract precedes tensor encoding. A local raster alone can hide remote
dependencies and used-boundary changes. Candidate encodings are a whole raster with entity
features, an attributed graph with explicit geometry, or a graph plus precise local rasters and
global spatial context. A crop is an observation choice, not an edit boundary or factory limit.
Summaries/crops may make the policy partially observed; do not claim a sufficient Markov state
without checking it. Full working-base geometry or suitable memory may be needed to reason about
discarding edits; a scalar score alone does not describe that fallback.

### Action and response

`EditAction = {schema_version, observation_revision, operation, typed_arguments}`.
The model selects operation and conditionally decoded arguments; the executor owns validation.
Pointers refer to the supplied entity tables. Integer grid transforms are exact. Decoder order
for multi-entity commands is canonical, with no duplicate facility assignments.

`EditStepResult` contains the new revision/observation, applied or rejected status, explicit
geometry/binding delta, derived component delta, affected entities and pending obligations,
charged work, and diagnostics. Derived component changes identify their inducing command and
incident channel handles; they are visible effects, not hidden route decisions.
No reward value is finalized until the learning objective is selected.

## Proposed command vocabulary

This is a semantic draft. It expands the conversation's shorthand where paper walkthroughs
expose missing operations. It is not yet a claim of coverage for every legal game layout.

| Operation | Arguments and exact effect |
| --- | --- |
| `SET_PLACEMENTS` | Explicit list of facility IDs and target origins/allowed rotations. Apply all assignments simultaneously; validate against unchanged geometry and one another. A singleton expresses an ordinary move. |
| `UNBIND_TERMINALS` | Explicit terminal IDs. Remove their physical port/boundary bindings in the draft; keep their immutable item, role, rate, and connectivity obligations. |
| `BIND_TERMINALS` | Explicit terminal-to-facility-port or terminal-to-external-boundary-anchor assignments. Check catalog compatibility and selected-port geometry; pending connectivity remains visible. |
| `ERASE_TRANSPORT` | Exact physical edge runs and/or channel references, with explicit layer and network/channel identity. Delete that geometry and recompute derived components, not an entire logical requirement's guessed path. |
| `EXTEND` | Network, exact source anchor/channel, directed growth mode, cardinal direction, positive integer length. Materialize that straight run and return its endpoint handle. Selecting an existing channel explicitly attaches the new run there. Every traversed arm/cell is checked; independent crossings do not create connections. No persistent cursor, path search, or automatic turn. |
| `CONNECT` | Explicit open-end handle and compatible target anchor/channel, with the directed connection specified. Join coincident handles or add exactly one adjacent directed edge and join. It performs no path search and never changes the selected target. |
| `DISCARD_EDIT` | Restore the latest fully validated `working_base`, remove handles created only in the discarded draft, and charge the work. It is not an episode reset or budget refund. |

### Placements and atomic groups

Facilities cannot be deleted or invented. Before moving/rotating a bound facility, explicitly
unbind the affected terminals and erase any transport/component geometry that would conflict
with the new footprints. Old transport does not move with the facility. Endpoint coordinates
are recomputed from catalog ports and chosen transforms; binding and route changes remain
explicit. A group command cannot hide auto-rerouting or delete obstacles.

Simultaneous assignments support swaps without representing an intermediate facility overlap.
This is a static layout edit, not a simulation of moving physical objects along collision-free
trajectories. Check final group geometry as a whole. Do not mask one group's destination simply
because another member currently occupies it. A singleton can instead use temporary free space.

Group size and decoder limits must be declared as action-domain limits before experiments;
they are not game rules. Sequential subassignments inside one command are charged even though
the final mutation is atomic. Truncated command decoding applies no partial geometry.

### Physical transport and terminal semantics

Use [the mathematical model](aic-game-rules-mathematical-model.md) to identify confirmed rules
and unresolved ambiguities. Never turn an unresolved ambiguity into a pruning rule.

- Shared trunks are one physical resource. Erasing one affects every dependent demand; retain
  and report all those demands rather than deleting one logical edge and pretending others work.
- Coincidence is not connectivity. Every shared/independent channel relationship is explicit;
  crossing two routes must not silently merge their materials.
- Derive ordinary transport, splitters, convergers, and bridges from directed geometry and
  explicitly chosen attachment relations, as specified below. Component kind and rotation are
  not independent policy outputs in the current design.
- Mere coordinate equality does not request attachment, even for the same item. `EXTEND`
  from an explicitly selected existing channel or `CONNECT` to it supplies that decision. Component derivation cannot
  invent a shared trunk, choose a junction coordinate, or turn a crossing into a merge.
- Port reassignment preserves supply/demand direction, transport kind, item, and rate. Aggregate
  compatible terminal rates on shared resources and check their actual capacities.
- External inputs/outputs are immutable obligations with editable geometry, not fake endpoints
  that can appear wherever convenient. Boundary membership is checked against the final actual
  used bounds, including all retained geometry. Expansion can invalidate an unchanged old anchor.
- Pending flows may be unresolved during drafting. Automatic completion checking requires a valid flow/capacity
  certificate for the exact specified geometry, with no geometry repair. The engine-owned
  boundary is proposed below; its exact checker/backend and unresolved operational rules remain
  OPEN. There is no global placement-routing solver fallback.
- A finite per-command segment length can be repeated and must not become a fixed W/H ceiling.
  Length-one segments should be expressible; this alone does not prove full topology coverage.

## Derived logistics: paths and connections are the policy outputs

This section replaces the earlier explicit `SET_TOPOLOGY` proposal following the user's
crossing and branch/merge simplification. There is no model action to place or rotate a splitter,
converger, or bridge in the current catalog scope. They are physical realizations of the
connectivity already specified by the model.

### Coordinate coincidence versus connection

Represent transport by directed adjacent-cell edges with explicit channel/junction handles,
not only a set of occupied coordinates. At one coordinate, two same-layer channels can belong
to one junction or remain independent. Item identity alone cannot decide this distinction.

- `EXTEND` preserves its path continuity. Passing across another straight channel does not join
  it. If the crossing is legal, the engine derives the bridge. Parallel overlap/edge reuse is
  not a second independent lane on the same physical resource; reject an incompatible overlap.
- `EXTEND` from an existing channel attaches the new run to that exact channel. An interior
  point is addressable by cell and channel handle; splitting an edge-run index there changes no
  existing physical geometry. The incident directed arms determine whether a fork or merge results.
- `CONNECT` explicitly attaches to a selected channel, port, or terminal anchor. Coincident
  handles are joined without a self-loop; exactly adjacent handles gain one directed cell edge.
  Other distances are rejected. Target selection is an input, not a nearest-anchor search.
- An extension ending at an occupied coordinate can remain an explicitly separate unfinished
  channel if a legal local completion exists. It is not auto-connected just because it stopped
  there. The model can connect intentionally or continue straight across; the pending state is
  observable, and cannot pass completion validation while required arms/connections remain open.
- Forward/backward route-growth mode fixes edge direction relative to the commodity flow.
  Derivation uses those directions and selected terminal arms, not the order commands were issued.

### Mechanical component derivation

After each atomic geometry or attachment edit, classify the affected channels and consult the
runtime catalog. A plain turn/line is still an explicit path choice made by the model.

| Specified incident structure on one layer | Derived realization under the current contract |
| --- | --- |
| One connected channel with at most one incoming and one outgoing arm | Ordinary line/turn/terminal geometry; no branching component. |
| One connected commodity junction, one incoming and two or three outgoing arms | A compatible splitter, with orientation matching the used sides. |
| One connected commodity junction, two or three incoming and one outgoing arm | A compatible converger, with orientation matching the used sides. |
| Two independent perpendicular straight channels, each with one incoming and one opposite outgoing arm | A compatible bridge; preserve both channel identities and per-axis flow. |
| A belt and a pipe sharing XY | Separate layers; no bridge merely because their coordinates coincide. |
| A connected two-input/two-output junction, same-layer independent turning overlap, facility collision, or unsupported shape | No automatic spatial repair; reject when locally impossible, otherwise expose a precisely defined pending completion. |

Terminal arms count with their actual source/sink direction. Splitters/convergers require the
same compatible commodity on connected arms; bridge channels need not have the same item under
the current semantic reference. Sharing an item also does not force them to join. A splitter and
bridge cannot be silently superimposed on one layer/cell; a bridge cannot also host a selected
facility terminal under that reference contract.

The engine chooses a catalog component and rotation only when the specified connectivity and
declared rules determine one behavior, or multiple choices are equivalent in allowed footprint,
capacity, channel behavior, and configured score. Equivalent output identities use a documented
canonical order, independent of input catalog ordering. If future catalogs introduce meaningful
alternatives, return `edit-topology-ambiguous`/unsupported-scope evidence and revisit the contract;
do not hide a substantive component choice in this derivation rule.

An incomplete channel may have several possible eventual completions. It is stored as pending,
not resolved by predicting the model's next turn. A complete local shape with insufficient known
capacity cannot be rescued by changing its paths. If loads are unresolved, capacity verification
remains pending until the fixed-geometry flow check; no arbitrary flow values are invented.

Deleting an incident branch may reduce a splitter to plain geometry. Removing one whole axis of
a crossing removes the derived bridge and preserves the other channel. Removing only part of an
axis leaves the explicit unfinished geometry; it does not silently erase its remaining pieces.
Recompute local derivations and record additions/removals in the step delta. This is an exact
consequence of the requested edit, not route cleanup or an unrequested geometry optimization.

Component footprint, occupancy and capacity remain part of state, validation and score. They are
absent from the action vocabulary, not absent from the physical model. All derivation and later
validation work is charged. Group edits are derived against the simultaneous final draft of the
command, not a sequence of artificial intermediate facility states.

### Paper example: a shared belt trunk

This is an authored local interface example, not a full factory, benchmark input, executed test,
or demonstration of game validity. Other geometry and complete production obligations are assumed
to be supplied by a future fixture. Source/demand anchors here represent retained network interfaces.

Use X increasing east and Y increasing south. Let `C` be the belt capacity loaded at execution
from the external catalog, and `q = C/4`. A source anchor `S=(4,1)` supplies `2q`; demands
`D1=(8,4)` and `D2=(4,8)` each require `q`. An existing route runs south from S to `J=(4,4)`,
then east to D1. That initially incomplete local draft is missing the D2 branch.

```text
e1 = EXTEND(network=N, anchor=J.channel, growth=forward, direction=SOUTH, length=4)
CONNECT(from=e1, target=D2, direction=from_to_target)
```

J now has incoming north and outgoing east/south. The engine derives the catalog's compatible
splitter; the model never emits its component ID or rotation. On complete closure, the shared
trunk carries `2q = C/2`, each branch `q = C/4`. These quantities obey aggregate conservation
and the presently recorded line/component capacities. Choosing equal branch loads avoids using
this example to settle the unresolved general splitter-allocation rule.

To move the shared upstream run to the west, retaining the two demand branches:

```text
ERASE_TRANSPORT(selection=the_physical_run_from_S_to_J)
e1 = EXTEND(network=N, anchor=S, growth=forward, direction=WEST, length=2)
e2 = EXTEND(network=N, anchor=e1, growth=forward, direction=SOUTH, length=3)
e3 = EXTEND(network=N, anchor=e2, growth=forward, direction=EAST, length=1)
CONNECT(from=e3, target=J.channel, direction=from_to_target)
```

These assignments are trace aliases for returned handles, not variables the model must name.
The endpoint e3 is at `(3,4)` before `CONNECT`, which adds exactly the adjacent edge into J.
The splitter now receives from west and emits east/south; its orientation is recomputed from
the catalog. Both demands remain pending after erasure and must be restored. The old central
run at `(4,2)` and `(4,3)` is removed; the engine never restores it as a shorter route. The
detour is not itself a claimed area improvement. Automatic completion validation additionally needs all unchanged
factory obligations, actual external bounds, geometry, and a valid flow certificate.

Reversing the complete example's flow and source/demand roles illustrates a converger: the
same connectivity rule sums two `q` inputs into one `2q` output. It is a different authored
request, not permission to reverse immutable roles within an episode.

If another required path goes straight north/south through `(6,4)` without selecting the east/west
path as its attachment target, the engine derives a bridge there. It must preserve independent
channel continuity even if both paths carry the same item. Selecting an explicit connection is
a different action; the engine then checks whether that connected topology has a legal realization.

## Proposed flow boundary: observed requirements, engine-checked allocation

The user asked which choices require their decision and suggested handling flow simply. The
recommendation is to keep it out of the policy's action vocabulary: observe the required amounts
and capacities, choose geometry/connections, and let the engine determine whether those exact
choices support the immutable production request. This is a proposal, not permission to choose
arbitrary terminal rates or change the game's splitter behavior.

### Information supplied to the policy

- Facility/terminal supply and required demand from the original request and recipe calculations.
- Transport line, selected port, and derived component capacities from the external catalogs.
- Compatible item/network identity and the direction/attachment of those obligations.
- Required-rate-to-line-capacity ratios, and verified load-to-capacity ratios where a certificate
  exists. Ratios can exceed one; do not clip away multi-line demand or overload information.
- An explicit unknown/pending flag for unresolved draft loads. Missing certification is not zero
  demand, zero load, or evidence that the draft is feasible.

Use normalized floating features for learning if appropriate, while retaining exact rational
request rates and capacities for validation. The numerical feature transform never changes the
production request or certificate. No `SET_FLOW` or per-tile rate-output action is proposed.

### What the engine may compute

`FixedGeometryFlowInput` contains the complete immutable terminal obligations, the exact directed
physical channel graph and attachments, runtime capacities, a declared semantic version, and a
verification budget. A crossing contributes two independent channels even for the same item;
ordinary connected junctions share only compatible material. It is not a graph whose vertices
are merely XY coordinates.

The engine seeks and verifies an exact allocation satisfying terminal supply/demand, flow
conservation, arm/line and aggregate component capacities, and the declared selected-segment
flow rules. Shared trunks carry the appropriate combined loads. Any splitter allocation rule
must come from the declared semantics; arbitrary ratios cannot be invented to make a layout
pass. A rate certificate is a steady-state witness, not a claim that physical machinery can
be configured to every mathematically feasible ratio.

The checker may assign rates on specified channels. It may not add/delete/reverse paths, move
facilities, select different ports, change branch connectivity, reduce production, invent an
external supply, or silently make every network a source-rooted tree. All possible allocations
it considers refer to the same model-chosen geometry and immutable request. Multiple certificates
do not authorize a geometry optimization. Specify deterministic certificate output or record the
selected certificate so replay and observations remain well defined.

`FixedGeometryFlowResult` is one of:

- `feasible`: exact per-channel rates plus terminal/component checks and input/geometry hashes;
- `infeasible-fixed-geometry`: a verified contradiction under this declared graph and semantics,
  with relevant entities; not infeasibility of the factory request;
- `unknown`: exhausted verification resources or unsupported/unresolved semantics, kept distinct
  from a proven capacity violation.

Automatic completion validation also checks geometry, original-request identity/coverage, and actual external
boundaries. A feasible flow certificate alone is insufficient. Checking exact fixed geometry can
be a dedicated graph/flow routine; no global placement-routing solver is part of this proposal.
Algorithm choice, completeness, strict-positive-flow handling and independent certificate
verification remain technical design work before implementation.

### Remaining user choices

No further user choice is needed merely to normalize features or select a fixed-geometry checker.
The agent should propose and justify those details. If accepted factory semantics, original
production obligations, or quality priorities would need to change, bring that concrete change
and its reason to the user. Unknown game behavior calls for evidence; do not ask the user to
choose whichever splitter rule is easiest to train. The current pilot and resource direction
already permit continuing the design without re-asking those questions.

### Completing and discarding work

After each applied geometry/binding command, the environment checks completion automatically.
For a simple first reference implementation, perform full checking after each such edit; reject
an obviously open draft early with its exact pending-obligation evidence. Do not add heuristic
"probably complete" gates or optimization machinery before their cost is measured. Checking work
belongs to that command's ledger and elapsed time. This is a provisional performance/credit choice.

A successful check independently verifies the complete original request, geometry, terminal
closure, topology, capacities, actual external boundary, and score. Promote the draft to
`working_base` even if its valid score is temporarily worse; update `best` only on a strict
lexicographic improvement. Retain best on a full tie. The next edit starts over this latest valid
working base, with unchanged physical handles preserved. There is no learned finish command.

If completion fails, return the relevant scope and leave the mechanically accepted draft editable;
do not roll back a useful incomplete edit automatically. A rejected mechanical command still makes
no geometry change. Verification exhaustion is distinct from invalidity. `DISCARD_EDIT` restores
the latest validated working base, so automatic completion also determines its rollback point.
That coupled choice is a hypothesis, not a necessary property of diff-based optimization.

At termination export `best`. The last command's validation must finish within the declared work/
time envelope to promote its draft. Otherwise retain the earlier certified best and report the
unfinished check/draft; there is no free post-episode repair or certification pass. Diagnostic
draft output is labeled invalid/unvalidated for factory use and kept outside tracked source.

## Paper walkthroughs

These are conceptual command/obligation checks, not executed experiments or catalog-valid
fixtures. Complete geometry, port identities, rates, and catalogs for component derivation must
be supplied before any walkthrough becomes executable. They show required interfaces, not a solvability
proof or evidence that the model can discover the sequence.

### A. Detour a route, then compact a facility

Assume an outer corridor permits a valid replacement for a central route and its terminals.

1. Erase the exact central physical run; affected connections become pending in the draft.
2. Start at the retained upstream anchor, extend explicit outer straight runs, and connect to
   the downstream anchor. The engine derives components from the specified connections.
3. The completed connection triggers automatic checking. This can establish a valid worse working
   base with more transport or larger bounds; the original best remains available. Any changed
   actual-boundary obligations must also be repaired before that check can succeed.
4. Unbind ports of the facility to move, remove conflicting geometry, and set its new placement.
5. Bind its terminals and explicitly redraw affected connections until completion checking succeeds.
6. Compare the complete result's actual score with best. No credit comes from the disconnected
   small draft after step 1 or 4.

Design consequence: direct paths, valid detours, terminal rebinding, and best/base separation
are all necessary. An engine that reinstates the central shortest path defeats this sequence.

### B. Exchange two facilities

Assume the two final footprints/rotations fit and eventual port routing is possible.

1. Unbind affected terminals of A and B; erase precisely the conflicting route geometry.
2. `SET_PLACEMENTS` assigns A to B's prior region and B to A's prior region in one atomic command.
3. Rebind legal ports and route the actual obligations until automatic completion checking succeeds.

A singleton-only interface requires a buffer location and additional moves; it is a narrower
bounded action domain. A rigid group translation cannot express a swap. The proposed list of
independent final placements resolves that particular interface gap. It does not guarantee the
resulting factory can be routed. The action edits an existing complete-factory draft, not an
empty constructor's global placement phase.

### C. Relocate a shared trunk

Assume one compatible commodity network supplies several consumers through shared geometry.

1. Identify the shared physical run and junction channels to replace. Erase that explicit set;
   retain every original consumer/supply obligation and expose all impacted pending terminals.
2. Draw the replacement trunk, explicitly connect all retained branches, and derive their
   components. Existing independent crossing channels must survive untouched when not selected.
3. Check capacities/flow for the whole affected network and external boundary, then validate
   the full factory. A success for only one consumer cannot finish the edit.

Design consequence: per-requirement path deletion is insufficient; physical identity and chosen
connections belong in observation and actions. Components follow from those connections. The
local example above refines this walkthrough. The engine-owned flow contract is drafted above;
its general checker and outstanding semantic issues remain unresolved.

## Budgets, masking, and diagnostics

The proposed fixed-T episode counts every submitted command, including rejection and discard.
Automatic completion checks are charged work within the inducing command, not additional model
decisions. Expose remaining commands. Also charge decoded group entries, expanded
transport cells, rule checks, full validation calls/work, elapsed time, and peak memory. A long
straight command and a singleton move are not equal computational work. Model inference and
mask construction are included in time comparisons. No free retries, internal route search, or
unlimited validation inside one nominal action.

Exact T, per-command limits, and deadline behavior need a predeclared experiment configuration.
If T defines the actual objective, it is a true finite-horizon episode. If data collection merely
cuts a longer task, it is truncation and requires appropriate value bootstrapping; do not mix the
two when selecting a learning algorithm. Longer evaluation is a separate generalization test.

Masks may exclude malformed references and proven immediate rule violations under the actual
command semantics. They must not silently prune inconvenient detours, future-disconnectivity
guesses, or heuristic candidate rankings. Report domain restrictions and mask costs. An inability
to decide legality within a bound is a resource diagnostic, not proof of illegality.

Proposed `EditDiagnostic` fields: `code`, `severity`, `stage`, `message`, `entity_refs`,
`observation_revision`, `command_index`, and relevant budget/contract details.

| Proposed stable code | Stage | Meaning |
| --- | --- | --- |
| `edit-input-invalid` | admission | Initial layout or immutable request fails validation. |
| `edit-input-missing` | admission | Required input/catalog path is absent; include the path. |
| `edit-semantics-unsupported` | admission or validation | Declared rules cannot be represented or verified. |
| `edit-reference-stale` | decode | Revision mismatch or deleted/unknown entity reference. |
| `edit-command-malformed` | decode | Invalid operation/arguments or incomplete atomic command. |
| `edit-geometry-conflict` | execute | Specified geometry violates a known immediate rule. |
| `edit-topology-ambiguous` | execute | Channel/component decision is missing; no automatic choice. |
| `edit-terminal-incompatible` | execute | Explicit binding contradicts terminal/catalog semantics. |
| `edit-obligations-open` | validation | Full original connectivity/boundary obligations are incomplete. |
| `edit-capacity-invalid` | validation | Specified network cannot satisfy the checked rate contract. |
| `edit-validation-exhausted` | validation | Verification budget ended without a conclusive check. |
| `edit-budget-exhausted` | episode | Command, decoded-work, time, or memory bound was reached. |
| `edit-draft-unfinished` | episode | Termination leaves private edits that cannot be exported. |

`EditEpisodeReport` records input/version hashes, seed/split, admission result, termination reason,
initial/best scores and geometry hashes, validated best improvements, valid detour completions,
command counts by operation/status, unfinished/discarded work, rule and capacity failures,
validation work, time/memory, and output paths. Exported best always has its validation evidence.
Artifacts belong under ignored `target/` or retained `artifacts/`; commit only concise findings,
source/configuration, and compact provenance. A model checkpoint alone may not resume a stream.

## Learning objective and evaluation: deliberately not selected

The product objective is complete factory quality within budget. A possible first scoped reward
is `r_t = (best_area_before - best_area_after) / initial_area`, with undiscounted finite-horizon
return. Only successfully completed validated edits can change best area. Its sum is the final
relative area improvement, averaged over the declared episode distribution. It supplies no
signal for unfinished edits and does not train the lower-priority routing objectives. Many
command sequences may therefore receive zero task reward. This is an open credit/exploration
problem, not a reason to silently add rewards for drawn tiles or short diffs.

No arbitrary weighted sum is accepted as preserving area/transport/turn priority. Avoid penalties
that rule out useful valid detours or rewards for small disconnected drafts, filler geometry,
partial connections, or repeated validation success without improvement. The exact objective, shaping, baseline/value targets,
discounting, and failure treatment need to be designed together before any learner is built.

A later experiment should freeze a question, distribution and admission accounting, train/dev/test
groups including related-layout descendants, independent seeds, checkpoint selection rule, and
budget before execution. Controls should share the same edit semantics: unchanged initial factory,
untrained model, random policy, and simple geometric/greedy search. Single-edit greedy search and
multi-command search have different reachability; report that distinction and search costs.
Compare both charged work and elapsed time, preserve every failure, audit actual returned layouts,
and distinguish fixed-root learning from held-out topology/scale generalization.

No numerical budget, training run, hardware allocation, success margin, CNN/GNN comparison, or
algorithm has been scheduled. Loss movement or parameter changes alone will not establish useful
factory improvement. Small paper examples are interface checks, not substitutes for that goal.

## Research references and their limits

- [NeuRewriter](https://papers.nips.cc/paper/2019/hash/131f383b434fdf48079bff1e44e2d9a5-Abstract.html)
  studies learned local region/rule selection. It motivates an improvement-policy framing, not
  this game's command completeness or achievable packing quality.
- [Graph Networks](https://arxiv.org/abs/1806.01261) and
  [Graph Attention Networks](https://arxiv.org/abs/1710.10903) distinguish relational representation
  from a particular aggregation mechanism. They do not select our encoder.
- [Time Limits in Reinforcement Learning](https://proceedings.mlr.press/v80/pardo18a.html)
  distinguishes task horizons from collection truncation and explains remaining-time observations.
- [Attention Routing](https://arxiv.org/abs/2004.09473) learns routing order with routing rules in
  an algorithm. Do not cite its results as proof that a model directly generates physical paths.
- [Deep Reinforcement Learning that Matters](https://arxiv.org/abs/1709.06560) and
  [Statistical Precipice](https://arxiv.org/abs/2108.13264) explain evaluation variability and the
  limits of point estimates from few training runs. They motivate uncertainty-aware comparisons,
  not any particular seed count, model architecture, or expected improvement for this factory task.
