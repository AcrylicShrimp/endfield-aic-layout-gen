# Throughput-Aware Recipe Graph

## Design Goal

Define milestone 2: given validated recipe data and a target production rate, calculate the exact recipe and item flow rates required to satisfy that target.

This stage builds on the existing acyclic recipe graph resolver. It does not select facility counts, place facilities, route belts, route pipes, or optimize layouts.

## Pipeline

```text
Recipe JSON file
  -> RecipeBook
  -> ValidationReport
  -> ValidatedRecipeBook

Throughput request JSON file
  -> RecipeThroughputRequest
  -> RecipeThroughputReport
```

`RecipeThroughputRequest` is an external JSON input contract and has its own schema version.

`RecipeThroughputReport` is the only expected output for throughput-domain success and throughput-domain failure. Invalid recipe books are still reported through the existing `ValidationReport` before this stage runs.

## Request DTO

```json
{
  "schema_version": 1,
  "target": {
    "item": "originium-ingot",
    "quantity": 1,
    "duration_ms": 10000
  }
}
```

`schema_version` must be `1`.

`target.item` is a stable item ID.

`target.quantity` is the requested target output quantity and must be positive.

`target.duration_ms` is the time window for the requested target output and must be positive.

The target rate is interpreted as `target.quantity / target.duration_ms`, then normalized into units per second.

Unknown request fields are invalid.

## Rate DTO

All calculated rates are exact rational values normalized as units per second.

```json
{
  "numerator": 1,
  "denominator": 2
}
```

The example means `1 / 2` units per second.

`denominator` is always positive. Success reports may contain zero rates only where a field explicitly allows them, but normal output arrays should omit zero-rate surplus entries.

## Report DTO

Successful reports use this shape:

```json
{
  "success": true,
  "target": {
    "item": "originium-ingot",
    "rate": { "numerator": 1, "denominator": 10 }
  },
  "recipe_rates": [
    {
      "recipe": "grind-originium-powder",
      "facility": "grinding-unit",
      "runs_per_second": { "numerator": 1, "denominator": 5 },
      "work_seconds_per_second": { "numerator": 2, "denominator": 5 },
      "limiting_outputs": ["originium-powder"],
      "input_rates": [
        {
          "item": "originium-ore",
          "rate": { "numerator": 1, "denominator": 5 }
        }
      ],
      "output_rates": [
        {
          "item": "originium-powder",
          "rate": { "numerator": 1, "denominator": 5 }
        }
      ]
    }
  ],
  "external_input_rates": [
    {
      "item": "originium-ore",
      "rate": { "numerator": 1, "denominator": 5 }
    }
  ],
  "item_demand_rates": [
    {
      "item": "originium-ore",
      "rate": { "numerator": 1, "denominator": 5 }
    }
  ],
  "surplus_rates": [],
  "diagnostics": [
    {
      "stage": "recipe-throughput",
      "severity": "info",
      "code": "throughput-calculated",
      "path": "/",
      "entity": "originium-ingot",
      "message": "throughput was calculated for target item 'originium-ingot'"
    }
  ]
}
```

Failure reports use the same top-level shape with `success: false`, `target: null`, empty rate arrays, and at least one error diagnostic.

## Output Fields

`target` is the requested target item and normalized target rate. It is `null` when request parsing or request validation prevents a target rate from being trusted.

`recipe_rates` lists every required recipe in dependency-first graph order.

`recipe_rates[].runs_per_second` is the required fractional recipe run rate.

`recipe_rates[].work_seconds_per_second` is `runs_per_second * recipe.duration_ms / 1000`. It is a fractional workload metric, not an integer facility count.

`recipe_rates[].limiting_outputs` lists the recipe output item IDs that determined the selected run rate. It is sorted by item ID.

`input_rates` and `output_rates` list the per-recipe item rates created by the selected run rate. They are sorted by item ID.

`external_input_rates` lists required external item rates sorted by item ID.

`item_demand_rates` lists total demanded item rates sorted by item ID. Demand is the amount needed by the target and downstream recipes before surplus is subtracted.

`surplus_rates` lists output rates produced beyond demanded rates, sorted by item ID. Zero-rate surplus entries are omitted.

`diagnostics` lists deterministic, structured stage diagnostics.

## Diagnostics

Every throughput diagnostic has this shape:

```json
{
  "stage": "recipe-throughput",
  "severity": "error",
  "code": "unknown-target-item",
  "path": "/target/item",
  "entity": "missing-item",
  "message": "target item 'missing-item' is neither external nor recipe-produced"
}
```

`stage` is always `recipe-throughput`.

`severity` is `info`, `warning`, or `error`.

`code` is a stable kebab-case diagnostic code.

`path` is a JSON pointer into the request or report when possible.

`entity` is an optional stable ID for the item or recipe most relevant to the diagnostic.

`message` is human-readable and not a stable programmatic key.

## Failure Modes

Throughput-domain failures produce `RecipeThroughputReport` with `success: false`.

- `unsupported-throughput-request-schema-version`
- `invalid-throughput-request-json`
- `invalid-target-id`
- `non-positive-target-quantity`
- `non-positive-target-duration`
- `unknown-target-item`
- `arithmetic-overflow`

Invalid recipe books remain `ValidationReport` failures because the throughput stage accepts only `ValidatedRecipeBook`.

Filesystem errors and output stream errors remain normal CLI errors because they are not recipe-domain or throughput-domain diagnostics.

## CLI Failure Priority

The `recipes throughput` command uses this priority:

1. Load and parse the recipe file. File access and JSON parse errors are normal CLI errors.
2. Load and parse the throughput request JSON. Request JSON shape errors print `RecipeThroughputReport` with `success: false`.
3. Validate request schema version, target ID, quantity, and duration. Request field errors print `RecipeThroughputReport` with `success: false`.
4. Validate and promote the recipe book. Recipe data errors print `ValidationReport`.
5. Calculate throughput. Unknown target items and arithmetic overflow print `RecipeThroughputReport` with `success: false`.

This keeps malformed request data observable before recipe-book validation, while still ensuring the throughput stage itself only receives `ValidatedRecipeBook`.

## Calculation Algorithm

The stage first resolves the dependency graph for the target item. Graph recipes are dependency-first, so throughput calculation walks them in reverse order to propagate demand from downstream consumers to upstream producers.

The initial demand map contains the target item at the requested target rate.

For each recipe in reverse graph order:

1. Inspect every output item from that recipe.
2. For each output with current demand, calculate `demanded_output_rate / output_quantity`.
3. Select the maximum of those values as `runs_per_second`.
4. Record every output item that equals the maximum as `limiting_outputs`.
5. Add `runs_per_second * input_quantity` to each input item's demand.
6. Calculate every produced output rate as `runs_per_second * output_quantity`.
7. Calculate surplus as `produced_output_rate - demanded_output_rate`.

Using the maximum output requirement prevents double-counting when one multi-output recipe satisfies multiple demanded outputs at the same time.

If the target item is external, the report contains no recipe rates and the target rate appears as an external input rate.

## Ordering Guarantees

- `recipe_rates` follows dependency-first graph order.
- Every `ItemRate` array is sorted by item ID, including nested `input_rates` and `output_rates`.
- `limiting_outputs` is sorted by item ID.
- `diagnostics` is emitted in deterministic stage order.

## Non-Goals

- No facility catalog joins.
- No integer facility count calculation.
- No belt throughput calculation.
- No pipe throughput calculation.
- No wiring plan.
- No layout generation.
- No layout optimization.
- No cyclic recipe support.

## Impact On Recipe Schema

Throughput math requires each recipe side to have one entry per item. The recipe schema therefore rejects duplicate item IDs within a single recipe's `inputs` and within a single recipe's `outputs`.

Data should combine quantities before entering the recipe book.
