# Incremental SCC Optimization Plan

## Status

Accepted design direction; implementation has not started.

This document supersedes the incremental placement, routing-repair, and portfolio contracts in `2026-08-30.29-iterative-scc-layout.md`. It also supersedes the per-worker time-budget and first-feasible portfolio policy in `2026-08-30.28-logistics-component-routing.md`. It preserves SCC decomposition, atomic cycle handling, output-first growth order, cumulative wiring projection, and phase history. The old `satisfy -> bounded anchor -> satisfy` execution policy is explicitly obsolete.

## Design Goal

`iterative-scc` must be an incremental compact-layout optimizer, not a staged feasibility constructor.

For each cumulative production subgraph, the strategy must:

1. construct or reuse a complete routed incumbent;
2. use the previous phase solution as a search hint and incumbent seed;
3. optimize the enlarged problem under a bounded phase budget;
4. retain the best independently validated full witness found during that phase;
5. expand the repair neighborhood when a smaller neighborhood cannot produce or improve a witness;
6. preserve enough diagnostics to explain reuse, movement, invalidation, objective improvement, and termination.

The intended lifecycle is:

```text
optimize small cumulative subgraph
-> add the next logical SCC frontier
-> extend the prior witness into an incumbent for the enlarged graph
-> reuse prior placement, rotation, port, and route choices as hints
-> optimize an affected neighborhood
-> expand the neighborhood when necessary
-> retain the best validated witness
-> repeat
-> run one final full-graph improvement phase
```

Optimality proof is not required for the MVP. Time-limited phases must return the best known validated witness, not the first feasible witness.

## Non-Goals

- Recipe selection, throughput calculation, or facility-count calculation.
- A monolithic dense route variable for every route and every cell in a 500 by 500 search domain.
- Preserving the obsolete bounded-anchor API as a compatibility layer.
- Proving global optimality for the Heavy Xiranite benchmark.
- Blueprint partitioning or the separate 50 by 50 export limit.
- Completing splitter and converger network sharing as part of this cutover.
- Retaining fixed search-perimeter external terminals; the external-connection correction is a prerequisite slice.
- Parallel candidate workers, randomized search, spatial-corridor neighborhood expansion, relative-order hints, logistics-component position hints, or cropped exact refinement in the deterministic MVP.

## Current-State Mismatch

The current executor already computes SCCs and cumulative output-first subgraphs, but each phase performs the following operations:

```text
first feasible coordinate placement
-> stateless sparse routing
-> accept first routed witness
-> copy placement coordinates into hard anchor bounds
```

This violates the target contract in several ways:

- phase zero is not optimized;
- prior coordinates are hard constraints before they are search hints;
- all prior facilities receive the same coordinate-radius policy regardless of graph impact;
- the first feasible radius wins even when a larger neighborhood contains a better layout;
- the global rescue attempt discards prior hints;
- rotation, port assignment, routes, and logistics components are not reused;
- placement has no access to routed-witness quality;
- route cells, turns, and bounds are recorded after selection rather than used to select the phase incumbent;
- phase status contains no initial score, final score, best bound, improvement count, or termination reason.

The current strategy is therefore a cumulative feasibility-repair pipeline, not an incremental optimizer.

## Preserved Logical Growth Contract

The following behavior remains authoritative:

- facility-to-facility wiring is condensed into strongly connected components;
- every cycle is introduced atomically;
- SCC identifiers and member ordering are deterministic;
- growth proceeds from output-facing sink SCCs toward upstream SCCs;
- phase `n` operates on a cumulative graph containing phases `0..n`;
- absent upstream producers are represented as frontier inputs until their SCC is introduced;
- the final cumulative graph exactly preserves the original facility-instance wiring.

### Bounded Phase Batching

Atomic SCCs are scheduled through a deterministic ready frontier. An SCC becomes ready only after every downstream SCC is already included. Ready SCCs are sorted by `(reverse_depth, component_id)` and greedily added until `max_new_facilities_per_phase` would be exceeded. At least one SCC is always added, even when that single atomic SCC exceeds the configured facility budget.

The MVP default is `max_new_facilities_per_phase = 8`. This is an orchestration parameter, not a correctness invariant. It prevents a wide graph with many sink or same-depth SCCs from making phase zero equivalent to the full graph. SCCs at the same depth have no dependency edge between them, so deterministic batching does not violate output-first ordering.

## Prerequisite Geometry Corrections

Incremental optimization must not optimize the currently incorrect search-perimeter terminal model. The following corrections precede optimizer orchestration:

1. Treat the caller's width and height as hard search bounds only.
2. Replace fixed search-perimeter external routes with port-adjacent dangling external connections for facility-to-external flows.
3. Split production-facility spacing from routing search expansion:
   - production-facility gap: one cell for the MVP;
   - sparse routing expansion margin: a separate search policy.
4. Compute used geometry from the minimum and maximum coordinates of facilities, belt cells, pipe cells, and logistics components.
5. Canonicalize every accepted witness by translating its used geometry to `min_x = 0` and `min_y = 0`.
6. Validate and report canonical bounds as:

```text
width  = max_x - min_x + 1
height = max_y - min_y + 1
```

These changes ensure that objective values describe installed geometry rather than search-canvas coordinates.

Port eligibility changes in the same hard cutover:

- a facility placement is not rejected merely because an unused declared port points outside the current canonical used rectangle;
- each declared port is projected independently to either an in-domain connection cell or an unavailable option;
- routing may select only an available compatible port;
- every selected port connection cell is part of its route geometry, including a one-cell dangling external route;
- only facility footprints, selected route cells, and placed logistics components participate in canonical extents;
- witness validation rechecks selected ports only and does not require unused port connection cells to lie in canonical bounds.

This removes the current all-ports clearance dependency that would otherwise make origin translation invalidate a witness.

## Core Domain Contracts

### Stable Entity Identity

Incremental reuse requires identities that survive phase projection.

- Facility identity remains the facility-instance ID.
- SCC identity remains the deterministic growth-component ID.
- `FacilityInstanceWiringEdge` gains a required stable `id` field.
- Wiring builders canonicalize exact duplicate keys `(source, target, kind, item)` by exact rate addition before assigning IDs. Such flows are physically fungible at the facility-instance boundary, so preserving duplicate array entries has no routing meaning. Arithmetic overflow is a structured wiring failure.
- The stable edge ID is derived from the canonical source node ID, target node ID, edge kind, and item ID. Facility-instance IDs already preserve contextual occurrence paths and instance indexes.
- A physical route requirement receives a stable ID derived from the original edge ID and the deterministic capacity-split lane index.
- A projected frontier route records the original route-requirement ID it temporarily represents.
- When an upstream SCC is introduced, the executor can identify exactly which frontier routes are superseded by internal routes.
- `IntegratedRoute` gains the stable route-requirement ID.
- Witness validation joins expected and actual routes by ID and rejects duplicate, missing, or unexpected IDs instead of positionally zipping arrays.

Array position or phase-local edge index must not be the durable identity of reusable state.

The hard-cut DTOs are:

```text
FacilityInstanceWiringEdge {
  id,
  source,
  target,
  kind,
  item,
  rate
}

RouteRequirementId = "{wiring_edge_id}:lane:{lane_index}"

RouteRequirement {
  id,
  original_wiring_edge_id,
  lane_index,
  source,
  target,
  item,
  rate,
  transport,
  projection
}

RequirementProjection =
  Original
  | FrontierExternal { missing_facility, original_endpoint }

RequirementFingerprint {
  source,
  target,
  item,
  rate,
  transport,
  projection
}
```

A retained route is reusable only when both its stable requirement ID and full fingerprint match. A projection change from `FrontierExternal` to `Original` therefore invalidates the old route without changing the durable ID.

The endpoint hard cutover is:

```text
IntegratedRouteEndpoint =
  Facility { instance, port }
  | External { node, side }
```

For a facility-to-external or external-to-facility requirement, the external endpoint occupies the selected facility port connection cell. A one-cell route is legal and has both logical endpoints on that connection cell. External-to-external routes remain invalid. `side` is the outward world direction of the selected facility port, not a search-canvas perimeter label.

The affected wiring and layout report schemas receive explicit incremented schema versions. These reports are output-only `Serialize` DTOs at the current CLI boundary, so there is no existing loader at which rejection can occur. Slice 1 adds serialized-contract tests that require the new version. The first future persisted-report reader, whether CLI or web service, must compare the version before decoding the version-specific payload and return a structured `unsupported-schema-version` diagnostic for an obsolete version. No speculative reader is added solely to claim migration support.

### Layout Score

Every complete validated witness for the same cumulative graph has one typed `LayoutScore`. Comparison is lexicographic and contains no unchecked weighted sum.

The MVP score order is:

```text
1. total_route_cells
2. total_route_turns
3. used_bounding_box_area
4. maximum_used_side
5. physical_transport_tiles
6. logistics_component_count
7. moved_prior_facility_count
8. total_prior_facility_manhattan_displacement
9. rotation_change_count
```

Definitions:

- `total_route_cells` is the sum of routed channel cells and remains the primary saturation-time proxy.
- `total_route_turns` breaks equal-length routing ties.
- `used_bounding_box_area` and `maximum_used_side` measure canonical compactness.
- `physical_transport_tiles` counts unique `(transport layer, coordinate)` installations and is distinct from logical route-cell occurrences.
- prior-solution stability is only a late tie-breaker; it may never defeat an intrinsically better routed layout.

The displacement and rotation-change fields are always measured against one fixed phase reference: the previous phase's final incumbent. Newly introduced facilities do not contribute to those fields, and accepting an improved candidate does not change the reference. Phase zero uses zero for all prior-solution stability fields. This keeps score comparison transitive while the incumbent changes.

Scores are comparable only between candidates for the same cumulative graph. A prior phase score is not compared directly with a later phase score because the later graph contains more requirements.

`deterministic_candidate_key` is not intrinsic layout quality. Candidate selection compares:

```text
CandidateRank = (LayoutScore, deterministic_candidate_key)
```

The key breaks ties between equal intrinsic scores.

The key is a lexicographically ordered structural tuple:

```text
DeterministicCandidateKey {
  phase_index,
  refinement_kind,
  neighborhood_rank,
  restart_index,
  policy_index,
  attempt_index,
  yield_index
}

RefinementKind = IncumbentExtension | GrowthNeighborhood | FinalGlobal
```

`neighborhood_rank` is `0..3` for frontier, one-hop, bounded conflict closure, and global. `policy_index` is the position in the versioned candidate-policy table. An attempt is one invocation of one policy under one deadline and candidate quota. A candidate is one distinct placement yielded by that invocation and subsequently routed and validated. `yield_index` is assigned in producer emission order before routing begins. The tuple is therefore unique within one strategy execution and does not depend on completion timing. Incumbent extension uses `RefinementKind::IncumbentExtension`; neighborhood optimization uses `GrowthNeighborhood`; constructive alternatives receive distinct attempt and yield indexes without colliding with normal neighborhood candidates.

The versioned candidate-policy table is an ordered data contract:

```text
CandidatePolicyTable {
  schema_version,
  policies: [CandidatePolicy]
}

CandidatePolicy {
  id,
  placement_policy,
  routing_order_policy,
  max_candidate_yields
}
```

For one neighborhood pass, attempt indexes are `0..candidate_attempts_per_neighborhood`. Attempt `j` selects `policies[j % policies.len]`; its `policy_index` is that table index. A pass is this entire ordered attempt sequence. A restart repeats the sequence with an incremented `restart_index`. `max_candidate_yields` is the explicit quota for one producer invocation. The table must be non-empty, policy IDs must be unique, and serialized order is semantically significant.

### Phase Incumbent

`PhaseIncumbent` is a complete, independently validated witness for the current cumulative graph. It contains:

- canonical production-facility placements and rotations;
- selected facility ports;
- stable route-requirement IDs and ordered route cells;
- placed logistics components;
- `LayoutScore`;
- provenance identifying whether it came from extension, a neighborhood candidate attempt, or global refinement.

An incomplete placement is a candidate seed, not an incumbent. Only a full routed witness may become the phase incumbent.

```text
PhaseIncumbent {
  cumulative_graph_key,
  cumulative_graph_fingerprint,
  witness,
  score,
  candidate_key,
  provenance
}

IncumbentProvenance =
  ExtendedPriorPhase
  | NeighborhoodCandidate { neighborhood, attempt }
  | FinalGlobalRefinement { attempt }
```

### Search Hint

Hints influence search order but do not change feasibility or objective semantics.

Placement hints include:

- `x` and `y` coordinates;
- rotation literals;
- the prior relative ordering of nearby facilities when supported by the candidate generator.

Routing hints include:

- prior port assignment;
- prior ordered route cells for unchanged requirements;
- preferred route corridors for invalidated requirements;
- prior logistics-component positions.

Dropping a hard neighborhood restriction must not drop these hints.

Relative-order and logistics-component position hints are schema extension points and are not required in the deterministic MVP. The MVP must implement coordinate, rotation, prior-port, and prior-route-corridor hints.

### Retained Routing State

Partial routing is a prerequisite for incumbent extension. The subset router accepts:

```text
RetainedRoutingState {
  graph_key: CumulativeGraphKey,
  retained_routes: sorted map RouteRequirementId -> IntegratedRoute,
  retained_components: sorted map LogisticsComponentId -> RetainedComponent,
  occupied_cells_by_transport: sorted map TransportKind -> sorted map Cell -> Occupant,
  selected_ports: sorted map RouteRequirementId -> SelectedPortAssignment,
  invalidated_requirement_ids: sorted set RouteRequirementId
}

SelectedPortAssignment {
  source: EndpointPortSelection,
  target: EndpointPortSelection
}

EndpointPortSelection =
  FacilityPort { facility_instance_id, port_id }
  | ExternalDangling { facility_instance_id, port_id, side }

RetainedComponent {
  id: LogisticsComponentId,
  kind,
  transport,
  cell,
  owner_requirement_ids: sorted non-empty set RouteRequirementId
}

LogisticsComponentId =
  SHA-256(kind, transport, canonical cell, sorted owner requirement IDs)

Occupant =
  RetainedRoute { requirement_id }
  | RetainedComponent { component_id }
```

The source and target map keys are requirement IDs, never facility IDs or array indexes. A facility endpoint must use `FacilityPort`; the logical external half of a dangling endpoint uses `ExternalDangling` and names the same selected facility port plus its outward side. Component ownership is explicit because a changed route invalidates every shared component it owns and every other owner route that depends on that component. A component ID is stable only while its canonical cell and owner set are unchanged; moving or changing ownership creates a new ID and enters the invalidation closure. The occupancy map is derived and checked against routes and components when the state is constructed rather than trusted as independent serialized truth.

Graph identity is collision-safe rather than digest-only:

```text
CumulativeGraphKey {
  schema_version,
  facilities: sorted [FacilityGraphRecord],
  requirements: sorted [RequirementGraphRecord]
}

FacilityGraphRecord { facility_instance_id, flattened_facility_id }
RequirementGraphRecord { requirement_id, fingerprint }
CumulativeGraphFingerprint { sha256_hex }
```

Records are sorted by their stable IDs. The diagnostic fingerprint is SHA-256 over a documented length-prefixed UTF-8 encoding of the complete key; it is never used as the sole equality check. In-memory reuse compares the complete `CumulativeGraphKey`. Numeric fields use unsigned big-endian bytes, enums use their schema-defined ASCII tags, and every variable-length field is prefixed by its unsigned 64-bit byte length. This avoids JSON object-order or display-format dependencies.

Retained route cells and components are hard occupied geometry for a candidate attempt unless their requirement is explicitly invalidated. New facilities and new routes may not overlap them except through a newly validated legal crossing. The subset router routes only the requested invalidated/new requirement set, then validates the complete retained-plus-new witness.

Invalidation is the transitive closure of:

- a new, removed, or fingerprint-changed requirement;
- a requirement incident to a moved or rotated facility;
- a selected port that is no longer available;
- a retained route or component overlapped by changed facility geometry;
- a crossing/component relationship changed by a rerouted requirement.

Routing failure returns:

```text
RoutingConflict {
  code,
  failed_requirement_ids,
  related_facility_ids,
  related_scc_ids,
  blocked_cells,
  blocking_requirement_ids,
  blocking_component_ids,
  message
}
```

Every entity list is deterministic and deduplicated. The MVP uses requirement, facility, SCC, and blocker identities for neighborhood expansion. More elaborate spatial-corridor extraction remains deferred.

### Neighborhood Constraint

Hard freezing is permitted only as a temporary large-neighborhood-search constraint outside the currently optimized neighborhood.

- Facilities outside the neighborhood may be fixed to the incumbent placement and rotation for one candidate attempt.
- Routes outside the invalidation set may be copied when validation proves they remain legal.
- Facilities inside the neighborhood are free within hard factory bounds; their prior values remain hints.
- A neighborhood result is accepted only after validation of the complete cumulative witness.
- Global refinement frees every facility but retains prior hints.

This is not the old anchor contract. A previous placement is never a permanent phase commitment.

## Incumbent Extension

When a new SCC frontier is added, the previous phase witness is not automatically feasible for the enlarged graph. `extend_incumbent` constructs a new-graph seed in deterministic steps:

1. Copy placements, rotations, ports, routes, and components whose stable requirements are unchanged.
2. Remove frontier routes superseded by newly introduced internal requirements.
3. Identify exposed downstream ports and route corridors associated with the new SCC.
4. Place new facilities near those exposed frontier locations using a small deterministic constructive portfolio.
5. Prefer prior ports and routes for unchanged requirements.
6. Route new and invalidated requirements.
7. Recompute logistics components and canonical bounds.
8. Run the independent witness validator.

If this succeeds, it becomes the initial incumbent for the phase. If it fails, the failure is diagnostic input to neighborhood selection; it is not proof of infeasibility. The phase may continue without an incumbent until its search budget is exhausted.

## Affected-Neighborhood Selection

Neighborhoods are graph- and conflict-based rather than uniform coordinate-radius boxes.

The deterministic MVP schedule is:

### Neighborhood 0: Frontier

- newly introduced SCCs;
- facility endpoints directly connected to those SCCs;
- superseded frontier routes and new internal routes.

### Neighborhood 1: One-Hop Repair

- Neighborhood 0;
- SCCs one condensation-graph edge away;
- prior routes incident to those SCCs;
- facilities and retained requirements named as blockers by `RoutingConflict`.

### Neighborhood 2: Bounded Conflict Closure

- Neighborhood 1;
- SCCs within two undirected condensation-graph hops of a failed or introduced SCC;
- blocker facilities, requirements, and components named by conflicts from Neighborhood 1;
- requirements incident to any facility added by this closure.

Closure stops after two graph hops for the MVP. It does not mean the entire connected component.

### Neighborhood 3: Global

- every facility, port choice, route, and logistics component in the cumulative graph.

Neighborhood escalation occurs when:

- no routed incumbent can be constructed;
- every candidate is invalid;
- no candidate improves the incumbent within the neighborhood budget;
- a structured routing conflict names entities outside the current neighborhood.

An unimproved incumbent remains available while the neighborhood expands. Every configured neighborhood receives one deterministic candidate-policy pass while phase budget remains. When a pass improves the incumbent, the same neighborhood restarts once from the improved incumbent. After a full pass without improvement, execution advances to the next neighborhood. The restart cap prevents an unbounded local loop; additional repeated LNS passes are deferred.

## Phase Optimization Loop

Each cumulative phase executes the following state machine:

```text
BUILD_GRAPH
-> EXTEND_INCUMBENT
-> OPTIMIZE_FRONTIER
-> OPTIMIZE_ONE_HOP
-> OPTIMIZE_BOUNDED_CONFLICT_CLOSURE
-> OPTIMIZE_GLOBAL_IF_BUDGETED
-> VALIDATE_AND_CANONICALIZE
-> COMPLETE
```

Detailed behavior:

1. Build the cumulative graph and stable route requirements.
2. Extend the previous witness into a candidate incumbent for the new graph.
3. Validate and score the extended witness when construction succeeds.
4. Allocate the phase budget across the deterministic neighborhood schedule.
5. Execute the deterministic candidate-policy sequence serially for the MVP.
6. Give each candidate attempt:
   - the same cumulative graph;
   - the current incumbent score as an upper bound at the orchestration layer;
   - prior full-solution hints;
   - one temporary free/fixed neighborhood definition;
   - one placement compactness policy or width cap;
   - one routing-order policy;
   - an explicit attempt deadline and candidate quota.
7. Route and independently validate every candidate before scoring it.
8. Replace the incumbent only when `CandidateRank` is strictly smaller.
9. Continue after the first feasible candidate until the phase budget or neighborhood schedule is exhausted.
10. Return the best incumbent with its termination reason.

If no incumbent is found, return `unknown` with structured failures. Constructive failure is not an infeasibility proof.

## Candidate Generation And Routing Coupling

The MVP must improve placement-routing coupling without rebuilding the full dense 500 by 500 model.

### Placement Candidate Producer

Replace the feasibility-only placement API with a time-limited candidate producer that:

- accepts full placement and rotation hints;
- accepts a temporary free/fixed facility set;
- respects hard bounds, port clearance, and non-overlap;
- optimizes a placement compactness surrogate within each candidate attempt;
- can produce multiple distinct candidates or deterministic portfolio alternatives;
- preserves its best candidate until the attempt deadline.

The existing `used_height` variable alone is not the routed-layout objective. Width-cap portfolios, canonical extents, approximate connection distance, and neighborhood-specific placement variants may be used to produce useful candidates, but final selection always uses the full routed `LayoutScore`.

### Sparse Routing Evaluator

For every placement candidate:

- retain unchanged valid routes where possible;
- assign prior ports first when still legal;
- reroute only invalidated or neighborhood-owned requirements initially;
- minimize route cells first and turns second;
- validate the complete witness, including retained routes;
- return structured conflicts on failure.

Placement candidates that cannot be routed do not become incumbents. Their conflicts may expand the neighborhood or add sound placement exclusions in a later cut-generation slice.

### Deferred Local Exact Refinement

A later implementation may build an exact joint placement/port/routing model only for a cropped neighborhood window while treating the rest of the incumbent as fixed boundary conditions. This is an extension point, not part of the deterministic MVP.

## Strategy Configuration And Budget Contract

The caller supplies one total strategy budget. It is not multiplied independently by every radius, phase, and routing retry.

The CLI and future web service load the same versioned DTO:

```text
IterativeOptimizationConfig {
  schema_version,
  total_time_limit_ms,
  final_refinement_reserve_percent,
  minimum_phase_attempt_ms,
  max_new_facilities_per_phase,
  candidate_attempts_per_neighborhood,
  same_neighborhood_restart_limit
}
```

MVP validation requires positive total and attempt durations, reserve percentage from 0 through 50, positive SCC and candidate quotas, and a restart limit of at most one. The executor receives an optional cancellation token as an explicit runtime input; the CLI passes a never-cancelled token, while a future web request may cancel it.

The initial release defaults are:

```text
total_time_limit_ms = 30000
final_refinement_reserve_percent = 20
minimum_phase_attempt_ms = 250
max_new_facilities_per_phase = 8
candidate_attempts_per_neighborhood = 3
same_neighborhood_restart_limit = 1
```

Slice 11 may tune these values from recorded benchmarks without changing the DTO or objective semantics.

The executor derives one absolute monotonic strategy deadline and mechanically allocates time as follows. All integer division rounds down.

```text
total_budget = total_time_limit_ms
initial_reserve = total_budget * final_refinement_reserve_percent / 100
ordinary_pool = total_budget - initial_reserve
reserve_remaining = initial_reserve

for each growth phase, including the phase that introduces the last SCC:
  remaining_growth_phases includes the current phase
  ordinary_grant = ordinary_pool / remaining_growth_phases
  ordinary_pool -= ordinary_grant
  phase_deadline = min(strategy_deadline, now + ordinary_grant)

  charge graph construction, incumbent extension, placement, routing,
         validation, diagnostics, and same-neighborhood restarts
         against this phase deadline

  after the phase:
    ordinary_pool += max(0, ordinary_grant - measured_phase_elapsed)

  if no incumbent exists when the ordinary grant expires:
    borrow = min(reserve_remaining, minimum_phase_attempt_ms)
    reserve_remaining -= borrow
    extend the phase deadline by exactly borrow, capped by strategy_deadline
    emit final-reserve-borrowed with the exact borrowed duration
    permit at most one reserve borrow for this phase

final_refinement_grant = min(
  time remaining before strategy_deadline,
  reserve_remaining + ordinary_pool
)
```

`minimum_phase_attempt_ms` is the minimum duration required to start a new solver candidate attempt; it is not a guaranteed minimum grant. If `ordinary_grant < minimum_phase_attempt_ms`, graph construction and incumbent extension may still run within the grant, but a candidate attempt starts only when its remaining phase time meets the minimum. This rule handles `ordinary_pool < remaining_growth_phases * minimum_phase_attempt_ms` without overspending or silently starving a later phase. If no incumbent exists, the one exact reserve chunk above is the only exception.

Within a neighborhood pass, the executor knows the remaining configured attempt slots in the current pass. Before each attempt it computes `attempt_grant = remaining_phase_time / remaining_attempt_slots`. It starts the attempt only when `attempt_grant >= minimum_phase_attempt_ms`; otherwise the pass terminates as budget-exhausted. Each producer invocation receives this absolute attempt deadline and `candidate_attempts_per_neighborhood` remains the number of invocation slots, not the number of placements it may yield. Each invocation may emit candidates only up to its explicit candidate quota from the versioned policy table. A same-neighborhood restart opens a new pass with a new `restart_index` and recomputes grants from the remaining phase time.

Every called solver, router, and validator receives the applicable absolute deadline or remaining duration. Results returned after their deadline are recorded as timed out and cannot replace the incumbent. There is no uncharged orchestration stage and no background work after the strategy deadline. The final pass receives the remaining reserve and returned ordinary time, never the original nominal values.

Required behavior:

- budget exhaustion returns the best incumbent already found;
- a phase with an extended incumbent cannot regress to `unknown` only because an improvement attempt timed out;
- no attempt may overwrite a better incumbent with a later worse result;
- cancellation checks occur between placement generation, routing, and validation;
- timing diagnostics use monotonic elapsed durations;
- deterministic serial candidate ordering decides ties.

## Status And Diagnostic Contract

Each phase records:

- phase index and introduced SCCs/facilities;
- cumulative facility and route-requirement counts;
- initial incumbent provenance and score, if any;
- final incumbent score;
- score delta for every component;
- attempted neighborhoods and candidate policies;
- candidates generated, routed, validated, improved, rejected, and timed out;
- reused, moved, newly placed, and rotation-changed facility counts;
- reused, invalidated, rerouted, and new route counts;
- structured routing conflicts;
- search-domain bounds and canonical used bounds;
- elapsed time by extension, placement, routing, validation, and total phase;
- termination reason;
- whether optimality was proven, remained unproven, or was not attempted.

Stable termination reasons include:

- `neighborhood-schedule-exhausted`;
- `phase-budget-exhausted-with-incumbent`;
- `phase-budget-exhausted-without-incumbent`;
- `global-optimum-proven`;
- `invalid-input`;
- `cancelled`.

The final strategy report records the same aggregate counters and identifies the authoritative final incumbent.

## Final Global Improvement

After the last SCC is introduced, the executor reserves time for one full-graph improvement phase.

- The last cumulative incumbent is the initial incumbent.
- Every facility may move and rotate.
- Every prior choice remains a hint.
- No obsolete anchor radius applies.
- The optimizer uses the global deterministic sparse/LNS candidate sequence in the MVP.
- The best validated full-graph witness remains authoritative even if refinement times out.

This pass prevents phase-local stability from becoming the final quality ceiling.

## Failure Semantics

- Invalid catalogs, wiring, or geometry contracts return `invalid-input`.
- A sound lower-bound violation may return `infeasible`.
- Failed constructive extension, routing, or neighborhood search returns `unknown` only when no incumbent exists.
- A failed improvement attempt does not invalidate an existing incumbent.
- A candidate that fails independent witness validation is rejected and reported as a solver/model defect; it is never silently repaired into the incumbent.
- A phase must not advance without a complete validated incumbent for its cumulative graph.

## Determinism

For identical input data, strategy configuration, and completed candidate-attempt prefix:

- SCC and neighborhood order is deterministic;
- stable entity IDs are deterministic;
- candidate policy keys are deterministic;
- score comparison is deterministic;
- equal-score selection follows `CandidateRank`;
- canonical translation removes meaningless global coordinate shifts;
- the selected witness is deterministic for the completed attempt set.

Wall-clock budgets may truncate the deterministic attempt sequence at different points on different hosts, so the plan does not promise bit-identical time-limited output across machines. A future reproducibility mode may replace time limits with deterministic solver-work and candidate quotas. Parallel candidate execution remains deferred until it can preserve deterministic candidate admission and reduction semantics.

## Rejected Alternatives

### Preserve Anchor Radii And Add An Objective

Rejected. The first feasible small-radius attempt would still prevent larger-neighborhood improvement, and global fallback would still discard useful hints.

### Treat Previous Coordinates As Permanent Commitments

Rejected. Newly introduced SCCs may require large movement or rotation changes to produce a compact routed layout.

### Rebuild The Full Dense 500 By 500 Model Every Phase

Rejected for the MVP. Route-variable growth is too large and defeats the purpose of incremental decomposition.

### Optimize Placement Bounds Without Routing Candidates

Rejected as the authoritative selector. Compact facility rectangles can be unroutable or require much longer transport paths.

### Accept The First Routed Witness And Refine Only At The End

Rejected. Poor early placement structure becomes a bad hint, degrades every history phase, and makes the final global pass do nearly all optimization work.

### Use Displacement As A Primary Objective

Rejected. Stability is useful for search and visualization, but it must not beat a shorter or more compact routed layout.

## Rollback And Cutover Policy

This is a hard internal cutover.

- Do not preserve `ANCHOR_RADII` as a legacy strategy inside the new executor.
- Do not translate new neighborhood reports back into movement-radius DTOs.
- Do not retain first-feasible selection behind an implicit fallback.
- Keep a separately named diagnostic baseline command only if benchmark comparison requires it; it must not be the production default.
- Remove obsolete APIs and tests in the slice that replaces them.
- Temporary compile failures are acceptable within a slice, but every committed slice must restore workspace verification.

## Tunable Parameters

The architecture does not depend on these values and they may be tuned from benchmarks:

- total interactive strategy budget;
- final-refinement reserve percentage within the fixed allocation algorithm;
- candidate-attempt count and per-policy candidate-yield quotas;
- spatial padding used by optional cropped exact refinement.

These are configuration and performance decisions. They must not change score semantics, incumbent validity, or neighborhood correctness.

## First Implementation Slice

Start with Slice 0 and commit its reproducible baseline before changing behavior. Then complete and commit Slice 1, followed by Slice 2. The first optimization commit must therefore build on stable requirement IDs and make a one-facility cumulative phase independent of the 500 by 500 search canvas before any optimizer claims are evaluated.
