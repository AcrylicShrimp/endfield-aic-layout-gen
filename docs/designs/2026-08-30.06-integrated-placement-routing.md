# Integrated Placement and Routing Model

## Purpose

The final layout solver must decide facility placement, facility rotation, port assignment, and logistics routes in one constraint model. A route generated after placement cannot prove that the chosen placement is routable, so post-placement A* is not the authoritative routing stage.

This document defines the target constraint contract and the implemented incremental slices.

## Stage Contract

### Planning Boundary

The user-facing tool accepts a final product, target rate, and optional items that should be treated as external input cutoffs. Before spatial solving it:

1. resolves the recipe dependency graph;
2. selects a recipe automatically only when the producer is unique;
3. returns an ambiguity diagnostic instead of guessing when multiple recipes can produce a required item;
4. computes throughput and facility instance counts;
5. expands the result into a fixed logical facility-instance graph.

The layout solver receives that fixed graph. Recipe selection, recipe mode selection, and production-graph discovery are not layout solver variables.

### Inputs

- a successful `FacilityInstanceWiringReport`;
- a validated facility catalog with footprints, rotations, and directional ports;
- hard `max_width` and `max_height` system bounds;
- a validated external item catalog that maps every item to exactly one of `belt` or `pipe`;
- a validated external transport catalog containing belt and pipe capacities;
- later: external definitions for allowed logistics components.

The item and transport catalogs are external runtime data. Game-balance values must not be compiled into the solver. Item transport is fixed input data, not a solver choice.

### Outputs

An integrated layout report contains:

- solver status;
- used layout bounds;
- selected facility positions and rotations;
- selected source and target ports for every routed logical edge;
- ordered route cells and transport kind;
- structured diagnostics.

The library can run indefinitely for proof-oriented tests or with an explicit wall-clock time limit. A timed run returns `feasible` with its incumbent layout when one exists, `optimal` when minimum total route length is proven, and `unknown` when the limit expires before any solution or proof.

### Invariants

- Every occupied facility cell and route cell lies within the hard W/H bounds.
- Facility footprints do not overlap.
- A facility route endpoint uses an output port at its source and an input port at its target.
- The routed item's transport kind, source port transport kind, and target port transport kind are identical.
- Route flow starts at the selected source connection cell and ends at the selected target connection cell.
- Route cells do not intersect facility footprints.
- Plain routes of the same transport kind do not share cells.
- A belt route and a pipe route may occupy the same horizontal cell because they use separate transport layers.
- Every non-endpoint route cell conserves flow.
- The returned route is derived from solver variables, not repaired after solving.

## Variable Model

For facility instance `i`, orientation `o`, and legal origin `(x, y)`:

```text
place[i,o,x,y] in {0,1}
sum(place[i,*,*,*]) = 1
```

Enumerated placement candidates make rotated port connection cells constants within each candidate. They also let routing endpoint activation be expressed directly from placement decisions.

For logical flow `k` and directed adjacent grid arc `(u,v)`:

```text
use[k,u,v] in {0,1}
```

For every grid cell `c`:

```text
sum(outgoing[k,c]) - sum(incoming[k,c])
  = source_at[k,c] - target_at[k,c]
```

`source_at` and `target_at` are sums of selected endpoint candidates whose rotated connection cell is `c`. Incoming and outgoing degree are each at most one for a simple route. Minimizing used arcs removes disconnected cycles.

## Constraint Translation Roadmap

| Game rule | Constraint representation |
| --- | --- |
| Hard system W/H | Generate only in-bounds placement, port, and route candidates. |
| Facility rotation | Exactly one enumerated orientation and origin per instance. |
| Facility collision | At most one selected placement candidate for every conflicting pair. |
| Directional ports | Endpoint candidates require output at the source and input at the target after rotation. |
| Belt versus pipe | Reject every endpoint candidate unless `item.transport == source_port.transport == target_port.transport`; transport is never selected as a free solver variable. |
| Continuous route | Directed-arc flow conservation from selected source cell to selected target cell. |
| Facility obstruction | A used route cell conflicts with every placement candidate covering that cell. |
| Belt direction | Directed arcs define item travel direction. |
| Per-line capacity | Reject an independent route above external transport capacity; later sum assigned rational rates on shared segments. |
| Splitter and converger | Activate an external component pattern when route degree exceeds the plain-line degree. |
| Same-layer crossing | Crossing occupancy requires a legal bridge pattern rather than two plain segments in one cell. |
| Belt and pipe overlap | Keep separate transport layers and constrain only combinations forbidden by the external rules. |
| Control port/filter | Bind the component's allowed item and rate fields to assigned logical flows. |

## Implemented Slices

Facility modes are flattened before this stage. Each mode becomes a dedicated facility definition with one fixed footprint, rotation set, and port setup, and every recipe directly references that flattened facility ID. The integrated solver has no facility-mode variable.

The first executable proof solved one facility-to-facility logical edge together with every facility placement:

- exactly one output port and one input port compatible with the item's fixed transport kind must exist;
- all facilities are placed by enumerated candidate variables;
- a directed simple grid path is solved in the same model;
- route length is minimized;
- no sharing, capacity, splitter, converger, bridge, or external boundary terminal is modeled yet.

The next slice generalizes the same model to every facility-to-facility logical edge in the input graph. Every route has its own directed arcs and endpoint choices, while all routes share the placement variables. The objective minimizes total route length. Facility occupancy excludes both transport layers. Route occupancy is exclusive within each transport layer, while one belt and one pipe may occupy the same horizontal cell. The slice therefore supports independent paths and cyclic flow graphs without silently introducing same-layer shared lines, crossings, bridges, splitters, or convergers.

External-input, target, and surplus nodes are modeled as selectable boundary terminals. Every boundary endpoint selects both a perimeter cell and its outward side. Boundary nodes must carry the same item as their logical edge.

The implemented proof supports multiple compatible fixed ports at each endpoint. It creates one endpoint option for each `(placement candidate, compatible port)` pair and constrains exactly one option to match the selected facility placement. Port direction and transport remain immutable input data.

Production-planning cycles are allowed upstream. The final multi-edge spatial model will receive the fixed cyclic flow graph and route every logical edge; production recipe rates and bootstrap inventory are not spatial solver decisions.

## Failure Modes

- failed upstream report;
- invalid hard bounds;
- missing facility definition;
- duplicate facility instance;
- missing, directionally invalid, or item-mismatched route endpoint;
- missing or ambiguous compatible port;
- no common endpoint transport;
- facility or route model infeasible;
- solver termination without a solution or proof;
- inconsistent extracted solver path.

## Evidence Boundary

Public game data exposes facility footprints and directional port coordinates. Public documentation describes belt and pipe lines, splitters, convergers, bridges, and control ports. Those sources establish the rule categories, but exact component geometry and all placement interactions still need representative in-game verification before their constraints are treated as authoritative.
