# First Factory Edit Learning Pilot: Fixed-Problem Fit

Status: provisional pilot hypotheses, 2026-09-07. Every design choice remains revisable.
The current phase is collaborative design only: this document does not authorize implementation,
timing probes, training, or evaluation execution.

Parent: [edit-policy design](2026-09-07.00-learned-factory-edit-policy.md).
Progress: [design tracker](../todos/2026-09-07.04-learned-factory-edit-design.md).

The user proposes deliberately fitting one fixed problem first: can it be learned at all, how
much does performance improve with training, and how do model size and architecture change those
curves? This supersedes held-out small-factory generalization as the first pilot question.

Resources: unrestricted local-Mac allocation; the latest user direction is CPU-only training
and evaluation for the first pilot and initial size comparisons. Begin small and progressively
increase model size to inspect performance characteristics if needed. Earlier RTX 5090 availability
remains a possible later resource, not the backend for this phase or an automatic fallback.
Future comparisons still need finite, declared horizons, checkpoints, and work accounting.
Availability does not authorize execution during this design-only phase.

## Questions and scope

Use exactly one immutable production request and one complete, validated initial layout for
all training and evaluation episodes. Deliberate memorization of this instance is acceptable.
Do not randomize requests, initial placements, translation, rotation, or production rates in
this first environment. Action sampling and independent training initializations may vary.

| Question | Main observation | Interpretation limit |
| --- | --- | --- |
| Can this setup fit the fixed problem? | Frozen trained policies repeatedly return better validated factories than their own untrained initializations. | A lucky training discovery alone does not show that the policy learned to reproduce improvement. |
| How does fit change with training exposure? | Checkpoint curves for area reduction and improvement frequency, alongside completion/reward diagnostics. | A flat finite curve is not proof of insufficient capacity or impossibility. |
| How does model size change performance? | Curves across a declared size ladder within one encoder family. | Compare both interaction exposure and actual compute; a bigger model can cost more per command. |
| How does architecture change performance? | Same-task curves with the same observable information, action interface, objective, and controlled training setup. | Results concern this instance and protocol; they do not rank architectures for unseen factories. |

Here, “overfit” means successful fit or memorization of one training instance. A single-instance
study cannot measure a train-versus-unseen-factory generalization gap or how much that gap grows.
Measure degree of fit with task quality and success frequency, not policy loss alone. Neither
validated return of the unchanged initial factory nor changed model weights is a learning result.

## Proposed RL environment

This is an edit environment around a complete factory, not a from-scratch construction episode.
The environment definition is independent of the encoder chosen to observe it.

| Interface | Proposed contract |
| --- | --- |
| Fixed input | Original production request, runtime catalog snapshot, initial complete layout, action/work configuration, and evaluator version. Record identities/hashes. |
| `reset` | Restore draft, working base, and episode best to the exact same initial layout. Reset command/work counters and episode-local state. Return the initial observation. |
| Observation | Whole draft geometry; facilities/rotations/ports; terminal bindings; network/channel identities; required rates and capacities; known or unresolved loads; pending obligations; latest valid working-base geometry; best score tuple; remaining command/work budgets. No expert next action. |
| Action | One of seven typed commands: `SET_PLACEMENTS`, `UNBIND_TERMINALS`, `BIND_TERMINALS`, `ERASE_TRANSPORT`, anchor-explicit `EXTEND`, local `CONNECT`, or `DISCARD_EDIT`. Exact domains remain to be specified for this instance. |
| Transition | Apply an explicit edit, derive components, and check completion automatically. Mechanically invalid commands leave geometry unchanged but consume budget. An incomplete draft remains editable. The engine never chooses replacement routes. |
| Valid completion | Verify the entire original request on the selected geometry, including exact flow/capacity requirements. Promote a valid draft to working base even if temporarily worse; update episode best only when the complete score tuple improves. |
| Reward | Relative decrease in best validated area after the command. No reward merely for changing geometry, closing a draft, or preserving the initial factory. |
| Normal termination | End at the declared command horizon and return episode best. An unresolved draft is never exported. Completion/improvement does not end the episode early. |
| Diagnostics | Structured command outcome, validation state and failure category, pending obligations, exact scores, and charged work. Each diagnostic has a stable code, severity, stage, message, and relevant entity when available. |

`DISCARD_EDIT` restores the latest valid working base without refunding work. There is no separate
route-start cursor or finish command: extensions name their anchors, and checking belongs to the
inducing edit. Explicit attachments determine network sharing; coincident coordinates do not
silently connect networks. The engine certifies flow on the policy-selected fixed graph. Unknown
flow is not zero, and an unknown validation result cannot promote a draft. These remain hypotheses.

Observation must distinguish states with different transitions or discard results. Encoder variants
must retain the same information about the draft, working base, budgets, and incumbent score.
Remaining horizon is observable. Runtime-derived geometry may expand temporarily; width/height
remain measured outputs, not game limits. Any finite experiment action-domain restriction must
be declared and justified for this diagnostic; it is not a production feasibility restriction.

Work guards need explicit outcomes before execution. A per-command expansion/checking limit
rejects or leaves a candidate uncertified according to its declared contract; it cannot turn
unknown into valid or infeasible. Normal fixed-horizon episodes are distinct from interruption
or a safety guard that prevents the planned exposure. Record these separately and specify value
bootstrap handling before implementation; do not pool incomplete runs into a completed learning
curve. Computational counters include rejected commands and automatic validation work.

### What resets and what keeps learning

Each episode starts at the same root. Policy/value weights and optimizer state persist across
training episodes; episode-local recurrent state, if any, resets. The run's RNG stream advances.
Cumulative checkpoints belong to one continuing learner per training seed, not separately
initialized models at each exposure point.

A run-wide champion may be retained as evidence, but it must not replace the next episode's
initial layout. Doing so would change the task during learning. Evaluation temporarily freezes
weights and observation-normalization state, starts from the same root, and performs no updates.
Use separate evaluation RNG streams so evaluation does not advance the training stream.

The resulting loop is: same initial factory -> a bounded edit episode -> collected experience ->
policy updates -> the same initial factory again. The exact PPO rollout/update batching remains
an algorithm setting; this description does not require one update per episode.

## Root admission and mechanical checks

Starting scope hypothesis: one naturally belt-only, connected, acyclic request with roughly
4-12 facilities and actual placement/routing improvement opportunities. This is a candidate
selection range, not a required size or a game constraint. Preserve every selected request's
facilities, recipes, production rates, and external obligations. Do not cut obligations from a
larger request to force admission. Prefer an inspectable instance with room for multiple quality
levels, so the learning curve does not immediately hit a trivial ceiling.

Before eventual learning, establish that the initial layout is independently valid and that at
least one strictly area-improving edit sequence fits the declared action/work envelope. Record
the sequence and final validation as an environment witness, not as model training labels or
reward shaping. Its result supplies a known attainable reference, not a proven optimum. Unless
an optimum is independently established, do not label distance from this witness an optimality
gap. Authored success establishes expressibility, not RL discovery or learnability.

Only cover behaviors actually needed by this root and its declared edit domain. Record whether
shared branches, merges, and crossings occur; do not require a complete mixed-transport/cycle
implementation just because the parent notebook discusses it. Resolve required semantics, or
select a different well-understood small request without claiming coverage of the omitted case.
Current helper/validator limitations in the parent design must not be inherited silently.

Load game data from external catalogs. Keep provenance for candidate selection and rejection,
and freeze the admitted request/layout before learning. No existing historical artifacts are
assumed to exist in a fresh clone. Fixtures and implementations have not been created here.

## Objective and learning curves

The user explicitly confirms that improvement curves are outcome-based and also asks to see
reward grow with training. Show returned complete-factory quality and episode rewards together.
Training losses and internal diagnostics help explain those outcomes; they do not replace them.

Let `A0` be initial complete area and `Bt` the best validated area after command t. Proposed
reward is `(B(t-1) - Bt) / A0`, with discount factor one and a true finite command horizon T.
Total return is `(A0 - BT) / A0`. Keep export selection lexicographic: area first, physical
belt/pipe tiles second, total route turns third. Area-only reward does not teach those lower
priorities; report all components. A valid temporary worsening receives no additional penalty.

| Curve | Measurement | Purpose |
| --- | --- | --- |
| Frozen-policy outcome | Final area reduction per evaluation episode, aggregated at each checkpoint; also report complete score tuples and improvement frequency. | Quality the current model can reproduce with a fixed evaluation opportunity. |
| Training episode reward | Undiscounted sum of rewards within each completed training episode, showing raw points and a declared moving average. | Whether the training policy receives more task reward as exposure increases; include zero-reward episodes. |
| Frozen-policy evaluation reward | Episode return distribution/mean under the fixed checkpoint evaluation protocol. | Reward performance with weights frozen, separate from the changing training policy. |
| Cumulative best discovery | Best validated factory ever encountered by the run, labeled separately. | Discovery history, not evidence that the current policy reproduces that result. |

Under the current reward, each episode's raw total reward equals its final relative area reduction.
The evaluation outcome and evaluation reward curves therefore coincide, apart from explicitly
different aggregation. Record both fields as a consistency check and to retain interpretability
if a later experiment changes reward. If auxiliary rewards, normalization, clipping, or shaping
are introduced, report raw task reward, auxiliary terms, and the signal supplied to the learner
separately; never relabel their sum as factory quality.

Do not use reward accumulated across all training episodes as the main improvement curve: it can
increase merely through additional attempts. Per-command reward frequency and positive reward
magnitude are useful secondary diagnostics. Declare smoothing windows in the run configuration,
retain raw values/variation, and mark interrupted episodes separately. Training reward and frozen
evaluation reward can differ because they come from different policy snapshots/sampling protocols;
do not combine them into one unlabeled series.

At each checkpoint, use a fixed number of evaluation episodes, each with the same root and
horizon. Plot the distribution/mean of final area reduction, frequency of strictly improving
returns, and the exact best/median score. Plot at least against cumulative submitted commands
and training elapsed time; also record completed episodes, optimizer updates, gradient exposure,
throughput, memory, inference/mask time, and validation work. An update count alone is not a
comparable training dose when rollout size or epochs differ.

Keep three quantities separate: cumulative best factory ever discovered during training,
frozen-policy performance under a fixed evaluation allowance, and policy/value optimization
losses. More attempts can improve the first with no improvement in the second; changed losses
alone do not establish task fit. Track validation closures, rejections, unfinished tails,
reward frequency, first improving episode, and time to declared quality levels to identify
where the loop is failing. Reaching a witnessed quality level is not a required product target.

Evaluations use declared rollout seed schedules shared across comparable configurations. They
are repeated measurements of the same task, not held-out-factory tests. Publish every independent
training seed; evaluation repetitions cannot substitute for fresh training replications. Use
training seeds as the replication unit when reporting across-run uncertainty, and keep rollout
variation distinct. Exact aggregation and intervals remain to be specified prospectively.

## Staged training, size, and architecture comparison

The following order limits confounding while directly serving the user's questions. It is a
candidate sequence, not a permanent ban on redesign after a diagnostic finding.

| Stage | Vary | Hold fixed | Read out |
| --- | --- | --- | --- |
| A: fixed-problem learning curve | Cumulative exposure of one baseline model, replicated with fresh training seeds. | Root, environment, reward, horizon, model, and training configuration within each curve. | Whether repeated improvement is learned; onset, growth, plateau, instability, and seed variability. |
| B: model size | Declared small/medium/large parameter budgets within the same encoder family. | Root/interface and initial comparison's optimizer recipe; use the same exposure checkpoints. | Fit versus commands and elapsed time, quality ceiling observed within budget, speed, and memory. |
| C: architecture | Candidate spatial, relational, and hybrid encoders. | Information available, command decoder semantics, environment/reward, and comparison protocol. | How representation changes fit and cost on this one task. |

Stage A has no universal pass/fail gate that forbids B or C: a failed baseline can motivate an
explicit size/architecture comparison. First check whether useful rewards/completions occur;
zero signal does not by itself identify a capacity shortage. Do not silently change reward or
action granularity along with the architecture and attribute the result solely to architecture.

### CPU-first model size proposal

Start at approximately **100,000 total trainable parameters**, including the shared encoder,
policy decoder, and value head. This is a proposed initial capacity, not a measured CPU-throughput
claim or a minimum capacity known to fit this task. Exact counts follow from the observation and
conditional decoder contract; report those counts before learning instead of calling a target
an implemented model size.

| Candidate | Approximate total parameters | CNN channels across three layers | Per-object MLP width | Fusion/decoder hidden width |
| --- | --- | --- | --- | --- |
| S: first baseline | 0.1M (100,000) | 16 / 32 / 32 | 32 | 64 |
| M: first increase | 0.4M (400,000) | 32 / 64 / 64 | 64 | 128 |
| L: further increase | 1.6M (1,600,000) | 64 / 128 / 128 | 128 | 256 |

Use the same layer counts, feature information, nonlinearities, shared actor/value encoder,
and typed action-head structure across this ladder. The starting hypothesis is three small
spatial convolution layers plus a shared two-layer per-object MLP and small conditional
policy/value heads. The user accepts omitting GNNs from this first model: no graph message-passing
or graph-attention encoder is included in S, M, or L. Encode facility/port/terminal attributes
with the MLP; retain explicit endpoint identities, bindings, and channel/network relationships
as input information available to the fusion/decoder. Connectivity information is not removed
just because the encoder has no GNN. Exact relation feature encoding remains to be specified;
do not introduce learned neighbor aggregation under the name of object preprocessing.

Preserve spatial/entity features for selecting coordinates and objects;
do not pool away action-relevant information merely to meet a parameter target. Layer kernels,
feature fusion, and the exact decoder still need a scoped specification.

Doubling hidden widths gives approximately fourfold growth in width-by-width weight matrices;
input/output terms do not scale identically, so the listed totals are planning targets rather
than counts derived from a finished network. Freeze the resulting exact width configurations
before comparison. Keep architecture/depth changes as separate interventions.

Begin with S's learning curve. If its fit is weak or an observed plateau merits a capacity test,
compare M and then L with the same instance, command horizon, reward, and exposure checkpoints.
An S success may also justify a comparison for learning speed or final quality. Each size starts
from fresh weights and optimizer state for its own continuing learning curve; do not grow a
trained S into M and interpret inherited training exposure as a clean size comparison. Warm-start
growth would be a separately labeled future experiment.

Weak performance alone does not show that S is too small. Use reward occurrence, completion,
and frozen-policy outcomes to decide whether a size increase is the next useful question; retain
the option to revise exploration, observations, or the interface as separate experiments. This
ladder is revisable and can be extended prospectively; L is not a CPU or product size limit.

### CPU execution and comparison cost

For this phase, environment execution, policy inference, value/policy updates, and evaluation all
run on the Mac CPU. No CUDA or MPS acceleration is assumed. Record the actual device/backend;
there is no automatic GPU retry. CPU-only does not mean single-threaded. Declare environment
worker count, tensor-library thread counts, and batch sizes, and calibrate them after execution
is authorized without changing the learning-task horizon to hide slow throughput.

Measure environment/edit/validation time, inference/masking time, optimizer-update time, peak
memory, and end-to-end commands per second separately. Parameter count alone does not specify
spatial activation size, candidate-scoring work, or environment cost. A slow validator would
motivate environment profiling, not a claim that the policy model needs a GPU. Replications may
run sequentially; do not oversubscribe CPU workers merely to run all seeds concurrently.

The [PyTorch performance tuning guide](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html)
documents CPU thread/runtime tuning considerations. It does not establish throughput for this
Mac, these candidate models, or this unimplemented environment. No package/backend choice or
timing measurement is implied by that reference.

### Architecture comparison after the initial baseline

GNN and CNN+GNN variants are deferred architecture candidates. Start with the CNN+per-object-MLP
baseline and its width ladder; no GNN is required before learning from that first comparison.
This is a revisable scope choice, not evidence that GNNs cannot help this task.

For architecture, start with approximately matched total parameter budgets and report the actual
counts, including shared versus separate actor/value weights. Every encoder must receive the
same underlying state information in a suitable representation, including bindings and remote
obligations. A CNN that omits required relational state is a representation-and-information
ablation, not a clean architecture comparison. An architecture with different routing actions is
a separate combined design comparison.

Equal parameters, equal interactions, and equal elapsed time cannot be assumed equivalent. Show
interaction-matched curves and compute/time-matched comparisons separately, recording hardware
and backend. Do not run one family on the Mac and another on the 5090 and attribute time differences
to architecture. A shared optimizer configuration is the first controlled comparison, not proof
of each model's best achievable fit; if tuning is needed, give candidates equal declared tuning
budgets and label tuned results separately. Model selection on this root is acceptable here and
must be disclosed before later generalization work.

Compare checkpoints to each configuration's own initialization because changing architecture
can change its untrained sampling behavior. Controls use the same command semantics and charge
all parameter decoding, cell expansion, checking, and search branching. No expert answer or
uncharged repair router is available. Define any search neighborhood/depth before comparison.
Control evaluation allowances stay fixed across checkpoints; a cumulative random-discovery
curve, if shown, is a separately labeled exposure-matched diagnostic.

sparse-reward suitability or suitable settings for this task. PPO/value settings, action masks,
conditional log probabilities, normalization, and batching remain to be specified. No dependency
selection, implementation, throughput measurement, or training has occurred.

## Interpretation and deferred generalization

Report fixed-instance fit with effect sizes, repeatability, training exposure, and uncertainty.
A successful finite run establishes learned improvement on this specific initial factory. It
does not establish optimality, arbitrary-factory learning, or the full Heavy Xiranite objective.
A null result is limited to the recorded configuration and budget. An invalid environment/checker
or incomplete allocation prevents interpreting the intended comparison. Do not silently extend
a disappointing run and retain the old endpoint label.

The previous 32-training/8-development/16-evaluation family-group proposal is deferred. It is not
an admission requirement or held-out gate for this overfit pilot. When generalization becomes the
next question, introduce new initial layouts and then new requests/topologies under explicit
grouped splits, keeping related layout descendants together. That later comparison must account
for architecture/hyperparameter selection on this first instance. No such dataset exists by
assertion in this document.
